    Formal specifications

    Testing samples a system's behavior; a specification describes all of it. A formal specification is a mathematical statement of what a system must do, written in a language precise enough that "does the system satisfy it?" is a mathematical question rather than an opinion. The picture: the spec draws a fence in the space of all possible behaviors, and verification proves the system never leaves the fence.

    Definition A specification is a predicate $\varphi$ over system behaviors. For a program computing $f$, a functional spec is a relation between inputs and outputs: $\forall x.\ P(x) \Rightarrow Q(x, f(x))$. For a reactive system, $\varphi$ is a property of infinite execution traces. A system $S$ satisfies $\varphi$, written $S \models \varphi$, iff every behavior of $S$ makes $\varphi$ true.
    Worked example Spec for integer square root: given input $n \ge 0$, the output $r$ must satisfy $r \ge 0 \wedge r^2 \le n \wedge (r+1)^2 > n$. Check candidates for $n = 10$: $r = 3$ gives $9 \le 10$ and $16 > 10$ ✓; $r = 4$ gives $16 \le 10$ ✗. Note what the spec does not say: which algorithm to use, how fast it runs. It pins down exactly the what, leaving the how free — and it is strong enough that the output is unique (if $r_1 < r_2$ both satisfied it, then $(r_1+1)^2 > n \ge r_2^2 \ge (r_1+1)^2$, contradiction).
    Pitfall A spec that restates the implementation ("returns the result of Newton's iteration") verifies nothing: it is satisfied by construction, bugs included. Good specs are extensional (about observable input/output or trace behavior) and simpler than the code — otherwise you've just written the same program twice and could have the same bug twice.
    Where this goes Specification gaming (Ch 35) is what happens when a spec is formal but wrong: the optimizer satisfies the letter, not the intent. Formal methods verify code against specs; alignment asks whether the spec captures what we meant.
    Drill
    1. EASY Write a formal spec for "sort a list of integers." A common first attempt says only "the output is sorted." What's missing?
      Solution
      Also require the output to be a permutation of the input. Spec: output $y$ satisfies $\forall i < j.\ y_i \le y_j$ (sorted) and $\text{multiset}(y) = \text{multiset}(x)$ (permutation). Without the second clause, return [] or return [1,2,3] "sorts" everything.
    2. MED Spec: "$\forall n \ge 0$: output $r$ satisfies $r^2 \le n$." Give three wildly different programs that satisfy it, and strengthen the spec until only correct integer square roots pass.
      Solution
      Satisfying programs: always return 0 ($0 \le n$); return 1 if $n \ge 1$ else 0; return the true floor sqrt. Underspecification lets degenerate programs through. Strengthen with maximality: add $(r+1)^2 > n$ and $r \ge 0$. Now $r = \lfloor\sqrt n\rfloor$ is forced (uniqueness argument as in the worked example).
    3. HARD For an LLM agent that "may only send emails the user approved," formalize the property as a trace predicate, and identify the observation problem that makes it harder than the sqrt spec.
      Solution
      Trace alphabet: events $\text{approve}(m)$, $\text{send}(m)$, plus others. Property: $\forall m.\ \square(\text{send}(m) \Rightarrow \blacklozenge\, \text{approve}(m))$ — every send of message $m$ is preceded (past-time "once", $\blacklozenge$) by an approval of that same $m$. Hardness: (1) identity of $m$ — if the agent edits the message after approval, is it "the same" message? The spec needs a canonical form or must bind approval to an exact hash, trading usability for rigor. (2) The events must be defined at a trusted observation boundary (the runtime's tool layer, Ch 32), not the agent's self-report — a spec over unobservable or agent-reported events is unenforceable. Formalizing forces these decisions into the open; that is much of its value.

    Preconditions

    A precondition is the caller's half of a contract: what must be true before the operation runs. Inside the precondition, the implementation may assume the world is sane; outside it, all bets — and all guarantees — are off. Preconditions turn "defensive programming everywhere" into a division of labor: the caller establishes, the callee assumes.

    Definition For an operation $\mathit{op}$, a precondition $P$ is a predicate on the state (and arguments) such that the contract only promises the postcondition when $P$ held at entry: if $P$ fails, behavior is unconstrained by the contract (or, in a checked design, $\mathit{op}$ must refuse to run). Weaker $P$ = stronger obligation on the implementer; stronger $P$ = stronger obligation on the caller.
    Worked example Binary search over array $a$ for key $k$. Precondition: $a$ is sorted ascending. With $a = [3, 9, 4, 7]$ (unsorted) and $k = 4$: probe middle $a[1] = 9 > 4$, recurse left into $[3]$, report "not found" — wrong, and no code bug anywhere. The algorithm is correct relative to its precondition; the caller broke the contract. This is why verified components come with verified preconditions: correctness composes only along satisfied contracts.
    Think first An agent's tool has precondition "file exists and is under 10 MB." Should the tool check this itself (and fail cleanly), or trust the agent? What changes versus human callers?
    Reveal
    Check it. With human programmers, unchecked preconditions are a (debatable) performance choice among trusted parties. An LLM agent is an unreliable, possibly prompt-injected caller: every tool boundary is a trust boundary, so preconditions must be validated, not assumed — this is exactly precondition checking from Ch 32. The contract stays the same; who bears the burden of enforcement moves to the boundary.
    Drill
    1. EASY State a sensible precondition for pop() on a stack, and what the contract says if it's violated.
      Solution
      Precondition: the stack is nonempty. If violated, the unchecked contract promises nothing (undefined behavior); a checked design instead specifies "raises EmptyStackError, state unchanged" — which is really a different, total contract with precondition true and a case-split postcondition.
    2. MED Which is the weakest precondition under which x = 10 / (a - b) executes without error and yields $x > 1$ (integer-free, real division)?
      Solution
      Need $a - b \ne 0$ and $10/(a-b) > 1$. The latter: if $a - b > 0$, $10 > a - b$, so $0 < a - b < 10$. If $a - b < 0$, $10/(a-b)$ is negative, never $> 1$. Weakest precondition: $0 < a - b < 10$. (This is Dijkstra's $\mathit{wp}$ computed by hand — the weakest condition guaranteeing the postcondition.)
    3. HARD Component A promises postcondition $Q_A: y \in [0, 100]$. Component B requires precondition $P_B: y \in [0, 50]$. The pipeline runs A then B. Is it verified? Give the general composition rule and two fixes.
      Solution
      Not verified: composition requires $Q_A \Rightarrow P_B$, but $y \in [0,100] \not\Rightarrow y \in [0,50]$ — A may legally output 80 and B's behavior is then unconstrained. General rule: a chain $A;B$ is verified iff $P = P_A$ holds initially and each postcondition implies the next precondition. Fixes: (1) strengthen A's spec (prove it actually yields $[0,50]$, if true); (2) insert a verified adapter/guard: if y > 50: handle, whose postcondition is $y \in [0,50]$ on the pass-through path. A third option — weaken B's precondition by reproving B on $[0,100]$ — is often costliest. The implication check between contracts is what "modular verification" means.

    Postconditions

    The postcondition is the callee's promise: what is true when the operation returns, assuming the precondition held. Together, precondition and postcondition form the contract $\{P\}\ \mathit{op}\ \{Q\}$ — everything a caller may rely on, and nothing more. A caller that depends on unpromised behavior is a bug waiting for a refactor.

    Definition A postcondition $Q$ is a predicate over the final state, the return value, and (via logical "old" values, written $x_{\text{old}}$) the entry state. Total correctness contract: if $P$ holds at entry, $\mathit{op}$ terminates and $Q$ holds at exit. Partial correctness drops the termination promise: if it terminates, $Q$ holds.
    Worked example withdraw(acct, amt). Precondition: $\mathit{amt} > 0 \wedge \mathit{balance} \ge \mathit{amt}$. Postcondition: $\mathit{balance} = \mathit{balance}_{\text{old}} - \mathit{amt}$ and the returned receipt references the transaction. Check an implementation that also charges a hidden fee: final balance $= \mathit{balance}_{\text{old}} - \mathit{amt} - 1 \ne \mathit{balance}_{\text{old}} - \mathit{amt}$ — postcondition violated, caught by any runtime contract checker without knowing anything about fees. The "old" value is what makes the promise checkable: postconditions relate after to before.
    Pitfall Postconditions that only constrain the return value and forget the frame: what did NOT change. "Returns the sorted list" is satisfied by an implementation that also deletes a random file. Frame conditions ("nothing outside $X$ is modified") are half the contract, and precisely the half that matters for agent tools with side effects (Ch 32's blast radius).
    Drill
    1. EASY Write pre- and postconditions for max(a, b) returning $m$.
      Solution
      Precondition: true (total function). Postcondition: $(m = a \vee m = b) \wedge m \ge a \wedge m \ge b$. Both clauses are needed: the first alone allows returning the min... no — the first alone allows returning either argument even the smaller; the inequalities alone allow returning $a+b$ for positive inputs.
    2. MED Contract: $\{x \ge 0\}\ y := \sqrt{x}\ \{y^2 = x \wedge y \ge 0\}$. A colleague claims the stronger postcondition $\{y^2 = x\}$ (dropping $y \ge 0$) is "the same, but simpler." Who's right, and what does a caller lose?
      Solution
      Dropping $y \ge 0$ weakens the postcondition (fewer guarantees, more implementations allowed — e.g. returning $-2$ for $x = 4$). A caller who then computes $\log y$ or compares $y \le y'$ can break. Direction matters: strengthening a postcondition or weakening a precondition makes a contract stronger (safer to rely on); the colleague did the opposite.
    3. HARD An agent tool apply_patch(repo, diff) should have what postcondition and frame condition to support verified rollbacks (Ch 32)?
      Solution
      Postcondition: the working tree equals $\text{apply}(\mathit{tree}_{\text{old}}, \mathit{diff})$; the return value contains an undo token $u$ with the property $\text{apply}(\text{apply}(\mathit{tree}_{\text{old}}, \mathit{diff}), \text{undo}(u)) = \mathit{tree}_{\text{old}}$ (a two-sided inverse on the touched paths). Frame: only paths mentioned in $\mathit{diff}$ are modified; the index, untracked files, and everything outside the repo are unchanged. The frame is what makes rollback sufficient: undoing the diff restores the world only if nothing else changed. Without a frame condition, "rollback" restores the files but not the deleted database — the tool's contract must say the database was never touchable.

    Invariants

    An invariant is a property that is always true — before and after every operation, at every observable moment. Where pre/postconditions guard single operations, invariants guard the system's whole life. The proof pattern is induction (Ch 3): true initially, preserved by every step, therefore true forever. Almost every safety argument in this chapter reduces to finding the right invariant.

    Definition For a transition system with states $S$, initial states $I \subseteq S$, and transition relation $\to$, a set $\mathit{Inv} \subseteq S$ is an inductive invariant iff (1) $I \subseteq \mathit{Inv}$ and (2) $s \in \mathit{Inv} \wedge s \to s' \Rightarrow s' \in \mathit{Inv}$. Then every reachable state lies in $\mathit{Inv}$. A property can be invariant (true in all reachable states) without being inductive; proofs need an inductive strengthening.
    Worked example Loop computing $s = 0; i = 0;$ then while $i < n$: $s \mathrel{+}= 2i + 1;\ i \mathrel{+}= 1$. Claim: invariant $s = i^2$. Base: $0 = 0^2$ ✓. Step: assume $s = i^2$ before an iteration; after, $s' = i^2 + 2i + 1 = (i+1)^2 = (i')^2$ ✓. At exit $i = n$, so $s = n^2$: the loop provably computes squares. Every loop-correctness argument you'll ever write has this three-beat shape — establish, preserve, conclude at exit.
    Worked example (non-inductive) System: $x$ starts at 0; each step does $x := x + 2$. Property "$x \ne 5$" is invariant (reachable states are even) but not inductive: $x = 3$ satisfies $x \ne 5$ yet steps to 5. The inductive strengthening "$x$ is even" implies $x \ne 5$ and is preserved. Finding such strengthenings is the creative core of verification — and the part modern tools ask humans (or LLMs) to supply.

    1. EASY Loop: $a = 1$; repeat $a := 3a$. Which of these are invariants: (i) $a$ odd; (ii) $a \le 100$; (iii) $a$ is a power of 3?
      Solution
      (i) yes — odd × 3 stays odd, base 1 is odd. (ii) no — fails after 5 steps ($243$). (iii) yes — base $3^0$, step multiplies by 3. Both (i) and (iii) are also inductive as stated.
    2. MED Euclid's algorithm: while $b \ne 0$: $(a, b) := (b, a \bmod b)$. State the invariant that proves it returns $\gcd(a_0, b_0)$, and verify the preservation step.
      Solution
      Invariant: $\gcd(a, b) = \gcd(a_0, b_0)$. Preservation: $\gcd(b, a \bmod b) = \gcd(a, b)$ because any common divisor of $a, b$ divides $a - qb = a \bmod b$, and conversely any common divisor of $b, a\bmod b$ divides $qb + (a \bmod b) = a$ — same divisor sets, same gcd. At exit $b = 0$: $\gcd(a, 0) = a$, so the returned $a$ equals $\gcd(a_0, b_0)$.
    3. MED An agent system maintains "every in-flight task has exactly one owner." Which operations must be checked to prove it inductively?
      Solution
      Every transition that touches ownership or task lifecycle: create-task (must assign exactly one owner atomically), delegate (must transfer, not copy — remove old owner and add new in one step), agent-crash/reap (must reassign orphaned tasks — this is where the invariant usually breaks), complete-task (removes it from in-flight). Inductive proof = a case per transition; the value of the exercise is that it forces you to enumerate the transitions, at which point the crash case reveals itself.
    4. HARD Prove: in the system $x := x + y;\ y := y + 2$ starting from $x = 0, y = 1$, the property $x$ is a perfect square always holds. Find the inductive invariant.
      Solution
      Trace: $(x,y) = (0,1) \to (1,3) \to (4,5) \to (9,7) \to (16, 9)$: $x = k^2$, $y = 2k+1$ at step $k$. Inductive invariant: $\exists k \ge 0:\ x = k^2 \wedge y = 2k + 1$ — equivalently $4x = (y-1)^2 \wedge y$ odd $\wedge\, y \ge 1$. Base: $4\cdot0 = 0 = (1-1)^2$ ✓. Step: new $x' = x + y = k^2 + 2k + 1 = (k+1)^2$, new $y' = y + 2 = 2(k+1) + 1$ ✓. The bare property "$x$ is a square" is not inductive (state $x = 4, y = 4$ satisfies it but steps to $x = 8$); coupling $x$ to $y$ is the strengthening.

    Hoare logic

    Hoare logic turns "this program is correct" into a derivation you can check line by line. Its sentences are triples $\{P\}\ C\ \{Q\}$: if $P$ holds and you run $C$, then $Q$ holds after. Each program construct gets one inference rule, so a correctness proof decomposes along the program's syntax — the chain rule of verification.

    Reveal
    Substitute: $(x+3)^2 > 25$, i.e. $x + 3 > 5$ or $x + 3 < -5$, i.e. $x > 2 \vee x < -8$. Weakest-precondition calculation is just substitution for assignments — the mechanical heart of every deductive verifier.

    1. EASY Is $\{x = 3\}\ x := 2x\ \{x = 6\}$ derivable? Show it with the assignment rule.
      Solution
      Assignment rule with $Q: x = 6$ gives precondition $Q[2x/x]: 2x = 6$, i.e. $x = 3$. Exactly the stated precondition, so yes.
    2. MED Derive the weakest precondition of the sequence $y := x + 1;\ z := 2y$ for postcondition $z > 10$.
      Solution
      Backwards: $\mathit{wp}(z := 2y,\ z > 10) = 2y > 10 = y > 5$. Then $\mathit{wp}(y := x+1,\ y > 5) = x + 1 > 5 = x > 4$. So $\{x > 4\}$ is weakest; any stronger condition (e.g. $x \ge 100$) also works via the consequence rule.
    3. HARD Prove partial correctness: $\{x = a \wedge y = b\}\ \texttt{while } y \ne 0\ \{x := x + 1;\ y := y - 1\}\ \{x = a + b\}$, assuming $b \ge 0$. Give invariant, preservation, exit, and the variant for total correctness.
      Solution
      Invariant $I: x + y = a + b \wedge y \ge 0$. Establish: $x + y = a + b$ ✓, $y = b \ge 0$ ✓. Preserve: assume $I \wedge y \ne 0$ (so $y \ge 1$). After the body: $x' + y' = (x+1) + (y-1) = x + y = a + b$ ✓ and $y' = y - 1 \ge 0$ ✓. Exit: $I \wedge y = 0$ gives $x = a + b$ ✓. Variant: $y \in \mathbb{N}$, strictly decreases; hence termination, so total correctness. (Note how the invariant is a conservation law — the quantity $x + y$ is conserved by the dynamics. Good invariants very often are.)

    Program verification

    Program verification assembles the pieces: annotate the code with contracts and invariants, generate the logical obligations each rule demands, and discharge those obligations with a theorem prover. The pipeline — annotate, generate verification conditions, solve — is what tools like Dafny, Why3, and Frama-C automate, with SMT solvers (later this chapter) as the engine.

    Definition A verification condition (VC) is a pure logical formula whose validity implies a Hoare triple. VC generation walks the program backwards computing weakest preconditions; each loop contributes three VCs: $P \Rightarrow I$ (entry), $\{I \wedge b\}\,\text{body}\,\{I\}$ unrolled to a formula (preservation), and $I \wedge \neg b \Rightarrow Q$ (exit). The program is verified iff all VCs are valid.
    Worked example Verify abs: $\{ \text{true} \}$ if $x < 0$ then $y := -x$ else $y := x$ $\{ y = |x| \wedge y \ge 0 \}$. Two VCs from the if-rule + assignment: branch 1: $x < 0 \Rightarrow (-x = |x| \wedge -x \ge 0)$ — valid since $x<0$ gives $|x| = -x > 0$. Branch 2: $\neg(x<0) \Rightarrow (x = |x| \wedge x \ge 0)$ — valid since $x \ge 0$. Both VCs are quantifier-free arithmetic an SMT solver settles in microseconds. Scale that recipe up and you have verified compilers (CompCert) and verified OS kernels (seL4) — the same three-step pipeline, with far harder invariants.
    Pitfall "Verified" always means "verified against this spec, under these assumptions" — the compiler is trusted or verified separately, the hardware model is assumed, the spec may be incomplete. seL4's proofs famously exclude, e.g., timing channels. A verification claim without its assumption list is marketing.
    Where this goes LLMs now draft the annotations (invariants, contracts) and provers check them — the generator–verifier pattern of Ch 33 with a sound verifier, and the model for tool-verified reasoning in Ch 30.
    Drill
    1. EASY Why is it fine for an unreliable LLM to propose loop invariants in this pipeline?
      Solution
      Because invariants are checked, not trusted: a wrong invariant fails the generated VCs and is rejected; a right one is machine-confirmed. Soundness lives in the checker, so the proposer only affects completeness/cost — the ideal division of labor between creative-but-fallible and mechanical-but-sound.
    2. MED Generate the three loop VCs for the summation program of the Hoare section (invariant $I: s = i(i-1)/2 \wedge 0 \le i \le n$, guard $i < n$, post $s = n(n-1)/2$, pre $n \ge 0$).
      Solution
      Entry: $n \ge 0 \Rightarrow (0 = 0 \wedge 0 \le 0 \le n)$ — valid. Preservation (body $s := s+i; i := i+1$, wp backwards): $s = i(i-1)/2 \wedge 0 \le i \le n \wedge i < n \;\Rightarrow\; s + i = (i+1)i/2 \wedge 0 \le i + 1 \le n$ — valid ($s + i = i(i-1)/2 + i = i(i+1)/2$; $i + 1 \le n$ from $i < n$). Exit: $s = i(i-1)/2 \wedge 0 \le i \le n \wedge i \ge n \Rightarrow s = n(n-1)/2$ — valid since $i = n$. All three are formulas over integers with no program text left: that's the point of VC generation.
    3. HARD Your verifier proves the VCs, yet the deployed program misbehaves. List four distinct places the gap can live.
      Solution
      (1) Spec gap: the postcondition doesn't capture the real requirement (verified sort, but the requirement was stable sort). (2) Model gap: the semantics used for VC generation differ from reality — unmodeled integer overflow, floating point, concurrency, exceptions. (3) Toolchain gap: compiler, runtime, or hardware deviates from the assumed semantics (miscompilation, bit flips). (4) Environment/assumption gap: preconditions assumed at the boundary aren't actually established by callers, or the OS/library contracts the proof leaned on don't hold. Verification moves bugs from "anywhere in the code" to "somewhere in this short assumption list" — a huge, but not total, victory.

    Type systems

    A type system is the lightweight, always-on formal method you already use: a compositional proof, computed by the compiler, that certain errors cannot happen at runtime. Each expression gets a type; rules say how types combine; and the slogan — well-typed programs don't go wrong — is a real theorem about a real class of errors.

    Definition A type system assigns judgments $\Gamma \vdash e : \tau$ ("in context $\Gamma$, expression $e$ has type $\tau$") via inference rules, e.g. $\frac{\Gamma \vdash f : \sigma \to \tau \quad \Gamma \vdash x : \sigma}{\Gamma \vdash f\,x : \tau}$. Soundness is the pair: progress (a well-typed program is either a value or can step) and preservation (types are invariants of evaluation: if $e : \tau$ and $e \to e'$ then $e' : \tau$). Types are exactly an inductive invariant over the small-step transition system of execution.
    Worked example Typecheck $f(g(3))$ where $g : \text{int} \to \text{str}$ and $f : \text{str} \to \text{bool}$. Judgment: $3 : \text{int}$; application rule gives $g(3) : \text{str}$; application again gives $f(g(3)) : \text{bool}$ ✓. Now swap: $g(f(\dots))$ — $f$ needs a $\text{str}$, but suppose we pass $3$: the rule's premise $3 : \text{str}$ fails, no derivation exists, program rejected before running. The proof of "no int-where-str-expected error at runtime" was assembled compositionally from one-line rules — no execution, no search, linear time. That trade (limited properties, zero effort) is why types are the most deployed formal method on earth.
    Pitfall Type soundness only excludes the errors the type language can express. Classic Java: no type errors, yet NullPointerException — because null inhabited every reference type. Richer type languages (option types, refinement types like $\{x : \text{int} \mid x > 0\}$, dependent types) push more properties into the checked zone, at rising annotation cost, until at the far end the type checker is a proof assistant.
    Drill
    1. EASY With $h : \text{int} \to \text{int} \to \text{bool}$ (curried), what is the type of $h\,5$? Of $h\,5\,7$?
      Solution
      $h\,5 : \text{int} \to \text{bool}$ (partial application); $h\,5\,7 : \text{bool}$. Currying means the arrow associates right: $\text{int} \to (\text{int} \to \text{bool})$.
    2. MED Explain "preservation is an inductive invariant" by matching the pieces to the invariant definition earlier in this chapter.
      Solution
      States = programs (expressions); transitions = evaluation steps $e \to e'$; initial states = the typechecked source program; invariant set = $\{e : e \text{ has type } \tau\}$. Preservation is exactly the preservation clause of inductive invariance; typechecking the source is the base case; progress converts the invariant into the safety property "never stuck at a type error." The compiler is a proof-by-induction generator.
    3. HARD Design a refinement-typed interface for an agent tool transfer(from, to, amount) so that entire classes of misuse are unrepresentable, and note what remains unverified.
      Solution
      Types: amount : {x : int | 0 < x ≤ limit(from)} (positive, within the caller's authorized limit); from : OwnedAccount(caller) (an account type parameterized by an ownership proof — capability-style, Ch 32); to : ValidatedAccount (only constructible via the validation routine). Now negative transfers, unauthorized sources, and unvalidated destinations are type errors: unrepresentable, not merely checked at runtime. Remains unverified: whether limit reflects current policy, races between the limit check and execution (needs transactional semantics), and whether the transfer should happen (intent — no type captures that). Types shrink the trusted surface; they don't eliminate judgment.
    Type soundness ("well-typed programs don't go wrong") is proved via which pair of lemmas?
    Progress: a well-typed term is a value or can step. Preservation: stepping keeps the type. Together they imply execution never reaches a stuck (type-error) state — an induction along the execution trace.

    Proof assistants

    A proof assistant (Lean, Coq/Rocq, Isabelle, Agda) is an environment where proofs are data: you build a formal proof object interactively, and a small trusted kernel checks every step against the rules of logic. Nothing is accepted on authority — not the user's, not an LLM's, not a famous mathematician's. The kernel is the whole ballgame: trust it, and you may trust everything it accepts.

    Definition Most assistants rest on the Curry–Howard correspondence: propositions are types, proofs are programs. A proof of $A \to B$ is a function turning proofs of $A$ into proofs of $B$; a proof of $A \wedge B$ is a pair. Checking a proof = typechecking a term, so the trusted base is a typechecker of a few thousand lines — the de Bruijn criterion: huge proof searches are fine because the found proof is re-checked by the tiny kernel.
    Worked example Proposition: $A \wedge B \to B \wedge A$. Proof-as-program: $\lambda p.\ (\mathrm{snd}\ p,\ \mathrm{fst}\ p)$ — take the pair, swap it. Typecheck: $p : A \times B$, so $\mathrm{snd}\,p : B$ and $\mathrm{fst}\,p : A$, so the result is $B \times A$ ✓. In Lean syntax: fun p => ⟨p.2, p.1⟩. The "proof" of commutativity of ∧ literally is the swap function; the kernel verifying it is doing the two-line type derivation above.
    Where this goes Proof assistants give reasoning systems (Ch 30) a perfect outcome verifier: an LLM can flail through 1000 wrong proof attempts, and the one the kernel accepts is simply correct — the purest instance of the generator–verifier gap, and why formal math (AlphaProof, Lean-based pipelines) is a frontier for test-time search.

      Solution
      $\lambda a.\ \lambda b.\ a$ — take a proof of $A$, take a proof of $B$, discard it, return the proof of $A$. (The K combinator.) The type is inhabited for any $A, B$, matching the tautology.
    2. MED Why does the de Bruijn criterion make LLM-generated proofs trustworthy even though LLMs hallucinate?
      Solution
      The LLM's output is a candidate proof term; the kernel typechecks it against the theorem statement. A hallucinated step is a type error and the proof is rejected — the LLM contributes search, never trust. The residual risks are only: kernel bugs (small, heavily audited surface) and misstatement — proving a theorem that doesn't say what you think it says. The second is the live danger: reading formal statements carefully cannot be delegated to the kernel.
    3. HARD Under Curry–Howard with constructive logic, there is no term of type $A \vee \neg A$ for arbitrary $A$ (no proof of excluded middle). Explain why in computational terms, and how classical assistants cope.
      Solution
      A constructive proof of $A \vee \neg A$ must be a program that, for any proposition $A$, decides which side holds and produces the evidence — a universal decision procedure for all propositions, which cannot exist (it would decide the halting problem, Ch 17: take $A$ = "this Turing machine halts"). So the type is uninhabited in pure constructive systems. Classical assistants (Isabelle/HOL; Lean with Classical.em) add excluded middle as an axiom: proofs may use it, but such proofs no longer carry executable content — you lose the program, keep the truth. The choice is per-development: constructive when you want certified algorithms extracted from proofs, classical when you just want theorems.

    Model checking

    Deductive proof asks you to be clever; model checking asks a machine to be exhaustive. Express the system as a finite transition system, the property in temporal logic, and the checker explores every reachable state. Its two superpowers: it is fully automatic, and when the property fails it hands you a concrete counterexample trace — the exact sequence of steps to the bug.

    Definition Given a transition system $M$ and a temporal property $\varphi$, model checking decides $M \models \varphi$ by state-space exploration. For safety properties this is reachability: compute $R$ = all states reachable from $I$; check $R \cap \mathit{Bad} = \emptyset$. Complexity is linear in $|R|$ — the catch being that $|R|$ explodes exponentially in the number of components ($n$ boolean variables → up to $2^n$ states). Symbolic methods (BDDs, SAT-based bounded model checking) fight the explosion by manipulating sets of states as formulas.
    Worked example Two agents, each either Idle or Using a shared resource, with a naive protocol: an agent may start using whenever it is idle. States: (I,I), (I,U), (U,I), (U,U). Initial: (I,I). Transitions: each agent independently I→U and U→I. Reachability: (I,I) → (U,I), (I,U) → (U,U) reachable in 2 steps. Bad set = {(U,U)} (mutual exclusion violated). Checker output: counterexample trace (I,I) → (U,I) → (U,U). Fix: add a lock variable — states (I,I,free), (U,I,taken), (I,U,taken); the transition I→U is only enabled when the lock is free and atomically takes it. New reachable set has no (U,U,·): property verified by exhaustion, no invariant-guessing needed.

    A token machine: counter starts at 0; each step adds a (green) or subtracts b (red) nondeterministically; bad states are counter ≥ danger. Explore reachability: which (a, b, danger) make the bad region unreachable? Watch BFS flood the state graph.

    Pitfall Model checking verifies the model, not the system. If the model abstracts away the behavior containing the bug (message reordering, timing, integer widths), the checker's "verified" is vacuous. Abstraction must be conservative: the model over-approximates real behaviors, so model-safe ⟹ system-safe — the direction of the approximation is everything.

    1. EASY A system has 12 boolean state variables. Upper bound on states? Why is this an upper bound on reachable states?
      Solution
      $2^{12} = 4096$ total valuations. Reachable states are a subset of all valuations (often a tiny one — that's what invariants describe), so 4096 bounds them from above.
    2. MED In the counter system (start 0; steps +3 or −2; values clamped to $[0, 15]$), is 11 reachable? Give a path or prove unreachability of some value instead.
      Solution
      Yes: 0 → 3 → 6 → 9 → 12 → 10 → 8 → 11. (Or shorter: 0→3→6→4→2→0... the direct one: +3,+3,+3,+3 hits 12, then −2 twice gives 8, +3 gives 11 — that's the path above, 7 steps.) In fact without clamping, reachable values from 0 using +3/−2 are all integers expressible as $3m - 2k \ge 0$ along a valid path; since $\gcd(3,2) = 1$, every value ≥ 0 becomes reachable within bounds — the interesting questions appear when clamping cuts paths off.
    3. HARD Bounded model checking (BMC) checks only traces of length ≤ $k$ by unrolling transitions into a SAT formula. What can BMC conclude when it finds no violation, and how do you make its answer complete?
      Solution
      No violation within $k$ steps ⟹ only "no counterexample of length ≤ k" — bugs at depth $k+1$ remain possible. Completeness routes: (1) reach the completeness threshold — e.g. the reachability diameter $d$ of the system (every reachable state reachable in ≤ $d$ steps); if $k \ge d$, absence of violations is a proof; computing $d$ is itself hard, but bounds exist. (2) $k$-induction: prove the property holds for the first $k$ states (base) and that $k$ consecutive property-satisfying states force a $(k{+}1)$-th (step); together they prove it for all depths. (3) IC3/PDR: incrementally build an inductive invariant from generalized blocked states. In practice BMC is run as a bug-finder (small $k$, fast), with inductive methods layered on for proofs.

    Transition systems

    The transition system is the common semantic currency of this chapter: programs, protocols, agents, circuits — all become states and arrows before verification begins. Get comfortable converting things to this form; every property you'll verify is a statement about the paths of such a graph.

    Definition A transition system is $M = (S, S_0, \to, L)$: states $S$, initial states $S_0 \subseteq S$, transition relation $\to \subseteq S \times S$, and a labeling $L : S \to 2^{AP}$ marking which atomic propositions hold in each state. A trace is a maximal sequence $s_0 \to s_1 \to \cdots$ with $s_0 \in S_0$; the system's behavior is its set of traces. Nondeterminism (a state with several successors) models scheduling, environment choice, and abstraction.
    Worked example A retry-loop agent as a transition system. States: $\{\text{Try}, \text{Wait}, \text{Done}, \text{Failed}(1), \text{Failed}(2)\}$... concretely: $S = \{T_0, T_1, T_2, W, D\}$ where $T_i$ = attempting with $i$ prior failures. $S_0 = \{T_0\}$. Transitions: $T_i \to D$ (success), $T_0 \to T_1$, $T_1 \to T_2$ (failure and retry), $T_2 \to W$ (give up, await human), $W \to T_0$ (human resets). Labels: $L(D) = \{\text{done}\}$, $L(W) = \{\text{escalated}\}$. Now precise questions: "is it possible to retry forever?" — no trace visits $T_i$ infinitely without passing $W$ (check: any cycle goes through $W$, i.e. through escalation) ✓. The vague design intuition became a checkable graph property.
    Think first How would you model "the network may drop any message" in a transition system of two communicating agents?
    Reveal
    As nondeterminism in the transition relation: from any state where a message is in flight, add two transitions — one delivering it, one dropping it (removing it from the channel without effect). Verifying a property over all traces then automatically covers every drop pattern; the adversarial network costs one extra arrow per message, not a probability model. When you need "drops are rare" quantitatively, you move to Markov chains (Ch 12) and probabilistic model checking.

    1. EASY Model a traffic light cycling green → yellow → red → green as a transition system. Is it deterministic?
      Solution
      $S = \{G, Y, R\}$, $S_0 = \{G\}$, arrows $G \to Y \to R \to G$, labels e.g. $L(G) = \{\text{go}\}$. Deterministic: every state has exactly one successor, so exactly one trace: $(G Y R)^\omega$.
    2. MED Two of the traffic lights above at an intersection, stepping asynchronously (either may advance at each step). How many states does the product system have, and which are "bad"?
      Solution
      Product: $3 \times 3 = 9$ states $(l_1, l_2)$. Bad: both green — $(G, G)$; typically also green–yellow pairs depending on the safety requirement.     3. HARD Give a transition system where every state satisfies "$p$ can eventually be reached" yet some trace never reaches $p$. What does this teach about branching- vs linear-time properties?
      Solution
      States $\{a, b\}$, $S_0 = \{a\}$, arrows $a \to a$, $a \to b$, $b \to b$, with $p$ holding only at $b$. From every state there exists a path to $p$ (from $a$: take $a \to b$), but the trace $a \to a \to a \to \cdots$ never reaches $p$. "Exists a path" (CTL's $\mathsf{EF}\,p$) is a branching-time property of the tree of possibilities; "all paths eventually" (LTL's $\mathsf F\,p$) is linear-time and fails here. Fairness assumptions (e.g. "the choice $a \to b$ cannot be ignored forever") are how checkers exclude such starvation traces when they're unrealistic.

    Safety properties

    "Nothing bad ever happens." A safety property forbids certain finite behaviors: violating one is an event you can point to — there, at step 17, the invariant broke. This finite-witness structure is why safety is the workhorse of verification: it's what invariants prove, what monitors can watch for, and what reachability checks decide.

    Definition A property $\varphi$ (a set of allowed infinite traces) is a safety property iff every trace violating $\varphi$ has a finite bad prefix: a finite prefix none of whose infinite extensions satisfy $\varphi$. Equivalently: $\varphi$ is closed in the topology of traces. Canonical form: $\square\, \neg \mathit{bad}$ ("always not-bad"). Safety is verified by proving an inductive invariant that excludes $\mathit{bad}$, or refuted by exhibiting a finite reachable path into it.
    Worked example Classify: (1) "the agent never spends more than \$100" — safety: a violating run has a prefix where cumulative spend first exceeds 100; nothing later can unspend it. (2) "every request is eventually answered" — not safety: any finite prefix with an unanswered request could still be extended by an answer; no finite witness of violation exists (it's liveness, next section). (3) "spend never exceeds \$100 and every purchase is eventually logged" — a conjunction of safety and liveness; the decomposition theorem says every linear-time property factors this way.
    Pitfall Teams "monitor for liveness violations" — but a monitor sees only finite prefixes, so it can never witness a pure liveness violation. What monitoring actually enforces is a safety approximation: "answered within 30 s." Choosing the bound is a design act; make it explicit rather than pretending the timeout is the property.
    Where this goes Runtime monitoring and safety shields (later this chapter) enforce exactly the safety fragment; Ch 35's control-and-monitoring agenda for powerful models is the same idea with fuzzier bad-sets.
    Drill
    1. EASY Safety or not: "the database is never corrupted"; "the two agents never both hold the lock"; "the system restarts infinitely often."
      Solution
      Safety; safety (a violating prefix shows both holding it); not safety — "infinitely often" can't be violated by any finite prefix (liveness).
    2. MED Show that an arbitrary intersection of safety properties is a safety property.
      Solution
      Let $\varphi = \bigcap_j \varphi_j$, each $\varphi_j$ safety. If a trace $\pi \notin \varphi$, then $\pi \notin \varphi_j$ for some $j$; since $\varphi_j$ is safety, $\pi$ has a finite prefix $u$ none of whose extensions satisfy $\varphi_j$ — hence none satisfy $\varphi \subseteq \varphi_j$ either. So every violator of $\varphi$ has a bad prefix: $\varphi$ is safety. (Practical reading: you can pile safety requirements onto a monitor freely; the conjunction stays monitorable.)
    3. HARD "The agent never exfiltrates the secret $s$" — why is this harder to cast as a checkable safety property than "never calls tool X," and what over-approximation makes it enforceable?
      Solution
      "Never calls tool X" is a predicate on single events — trivially monitorable. Exfiltration is an information-flow property: whether outputs depend on $s$, which is a relation between pairs of traces (would the output differ had $s$ differed?) — a "hyperproperty," not a set of traces, so no single-trace monitor can decide it exactly (and encodings can hide $s$ in innocuous-looking outputs). Enforceable over-approximations: taint tracking (label data derived from $s$; block any labeled data crossing the output boundary — may false-positive on benign summaries), or structural isolation (the component that saw $s$ has no channel to the output — Ch 32 sandboxing), which enforces noninterference by architecture rather than by watching content. The general lesson: when the true property isn't monitorable, enforce a stronger, cruder property that implies it.

    Liveness properties

    "Something good eventually happens." Liveness forbids infinite procrastination: requests get answered, the loop terminates, the agent eventually escalates. No finite observation can refute liveness — the good thing might still be coming — so proving it needs a different tool than invariants: a quantity that must decrease, or a fairness assumption that choices can't be dodged forever.

    Definition $\varphi$ is a liveness property iff every finite prefix can be extended to some trace satisfying $\varphi$ (the property is dense: no finite behavior is yet a violation). Canonical forms: $\lozenge\, \mathit{good}$ (eventually), $\square\lozenge\, \mathit{good}$ (infinitely often), $\square(\mathit{req} \Rightarrow \lozenge\, \mathit{resp})$ (response). Proof method: a ranking function $V$ into a well-founded order that strictly decreases until $\mathit{good}$ — the same mathematics as Lyapunov functions (Ch 28) and loop variants (Hoare logic above).
    Worked example Prove the retry system from the transition-systems section satisfies "every trace eventually reaches $D$ or visits $W$": rank states by $V(T_0) = 3, V(T_1) = 2, V(T_2) = 1$, target set $\{D, W\}$. Every transition from a $T_i$ either enters the target ($T_i \to D$, $T_2 \to W$) or strictly decreases $V$ ($T_0 \to T_1 \to T_2$). $V$ is a natural number, so it cannot decrease forever: within 3 steps the trace hits the target. Note what fails without the give-up arrow: with $T_2 \to T_0$ (retry forever), the trace $T_0 T_1 T_2 T_0 \cdots$ violates liveness, and indeed no ranking function exists on that cycle.
    Think first A scheduler alternates between two queues, but under load it always finds queue 1 nonempty and never serves queue 2. Which assumption, added to the model, restores "every queued task is eventually served"?
    Reveal
    Fairness. Weak fairness: a transition continuously enabled is eventually taken; strong fairness: a transition enabled infinitely often is eventually taken. Here "serve queue 2" is continuously enabled while queue 2 is nonempty, so weak fairness suffices to exclude the starving schedule. Fairness assumptions are promises about the scheduler/environment — liveness claims are always conditional on them, and an implementation must actually honor them (e.g. round-robin), or the proof is about a fiction.
    Drill
    1. EASY Classify: "the program terminates"; "the program never divides by zero"; "the agent asks for help infinitely often."
      Solution
      Liveness (no finite prefix refutes it); safety; liveness ($\square\lozenge$-form).
    2. MED Give a ranking function proving termination of: while $x > 0 \wedge y > 0$: if coin(): $x := x - 1;\ y := y + 2$ else: $y := y - 1$. Ordinary naturals won't work — why, and what does?
      Solution
      $y$ can grow (by 2) when $x$ decreases, so no single natural-number combination like $x + y$ works ($x{+}y$ can increase). Use a lexicographic rank $V = (x, y)$ ordered lexicographically: branch 1 decreases $x$ (dominant coordinate) — lex-decrease regardless of $y$; branch 2 keeps $x$, decreases $y$ — lex-decrease. Lexicographic orders on $\mathbb N^k$ are well-founded, so no infinite run exists. (This is why termination provers synthesize lexicographic and polyranking functions.)
    3. HARD Why can no runtime monitor enforce a liveness property, and what is the standard transformation to make "eventually responds" operationally enforceable? Formalize the transformed property and its cost.
      Solution
      A monitor decides based on finite prefixes; for liveness, every finite prefix is still extendable to a satisfying trace, so the monitor can never soundly raise a violation (it would be wrong about some extension). Transformation: bound the "eventually" — replace $\square(\mathit{req} \Rightarrow \lozenge\,\mathit{resp})$ with $\square(\mathit{req} \Rightarrow \lozenge_{\le k}\,\mathit{resp})$ ("responds within $k$ ticks"), which is safety: a prefix with a request unanswered for $k$ ticks is a bad prefix. Cost: (1) false alarms — legal-but-slow behaviors now count as violations, so $k$ trades alarm rate against detection latency; (2) the property changed — a system satisfying the original but not the bounded version (unbounded but finite delays) is now "wrong." Every SLA is exactly this transformation applied to a liveness wish.

    Temporal logic

    Propositional logic talks about one state; temporal logic talks about a state and everything after it. With a handful of operators — always, eventually, until, next — it expresses the safety and liveness patterns above as crisp formulas that model checkers consume directly. It is the type system of time.

    Definition Over a trace $\pi = s_0 s_1 s_2 \dots$ (writing $\pi^i$ for the suffix from $s_i$): $\square\varphi$ (G, always): $\forall i.\ \pi^i \models \varphi$. $\lozenge\varphi$ (F, eventually): $\exists i.\ \pi^i \models \varphi$. $\bigcirc\varphi$ (X, next): $\pi^1 \models \varphi$. $\varphi\,\mathsf U\,\psi$ (until): $\exists i.\ \pi^i \models \psi$ and $\forall j < i.\ \pi^j \models \varphi$. Dualities: $\neg\square\varphi \equiv \lozenge\neg\varphi$, $\neg\lozenge\varphi \equiv \square\neg\varphi$. Branching-time logics (CTL) add path quantifiers $\mathsf A$ (all paths), $\mathsf E$ (some path).
    Worked example Evaluate on the finite-then-looping trace $\pi$: $p$ holds at steps 0,1,2; $q$ holds at step 3; from step 4 on, nothing holds (looping on an empty label). (1) $\lozenge q$: true — $q$ at step 3. (2) $\square p$: false — $p$ fails at step 3. (3) $p\,\mathsf U\, q$: true — $q$ at step 3, $p$ at 0,1,2 ✓. (4) $\square(p \Rightarrow \lozenge q)$: check every step: steps 0–2 have $p$ and $q$ later ✓; steps ≥ 3 have no $p$, implication vacuously true ✓ — so true. (5) $\square\lozenge q$: false — after step 3, $q$ never recurs; the suffix from step 4 fails $\lozenge q$.

The temporal dualities are just quantifier dualities ($\neg\exists \equiv \forall\neg$) over time indices — LTL is first-order logic over $\mathbb{N}$ in disguise (with $\mathsf{U}$ adding the ordering).

    Linear temporal logic

    LTL is the specific temporal logic of single traces — linear time, no branching — and the lingua franca of model checkers (SPIN, NuSMV), runtime monitors, and the hardware-adjacent standards built on it. Its deepest property: every LTL formula compiles to an automaton, turning logic into graph search.

    Definition LTL syntax: $\varphi ::= p \mid \neg\varphi \mid \varphi \wedge \varphi \mid \bigcirc\varphi \mid \varphi\,\mathsf U\,\varphi$ (with $\lozenge\varphi \equiv \top\,\mathsf U\,\varphi$, $\square\varphi \equiv \neg\lozenge\neg\varphi$), interpreted over infinite traces. Automata connection: every LTL formula $\varphi$ has a Büchi automaton $A_\varphi$ (possibly $2^{O(|\varphi|)}$ states) accepting exactly the traces satisfying $\varphi$. Model checking $M \models \varphi$ = emptiness of the product $M \times A_{\neg\varphi}$: does the system have any trace the negation-automaton accepts? LTL model checking is PSPACE-complete in the formula, linear in the system.
    Worked example Compile $\square\lozenge p$ ("$p$ infinitely often") to a Büchi automaton: two states, $q_0$ (waiting for $p$) and $q_1$ (just saw $p$, accepting). Transitions: on $p$, go to $q_1$; on $\neg p$, go to $q_0$; acceptance: visit $q_1$ infinitely often. A trace where $p$ eventually stops forever gets stuck cycling in $q_0$ and is rejected ✓. To check a system satisfies $\square\lozenge p$, build $A_{\neg\varphi} = A_{\lozenge\square\neg p}$ and search the product for an accepting cycle — a lasso: a reachable cycle along which $\neg p$ always holds. Counterexamples to LTL properties are exactly lassos: a finite stem plus a finite loop repeated forever, which is why checkers can print them.
    Pitfall LTL's implicit "for all traces." $M \models \lozenge\,\mathit{done}$ means every trace finishes — often you meant "some strategy exists," which is a branching (CTL: $\mathsf{EF}$) or game-theoretic statement. Writing the right logic matters as much as the right formula; a correct proof of the wrong quantifier is a favorite failure.
    Drill
    1. EASY Express using only $\bigcirc, \mathsf U, \neg, \wedge, p, q$: "eventually $q$."
      Solution
      $\top\,\mathsf U\, q$, where $\top$ can be written $\neg(p \wedge \neg p)$. Until with a trivially-true left side is exactly "eventually."
    2. MED What is the negation of the response property $\square(r \Rightarrow \lozenge g)$, pushed inward to negation normal form, and what does a counterexample trace look like?
      Solution
      $\neg\square(r \Rightarrow \lozenge g) \equiv \lozenge\neg(r \Rightarrow \lozenge g) \equiv \lozenge(r \wedge \neg\lozenge g) \equiv \lozenge(r \wedge \square\neg g)$: eventually a request after which $g$ never holds. Counterexample lasso: a stem reaching a state where $r$ fires, then a loop containing no $g$ — the visual is "request, then the system spins forever ungranted."
    3. HARD Two formulas: $\square\lozenge p \Rightarrow \square\lozenge q$ ("fair $p$ implies fair $q$") vs $\square(\lozenge p \Rightarrow \lozenge q)$. Are they equivalent? Prove or give a separating trace.
      Solution
      Not equivalent. Note $\square(\lozenge p \Rightarrow \lozenge q)$: at every suffix, if $p$ occurs in that suffix then $q$ occurs in that suffix. Separating trace: $p$ at step 0 only, $q$ at step 0 only, nothing after (say both hold at 0, never again). Check formula 2 at suffix 0: $\lozenge p$ true, $\lozenge q$ true ✓; at suffixes ≥ 1: $\lozenge p$ false, vacuous ✓ — formula 2 holds. Formula 1: $\square\lozenge p$ is false (p not infinitely often), so the implication is vacuously true too. Try again: trace with $p$ at every even step, $q$ at step 0 only. Formula 1: $\square\lozenge p$ true, $\square\lozenge q$ false → formula 1 false. Formula 2: suffix from step 1: $\lozenge p$ true (step 2), $\lozenge q$ false → the implication fails at that suffix → formula 2 false. Third try — separate the other way: trace with $p$ at step 0 only, $q$ never. Formula 1: $\square\lozenge p$ false → vacuously true. Formula 2: at suffix 0, $\lozenge p$ true, $\lozenge q$ false → false. So formula 2 is strictly stronger: it also polices finitely-many-$p$ traces, where formula 1 says nothing. Moral: "infinitely often" premises silently excuse all finite behavior — a recurring source of vacuously-true fairness specs.

    SMT solving

    An SMT (Satisfiability Modulo Theories) solver answers: does this formula — over integers, reals, arrays, bitvectors, uninterpreted functions — have a satisfying assignment? It is the engine room of modern verification: VC discharge, symbolic execution, bounded model checking, and program synthesis all bottom out in SMT queries. Think "SAT solver with a mathematician bolted on."

    Definition SMT input: a first-order formula $\varphi$ over a combination of theories $T$ (e.g. linear integer arithmetic, arrays, bitvectors). Output: sat with a model (assignment), unsat (often with a proof/core), or unknown. Architecture (DPLL(T)/CDCL(T)): a SAT solver enumerates boolean skeletons; theory solvers check whether each skeleton's literals are jointly consistent in $T$, returning conflict clauses that prune the search. Verification uses the duality: to prove $\psi$ valid, ask for a model of $\neg\psi$; unsat = proved.
    Worked example Prove: for integers, $x > 2 \wedge y > 2 \Rightarrow x + y > x \cdot y$ is false — i.e., its negation is sat. Query: $x > 2 \wedge y > 2 \wedge x + y > xy$? Try $x = 3, y = 3$: $6 > 9$ false; the solver instead reports... let's do the real check: for $x, y \ge 3$, $xy \ge 3\max(x,y)\ge x + y$ ... precisely $xy - x - y = (x-1)(y-1) - 1 \ge 2\cdot2 - 1 = 3 > 0$, so $x + y > xy$ is impossible: the query is unsat, hence the original implication "$x>2 \wedge y>2 \Rightarrow x + y \le xy$" is valid (and our first reading — that it's false — is itself refuted: this is exactly the kind of sign-flip a solver saves you from). The solver's unsat answer is the proof of validity, obtained without any human algebra.
    Where this goes Tool-verified reasoning (Ch 30): an LLM translates a word problem into SMT and lets Z3 do the logic. Neural-network verification (end of this chapter) encodes ReLU networks as SMT/MILP constraints.

    1. EASY To prove "$\forall x.\ x^2 \ge 0$" over the reals with an SMT solver, what query do you issue, and what answer do you want?
      Solution
      Assert the negation: $\exists x.\ x^2 < 0$, i.e. assert $x \cdot x < 0$ and check. Desired answer: unsat — no counterexample exists, so the universal statement is valid.
    2. MED Is $x \equiv 1 \pmod 4 \wedge x \equiv 2 \pmod 6$ satisfiable over the integers? Answer as a theory solver would.

      Solution
      Theory: bitvectors (width 8). Encode SSA-style: $a_1 = a_0 \oplus b_0$; $b_1 = b_0 \oplus a_1$; $a_2 = a_1 \oplus b_1$. Prove validity of $a_2 = b_0 \wedge b_1 = a_0$ by asserting its negation and expecting unsat (it is: $b_1 = b_0 \oplus a_0 \oplus b_0 = a_0$; $a_2 = a_1 \oplus b_1 = (a_0 \oplus b_0) \oplus a_0 = b_0$). Aliasing: if a,b are the same cell, the program is really $c_1 = c_0 \oplus c_0 = 0$; then $c_2 = c_3 = 0$: the value is destroyed. Encode with the theory of arrays: memory $M$, addresses $p, q$; each statement is a read-modify-write on $M$; the correctness claim is proved only under the side condition $p \ne q$ — dropping it, the solver returns sat with the model $p = q$, exhibiting the aliasing bug. The encoding forces the hidden assumption into the open, which is the recurring gift of formalization.

    SAT solving

    Boolean satisfiability is the primal decision problem (Ch 17: the first NP-complete problem) — and, paradoxically, one of computing's great practical success stories: modern CDCL solvers routinely crack industrial instances with millions of variables. Verification's dirty secret is that half the field is clever reductions to SAT.

    Definition SAT: given a CNF formula (a conjunction of clauses, each a disjunction of literals), decide if some assignment satisfies all clauses. CDCL (conflict-driven clause learning): iteratively decide a variable, propagate forced values (unit propagation: a clause with all-but-one literal false forces the last), and on conflict, analyze the implication graph, learn a new clause that blocks that failure pattern everywhere, and backjump. Learned clauses are the memoization that lifts CDCL far beyond brute force on structured instances.
    Worked example Solve $(x \vee y) \wedge (\neg x \vee z) \wedge (\neg y \vee \neg z) \wedge (\neg x \vee \neg z \vee y)$... take the cleaner classic: $(x \vee y) \wedge (\neg x \vee y) \wedge (x \vee \neg y) \wedge (\neg x \vee \neg y)$. Decide $x = \top$: clause 2 unit-propagates $y = \top$; clause 4 becomes $(\bot \vee \bot)$ — conflict. Conflict analysis: the conflict depended on decision $x = \top$ (which forced $y$); learn clause $(\neg x)$. Backjump, propagate $x = \bot$: clause 1 forces $y = \top$; clause 3 becomes $(\bot \vee \bot)$ — conflict with no decisions left: unsat, proved after exploring 2 branches instead of 4 assignments. The learned clause turned a search tree into a resolution proof — every CDCL unsat run is implicitly a checkable proof.
    Think first Unit propagation alone (no decisions) runs in linear time. What class of encodings tries to ensure the solver can deduce everything by propagation, and why does it matter for verification tooling?
    Reveal
    "Propagation-complete" or arc-consistent encodings: constraints translated so unit propagation discovers every forced literal without search. It matters because reductions are engineering: two logically equivalent CNF encodings of the same circuit or CSP can differ by orders of magnitude in solve time depending on how much the propagator can see. Encoding quality — auxiliary variables, symmetry breaking, Tseitin transformation structure — is as important as the solver.
    Drill
    1. EASY Apply unit propagation: $(\neg a) \wedge (a \vee b) \wedge (\neg b \vee c)$.
      Solution
      Clause 1 forces $a = \bot$; clause 2 becomes unit, forces $b = \top$; clause 3 forces $c = \top$. Satisfying assignment found with zero search: $a{=}\bot, b{=}\top, c{=}\top$.
    2. MED Encode "exactly one of $x_1, x_2, x_3$ is true" in CNF.
      Solution
      At-least-one: $(x_1 \vee x_2 \vee x_3)$. At-most-one, pairwise: $(\neg x_1 \vee \neg x_2) \wedge (\neg x_1 \vee \neg x_3) \wedge (\neg x_2 \vee \neg x_3)$. Four clauses total. (For $n$ variables the pairwise encoding costs $\binom n2$ clauses; ladder/commander encodings get $O(n)$ with auxiliaries — the encoding-engineering point again.)
    3. HARD Reduce this 3-coloring instance to SAT and decide it: triangle $\{A, B, C\}$ plus vertex $D$ adjacent to $A$ and $B$.
      Solution
      Variables $v_c$ for each vertex $v$ and color $c \in \{1,2,3\}$. Clauses: each vertex gets ≥1 color ($v_1 \vee v_2 \vee v_3$, 4 clauses); ≤1 color (pairwise, $3\times4 = 12$ clauses); adjacent vertices differ: for each edge $(u,v)$ and color $c$: $(\neg u_c \vee \neg v_c)$ — edges AB, BC, CA, DA, DB: $5 \times 3 = 15$ clauses. Decision: the triangle forces all three colors, say $A{=}1, B{=}2, C{=}3$ (up to symmetry); $D$ adjacent to $A, B$ must avoid colors 1, 2 → $D = 3$. Satisfiable, e.g. $(A,B,C,D) = (1,2,3,3)$ — and $C, D$ nonadjacent so that's legal. A solver finds this instantly; had we added edge $CD$... $D$ would need to avoid 1,2,3: the three at-most/at-least clauses for $D$ plus edge clauses become jointly unsat, and CDCL would learn its way to a refutation.

    Constraint encoding

    Solvers don't speak your problem's language; encoding is the translation. The craft: choose variables that make constraints local, express constraints so propagation is strong, and keep the blowup polynomial. A good encoding is to a solver what a good representation is to a learner (Ch 21) — most of the battle.

    Definition An encoding of problem $P$ into solver language $L$ is a map $e$ with: (soundness/completeness) $P$ has a solution iff $e(P)$ is satisfiable, and a poly-time decoding of models back to solutions. Standard toolkit: one-hot encodings for finite domains, Tseitin transformation (introduce a fresh variable per subformula to get linear-size CNF from arbitrary circuits), sorting networks and totalizers for cardinality constraints ($\le k$ of these), and big-M / indicator constraints on the MILP side.
    Worked example Encode a 4-task/4-slot scheduling constraint "tasks 1 and 2 cannot run in adjacent slots" with one-hot variables $x_{t,s}$ (task $t$ in slot $s$). Adjacency pairs: $(1,2), (2,3), (3,4)$ — and both orders of the two tasks: clauses $(\neg x_{1,s} \vee \neg x_{2,s'})$ for every adjacent $\{s, s'\}$: $(\neg x_{1,1}\vee\neg x_{2,2})$, $(\neg x_{1,2}\vee\neg x_{2,1})$, $(\neg x_{1,2}\vee\neg x_{2,3})$, $(\neg x_{1,3}\vee\neg x_{2,2})$, $(\neg x_{1,3}\vee\neg x_{2,4})$, $(\neg x_{1,4}\vee\neg x_{2,3})$ — 6 clauses, plus the standard exactly-one-slot-per-task and at-most-one-task-per-slot frames. Every English constraint became a handful of two-literal clauses; the solver never needs to know what a "task" is.
    Pitfall Encoding validity into the wrong direction. To verify "property holds for all inputs," you must encode the search for a violation and hope for unsat. Encoding "there exists an input where the property holds" and celebrating sat is a cheerful, common, and completely wrong ritual. Always ask: what does a model of my formula physically mean?
    Drill
    1. EASY Tseitin-encode $y \leftrightarrow (a \wedge b)$ into clauses.
      Solution
      $(\neg y \vee a) \wedge (\neg y \vee b) \wedge (\neg a \vee \neg b \vee y)$. The first two say $y \Rightarrow a \wedge b$; the last says $a \wedge b \Rightarrow y$.
    2. MED You need "at most 2 of $x_1..x_5$ are true." How many clauses does the naive encoding take, and what is it?
      Solution
      Forbid every triple: for each of $\binom{5}{3} = 10$ triples $\{i,j,k\}$, clause $(\neg x_i \vee \neg x_j \vee \neg x_k)$ — 10 clauses. General $\le k$ of $n$: $\binom{n}{k+1}$ clauses, exponential in $k$; totalizer/sequential-counter encodings use $O(nk)$ clauses with auxiliary variables instead.
    3. HARD Encode the verification query "this 2-layer ReLU net $f(x) = W_2\,\mathrm{relu}(W_1 x + b_1) + b_2$ maps every $x \in [l, u]$ to $f(x) > 0$" for an SMT/MILP solver. Give the ReLU trick.
      Solution
      Variables: $x$ (with bounds $l \le x \le u$), pre-activations $z = W_1 x + b_1$ (linear equalities), post-activations $h$, output $y = W_2 h + b_2$. ReLU per unit $i$, MILP-style with binary $\delta_i$ and precomputed bounds $L_i \le z_i \le U_i$ (from interval arithmetic): $h_i \ge 0$, $h_i \ge z_i$, $h_i \le z_i - L_i(1 - \delta_i)$, $h_i \le U_i \delta_i$ — $\delta_i = 1$ ⟹ $h_i = z_i$ (active), $\delta_i = 0$ ⟹ $h_i = 0$ (inactive). Query: assert the negation $y \le 0$; unsat proves the property, sat yields a concrete adversarial $x$. The binaries make it NP-hard in the number of unstable ReLUs — exactly why bound tightening ($L_i, U_i$) and relaxations dominate the neural-verification literature (last section).

    Policy verification

    Agent systems run under policies: "may read repo X, may not email externally, must get approval above \$50." Policies are code — usually declarative rules — and like code they have bugs: shadowed rules, unintended allow-paths, conflicts. Policy verification applies this chapter's machinery to the rules themselves, before an agent finds the hole at runtime.

    Definition A policy is a function $\mathit{pol}: \text{Request} \to \{\text{allow}, \text{deny}\}$, typically composed from ordered or combined rules. Core verification queries, each an SMT/SAT problem over the request space: reachability ("is any request matching predicate $B$ allowed?" — assert $B \wedge \mathit{pol} = \text{allow}$, want unsat), equivalence ("did the refactor change behavior?" — assert $\mathit{pol}_1 \ne \mathit{pol}_2$, want unsat), shadowing ("does rule $r$ ever fire?" — sat check on "reaches $r$"), and separation ("no single principal is allowed both A and B").
    Worked example Rules, first-match order: (1) deny if destination is external email; (2) allow if sender role = "reporting-agent"; (3) allow if amount < 50; (4) deny otherwise. Query: can a reporting-agent cause an external email? Encode: $\mathit{ext} \wedge \mathit{pol} = \text{allow}$. Rule 1 matches all $\mathit{ext}$ requests first → deny → unsat: verified ✓. Now a teammate "harmlessly" reorders (2) before (1): the same query is now sat with model {role = reporting-agent, ext = true} — the reorder opened an exfiltration path that no test caught because no test happened to combine that role with an external destination. Equivalence checking across the diff would have flagged it mechanically: the two policies differ exactly on that slice of request space.
    Where this goes This is Ch 32's capability/RBAC machinery made analyzable, and the concrete substrate for Ch 35's "control" agenda: you can't reason about containing an agent whose permission surface you can't even compute.
    Drill
    1. EASY Why is "we tested 50 requests against the policy" weak assurance compared to a reachability query?
      Solution
      The request space is combinatorial (roles × actions × resources × amounts × contexts); 50 points sample a sliver. The reachability query quantifies over the whole space at once — it's the difference between testing and proof, applied to configuration.
    2. MED First-match rules: (1) allow read if path starts with /public; (2) deny read if path contains ..; (3) deny all. Find the bug with a witness request.
      Solution
      Witness: read /public/../secrets/key. Rule 1 matches (prefix /public) → allow, and rule 2 never fires because it's after rule 1: path traversal escapes the public directory. Fixes: put the .. deny first, or better, canonicalize paths before matching (verify the property on the canonical form — the policy should quantify over semantic objects, not strings).
    3. HARD Define and check "separation of duty": no single agent may both create a payment and approve it. The policy grants by role; agents can hold multiple roles; role "admin" implies all permissions. Formalize the query and identify the finding.
      Solution
      Variables: agent $a$, role set $R(a)$; permission function $\mathit{perm}(\rho)$ per role; agent's permissions $= \bigcup_{\rho \in R(a)} \mathit{perm}(\rho)$, with $\text{admin} \Rightarrow$ everything. Query: $\exists a:\ \text{create\_payment} \in \mathit{perms}(a) \wedge \text{approve\_payment} \in \mathit{perms}(a)$. Finding: sat, trivially, via $R(a) = \{\text{admin}\}$ — the admin role violates separation of duty by construction. Resolutions: exclude break-glass admin from the invariant but compensate with mandatory audit + two-person control on its use; or split admin into admin-ops and admin-finance and re-run the query to unsat. The formal exercise's real output is the forced decision about admin, which informal policy review perennially defers.

    Permission verification

    Policy verification asks whether the rules are right; permission verification asks whether the system enforces them — that every action an agent can actually take traces back to an explicit grant, through every delegation hop and tool layer. The gold standard is a small, auditable reference monitor: one chokepoint all actions pass through, so the proof obligation is local.

    Definition Let $\mathit{granted}(a, \mathit{act})$ be the policy's answer and $\mathit{can}(a, \mathit{act})$ be operational ability (there exists a sequence of system calls by which $a$ effects $\mathit{act}$). Complete mediation: $\mathit{can}(a, \mathit{act}) \Rightarrow \mathit{granted}(a, \mathit{act})$. Verifying it decomposes into: (1) every effectful pathway passes the reference monitor (an architectural/flow property), (2) the monitor correctly decides $\mathit{granted}$ (policy verification), (3) permissions attenuate under delegation: $\mathit{perms}(\text{delegate}) \subseteq \mathit{perms}(\text{delegator})$, inductively along the delegation tree (Ch 33).
    Worked example Attenuation check as an invariant proof. Grant chain: user grants agent $A$ {read repo, write repo, run tests}; $A$ delegates to executor $E$ with {write repo, run tests}; $E$ spawns sandbox helper $H$ with {run tests}. Invariant: each node's set ⊆ parent's set. $\{w, t\} \subseteq \{r, w, t\}$ ✓; $\{t\} \subseteq \{w, t\}$ ✓. Now $E$ requests to grant $H$ {read repo} for debugging: $\{r, t\} \not\subseteq \{w, t\}$ — the monitor rejects the grant even though the root user has read: authority must flow through the chain, not around it. If it didn't, any deep sub-agent could ratchet back up to root authority by asking nicely — the confused-deputy failure this invariant exists to kill.
    Pitfall Ambient authority: tools that act with the runtime's credentials rather than per-request, delegated credentials. Then $\mathit{can}$ silently exceeds $\mathit{granted}$ for every agent that can reach the tool, and no policy analysis will see it because the leak is in the plumbing. Verification must cover the mechanism, not just the rulebook.
    Drill
    1. EASY An agent cannot call the email tool, but can write files, and a cron job emails any file in /outbox. Does complete mediation hold?
      Solution
      No: $\mathit{can}(a, \text{send email})$ is true via the two-step path (write to /outbox → cron sends), while $\mathit{granted}$ is false. Effectful pathways include compositions through the environment; the monitor must sit at the actual effect boundary (outbound mail) or the outbox write must itself require email permission.
    2. MED Prove: if every delegation step satisfies $\mathit{perms}(\text{child}) \subseteq \mathit{perms}(\text{parent})$, then every descendant's permissions are a subset of the root grant.
      Solution
      Induction on delegation depth. Base: depth 0, the root, trivially $\subseteq$ itself. Step: a node at depth $k+1$ has $\mathit{perms} \subseteq \mathit{perms}(\text{parent at depth } k) \subseteq \mathit{perms}(\text{root})$ by the delegation condition and the inductive hypothesis; subset is transitive. Hence unbounded delegation depth adds convenience but never authority — the invariant that makes deep agent trees (Ch 33) auditable.
    3. HARD Time makes permissions leak: a grant is revoked while an agent's long task is mid-flight. Specify the desired property in temporal logic and describe two enforcement designs with their trade-offs.
      Solution
      Property: $\square(\mathit{exec}(a, \mathit{act}) \Rightarrow \mathit{granted}(a, \mathit{act}))$ — at the moment of each effect, the grant holds (not merely at task start). Designs: (1) Check-per-effect: the reference monitor re-evaluates the policy on every tool call; revocation takes effect at the next call. Trade-off: per-call latency and a thundering herd on the policy service; residual window = one in-flight call. (2) Leases/capability expiry: grants are short-lived tokens the agent must renew; revocation = refusing renewal. Trade-off: revocation latency up to the lease TTL, but zero policy-service coupling per call and graceful offline behavior. Both beat check-at-start, whose violation window is the whole task duration — the formal property makes the window a designed, stated quantity instead of an accident.

    Attenuation is checked edge-by-edge; permissions flow only through the chain. If the root really should grant it, the request must travel up to the root and come back down as a new explicit grant — otherwise any leaf could self-escalate.

    Runtime monitoring

    When you can't verify the system ahead of time — the agent is a neural network; the environment is open — verify the behavior as it happens. A runtime monitor watches the event trace and checks it against a formal property, flagging or halting on violation. It trades the universality of proof ("all runs are safe") for certainty about the one run that matters: this one.

    Definition Given a property $\varphi$ over traces, a monitor is a function from finite prefixes to verdicts $\{\top, \bot, ?\}$: $\bot$ when the prefix is a bad prefix (no extension satisfies $\varphi$), $\top$ when every extension satisfies it, else $?$. For LTL, monitors are built by compiling $\varphi$ (and $\neg\varphi$) to finite automata over finite words; the monitorable properties are those with reachable definite verdicts — safety (refutable), co-safety (confirmable), and their boolean combinations.
    Worked example Monitor for $\square(\mathit{write} \Rightarrow \blacklozenge\,\mathit{backup})$ ("no write before a backup has happened at least once"). Automaton state: has a backup occurred yet? Start: no. Events: read → state unchanged, verdict ?. backup → state yes; from now on writes are fine. write while state = no → verdict $\bot$, halt the action. Implementation is a two-state machine consulted before each effect: constant memory, microsecond decisions, and — crucially — it sits in the enforcement path, so the bad write is prevented, not just recorded. Monitoring for past-time LTL is always this cheap: one automaton state, updated per event.
    Think first Your monitor watches the agent's tool calls but the property refers to real-world effects ("never contact a customer twice in a week"). What gap must you close for verdicts to mean anything?
    Reveal
    The observation map: each abstract event in the property must correspond, soundly, to something the monitor can see. If contacting customers can happen through three tools (email, SMS, a CRM automation), all three must emit the "contact" event with a canonical customer id; a tool that doesn't is a monitoring blind spot, and the verdict "no violation" silently means "no violation through instrumented channels." Trace completeness is to monitoring what the model gap is to model checking.
    Drill
    1. EASY Which verdicts can a monitor ever issue for the pure liveness property $\lozenge p$, and for the safety property $\square \neg b$?
      Solution
      $\lozenge p$: can confirm $\top$ (the moment $p$ occurs) but never refute — no $\bot$ verdict from a finite prefix (it's co-safety: confirmable). $\square\neg b$: can refute $\bot$ (the moment $b$ occurs) but never confirm on a finite prefix of an ongoing run. Mirror images.
    2. MED Build the monitor automaton for "$\mathit{approve}$ must precede $\mathit{deploy}$, and $\mathit{deploy}$ happens at most once" and list its states.
      Solution
      States: $S_0$ (no approval, no deploy), $S_1$ (approved, no deploy), $S_2$ (deployed — terminal OK), $\bot$ (violation). Transitions: $S_0$: approve → $S_1$; deploy → $\bot$; other → $S_0$. $S_1$: deploy → $S_2$; approve → $S_1$; other → $S_1$. $S_2$: deploy → $\bot$; other → $S_2$. Four states, constant-time updates, and the two failure modes (unapproved deploy, double deploy) map to the two arrows into $\bot$.
    3. HARD Monitoring overhead: the monitor must decide before each effect (synchronous) or can lag (asynchronous). Analyze the trade-off for an LLM agent whose property is "no PII in any outbound message," where the PII check is itself an ML classifier with 50 ms latency and 2% FNR.
      Solution
      Synchronous: every outbound message pays +50 ms; violations are prevented (modulo the 2% FNR — misses go through; there is no free soundness with a statistical monitor). Asynchronous: zero added latency; the monitor detects ~50 ms later, after the message left — detection becomes damage control (recall the message if the channel allows, alert, quarantine the agent). Decision rule: synchronous for irreversible, high-severity channels (external email, payments); asynchronous plus a fast cheap pre-filter (regex for obvious PII, ~0 ms) for low-risk internal channels. And because the classifier is unsound, the formal layer should carry the sound part: hard rules (structured fields never leave; only allow-listed recipients) enforced synchronously by exact automata, with the ML monitor as a second, statistical net — layering exact safety and learned detection is the standard architecture (and Ch 35's control agenda in miniature).

    Safety shields

    A monitor that can also overrule is a shield: it sits between the agent's chosen action and the world, and blocks or replaces any action that would leave the verified-safe region. The agent — an RL policy, an LLM — stays a black box and stays free to optimize; the shield guarantees that whatever it tries, the executed behavior satisfies the safety spec. Freedom inside a proven fence.

    Definition Given a transition model and safety property $\square\neg\mathit{Bad}$, compute the maximal safe (winning) region $W$: the largest set of states from which safety can be maintained forever against worst-case environment moves, with the allowed-action map $\mathit{safe}(s) = \{a : \forall\text{ env responses}, \ \delta(s, a) \in W\}$ — computed as a greatest fixed point (backward induction shrinking $W$ until stable). The shield executes $a_t$ if $a_t \in \mathit{safe}(s_t)$, else a fallback from $\mathit{safe}(s_t)$. Guarantee: if $s_0 \in W$, the composed system satisfies $\square\neg\mathit{Bad}$ — for any agent whatsoever.
    Worked example Gridworld corridor with cells $1..6$; cell 6 is a cliff ($\mathit{Bad}$); actions L/R; ice on cell 4: from 4, action R may slide 1 or 2 cells (adversarial). Compute $W$: cell 6 bad. Cell 5: action R → 6 unsafe; action L → 4 safe: $\mathit{safe}(5) = \{L\}$, 5 ∈ W. Cell 4: R may land on 5 or 6 — 6 ∈ Bad, so R ∉ safe(4); L → 3 ✓: $\mathit{safe}(4) = \{L\}$. Cells 1–3: both actions stay in $\{1..4\}$... check 3: R → 4 ∈ W ✓, so $\mathit{safe}(3) = \{L, R\}$. Result: $W = \{1,\dots,5\}$, and the shield's only interventions ever are: replace R at 4 and at 5. An RL agent trained inside this shield explores everything else freely and can never take the sliding step off the cliff — even at random initialization, even under adversarial ice.
    Pitfall The shield's guarantee is conditional on its model of the dynamics (which transitions are possible). If real ice slides 3 cells, $W$ was computed against the wrong game and the fence has a gap. Shields for LLM agents face this squarely: "what can this tool call cause?" needs a sound over-approximation of effects — take the coarse, conservative model and accept more false blocks.
    Where this goes Shields are the deployment-grade version of Ch 32's precondition checks, and one concrete mechanism in Ch 35's control stack: the model proposes, a verified layer disposes.
    Drill
    1. EASY Why is a shield's fallback action required to come from $\mathit{safe}(s)$ rather than being "do nothing"?
      Solution
      "Do nothing" is an action too, and not always safe (a drone doing nothing falls; a car doing nothing keeps rolling). The fallback must be verified like any action; if $\mathit{safe}(s)$ were empty, $s$ wouldn't be in $W$ in the first place — that's exactly what the fixed-point computation guarantees.
    2. MED Recompute the corridor example when the ice is on cell 3 instead (R from 3 slides 1 or 2). What is $W$ and where does the shield intervene?
      Solution
      Cell 5: R → 6 bad, so $\mathit{safe}(5) = \{L\}$. Cell 4: R → 5 ∈ W ✓ (5 is safe via L), L → 3 ✓: both allowed. Cell 3: R slides to 4 or 5 — both in W ✓, so R allowed; L → 2 ✓. So $W = \{1..5\}$ with interventions only at 5 (block R). The ice stopped mattering because both slide outcomes are recoverable — safety regions care about recoverability, not about noise per se.
    3. HARD Design a shield for an LLM coding agent whose $\mathit{Bad}$ = "repository main branch fails CI." Define states, the safe region, the action filter, and what plays the role of the adversarial environment.
      Solution
      States: (branch, CI status, pending diff). Effect model: actions = tool calls; the ones that can reach $\mathit{Bad}$ are exactly pushes/merges to main (a sound over-approximation: nothing else touches main). Adversary: flaky tests, concurrent human pushes, nondeterministic builds — anything between "CI passed on the candidate" and "CI passes on main after merge." Safe region: states where main's HEAD has a green CI run for the exact merge result. Action filter: allow all edits/commits/branch pushes freely (they can't reach Bad); intercept merge-to-main and require (1) CI green on the true merge commit (merge queue semantics — recheck after any main movement, closing the adversary's race window), (2) else substitute the fallback: keep the change on a branch and open a request for review. Note the shield never evaluates code quality — that stays the agent's and reviewers' job; it enforces only the invariant that is cheap to state and catastrophic to lose. Good shields are narrow and absolute.

    Verifying neural networks

    Can formal methods reach the network itself? For properties like "no small input perturbation flips this classification" — robustness balls around inputs — the answer is a qualified yes: a trained network is just a fixed piecewise-linear function, and questions about it are constraint problems. The obstacle is scale: exactness costs exponential time in the ReLUs, so the field lives on relaxations that trade completeness for speed.

    Definition Local robustness: for network $f$, input $x_0$ with label $c$, radius $\epsilon$: $\forall x.\ \lVert x - x_0\rVert_\infty \le \epsilon \Rightarrow \arg\max_j f_j(x) = c$. Complete methods (SMT/MILP à la Reluplex/branch-and-bound) decide it exactly (NP-complete in general). Incomplete methods propagate over-approximations layer by layer — interval bound propagation (IBP): given $z \in [l, u]$ elementwise, an affine layer $Wz + b$ has output bounds $l' = W^+ l + W^- u + b$, $u' = W^+ u + W^- l + b$ (with $W^{\pm}$ the positive/negative parts), and ReLU maps $[l, u] \mapsto [\max(l,0), \max(u,0)]$. If the certified bounds already separate class $c$ from all others, robustness is proved; if not, unknown.
    Worked example Tiny net: $h = \mathrm{relu}(W_1 x)$, $y = W_2 h$, with $W_1 = \begin{pmatrix}1 & -1\\ 2 & 1\end{pmatrix}$, $W_2 = (1\ \ {-1})$, input box $x_1 \in [0, 1], x_2 \in [0, 1]$. Pre-activation bounds: $z_1 = x_1 - x_2 \in [0-1,\ 1-0] = [-1, 1]$; $z_2 = 2x_1 + x_2 \in [0, 3]$. ReLU: $h_1 \in [0, 1]$, $h_2 \in [0, 3]$. Output $y = h_1 - h_2 \in [0 - 3,\ 1 - 0] = [-3, 1]$. Property "$y < 2$ always": certified ✓ (upper bound 1 < 2). Property "$y < 0.5$": bounds say $[-3, 1]$ — unknown; the true maximum is $\max(x_1 - x_2 \text{ clipped}) - \min(\dots)$… exact analysis: $y = \mathrm{relu}(x_1 - x_2) - \mathrm{relu}(2x_1 + x_2)$; at $(1, 0)$: $1 - 2 = -1$; the true max over the box is at… try $(x_1, x_2)$ with $x_1 - x_2$ big and $2x_1 + x_2$ small — conflicting; check corners: $(0,0) \to 0$, $(1,0) \to -1$, $(0,1) \to 0 - 1 = -1$, $(1,1) \to 0 - 3 = -3$; interior can't beat 0 (both terms continuous, $y \le \mathrm{relu}(x_1 - x_2) \le x_1 \le 2x_1 + x_2$ when $x_2 \le x_1$... at any point $y \le 0$): true max is 0, so "$y < 0.5$" actually holds — IBP just couldn't see it. That gap between the certified bound (1) and the truth (0) is the relaxation looseness that branch-and-bound (splitting the unstable ReLU $z_1 \gtrless 0$) closes: on each half, $h_1$ is exactly linear and the bounds collapse to the truth.

    1. EASY Through one ReLU layer, propagate the interval $z \in [-2, 3]$. And $z \in [1, 4]$? And $[-3, -1]$?
      Solution
      $[\max(-2,0), \max(3,0)] = [0, 3]$; $[1, 4]$ (stable active — exact); $[0, 0]$ (stable inactive — exact). Only the straddling case introduces looseness; the count of straddling ("unstable") ReLUs is the difficulty knob.
    2. MED Affine layer $y = 2x_1 - 3x_2 + 1$ with $x_1 \in [0, 1], x_2 \in [0, 2]$. Compute the exact output interval via the $W^\pm$ rule.
      Solution
      Lower: positive coeff (2) takes $x_1$'s min 0; negative coeff (−3) takes $x_2$'s max 2: $0 - 6 + 1 = -5$. Upper: $2(1) - 3(0) + 1 = 3$. $y \in [-5, 3]$ — exact for a single affine map (the looseness only appears when composing through layers, because dependencies between units are forgotten).
    3. HARD Why do interval bounds blow up with depth even for well-behaved networks, and name two ideas that fight it.
      Solution
      Two compounding causes. (1) Dependency loss: intervals treat each unit's range as independent, so correlations that would cancel (e.g. $h_1 - h_1$) are bounded as if adversarially misaligned — worst-case width multiplies by roughly the layer's operator-norm-like factor per layer, giving exponential growth in depth (the wrapping effect). (2) Unstable ReLUs each add a relaxation gap that later layers amplify. Fixes: linear relaxation methods (CROWN, DeepPoly) carry symbolic linear bounds in terms of the input variables, preserving first-order correlations; zonotopes/polyhedra keep richer dependency structure; branch-and-bound splits unstable neurons to restore exactness locally; and certified training (train with IBP bounds in the loss) reshapes the network so its bounds are tight in the first place — changing the artifact to fit the verifier, the deepest trick in the book.

    Problem 1 (MED) — Verified budget guard An agent loop spends from budget $b_0 = 100$; each iteration chooses a tool call costing $c \in \{5, 20\}$ nondeterministically, then, if $b < 20$, must call escalate and stop. Requirements: (a) safety $\square(b \ge 0)$, (b) the loop always terminates. Model as a transition system, give the inductive invariant for (a), the ranking function for (b), and identify the off-by-one bug if the guard is instead written "if $b \le 20$... stop" vs "if $b < 20$" when a cost-20 call is chosen at $b = 20$.
    Solution
    States: $b \in \mathbb Z$ plus a mode {run, stopped}. Transitions (mode run): if $b \ge 20$: $b := b - c$ for $c \in \{5, 20\}$; if $b < 20$: → stopped. Invariant for (a): $I: b \ge 0 \wedge (\text{mode = run} \Rightarrow \text{last check passed})$ — cleanly: prove $b \ge 0$ inductive given the guard "spend only when $b \ge 20$": base $100 \ge 0$ ✓; step: spending requires $b \ge 20$, so $b' = b - c \ge 20 - 20 = 0$ ✓; stopping doesn't change $b$ ✓. So $\square(b \ge 0)$ holds. (b) Ranking: $V = b$ in mode run (a natural number after the invariant), each spend strictly decreases it by ≥ 5; since $V$ can't decrease below 0 forever, the guard $b < 20$ eventually trips (once $b \le 15$... precisely once $b < 20$) and the system stops within $\lceil 100/5 \rceil = 20$ iterations. Guard variant analysis: with guard "spend when $b \ge 20$" (i.e. stop when $b < 20$), at $b = 20$ a cost-20 call yields $b = 0$ ✓ safe. If instead the code spends when $b > 20$ fails only at exactly 20 — still safe but stops earlier (conservative). The dangerous variant is spending when $b \ge 5$ (checking against the cheapest cost): at $b = 10$, a cost-20 call gives $b = -10$, violating safety — the guard must be checked against the maximum next-step cost, the worst-case adversarial choice, which is exactly what the inductive step forces you to notice.
    Problem 2 (HARD) — Model-check a two-agent handoff Agents P (producer) and C (consumer) share a one-slot buffer with a flag. P: when flag = 0, may write item and set flag := 1. C: when flag = 1, may read and set flag := 0. A buggy variant lets P also rewrite when flag = 1 ("overwrite mode"). States: (flag, items-written $w$, items-read $r$), abstracted to $d = w - r \in \{0, 1, 2^+\}$ and flag. (a) Build both transition systems. (b) Property: $\square(d \le 1)$ — no lost items. Check both. (c) For the buggy one, give the counterexample trace and the shortest fix. (d) State the property "every written item is eventually read" and say what assumption it needs.
    Solution
    (a) Correct system states: (flag 0, $d$ 0) initial; transitions: P-write: (0, 0) → (1, 1); C-read: (1, 1) → (0, 0). Reachable: {(0,0), (1,1)} only. Buggy adds P-overwrite: (1, 1) → (1, 2⁺) — writing while flag = 1 (the previous item is clobbered: $w$ increments with no read). (b) Correct: reachable set never has $d \ge 2$: $\square(d \le 1)$ ✓ by exhaustion of the two states. Buggy: (0,0) →P (1,1) →P (1, 2⁺): violated. (c) Counterexample trace: write, write — length 2; the second write destroys an unread item. Shortest fix: remove the overwrite transition, i.e. guard P's write with flag = 0 (the original protocol); at the code level, one guard condition. (d) Liveness: $\square(\mathit{written} \Rightarrow \lozenge\,\mathit{read})$, equivalently in this abstraction $\square(d = 1 \Rightarrow \lozenge\, d = 0)$. It fails without a fairness assumption: the trace (0,0) →P (1,1) followed by C never scheduled (infinite stutter) is a legal run of the unconstrained system. Needs weak fairness for C: if C's read is continuously enabled (flag stays 1), C eventually fires. With that, from (1,1) the only fair continuations fire C: property holds. The capstone moral: safety came from a guard; liveness came from the scheduler's promise — different obligations, different owners.
    Problem 3 (HARD) — End-to-end: shielded, monitored, certified An LLM agent drives a thermostat for a server room: it reads temperature $T$ and sets heater power $u \in \{0, 1, 2\}$. Dynamics (worst case): $T' = T + u - L$ where load cooling $L \in \{0, 1, 2, 3\}$ is adversarial each step. $\mathit{Bad}$: $T \le 15$ or $T \ge 30$ (integers throughout). (a) Compute the maximal safe region $W \subseteq \{16, \dots, 29\}$ and the allowed-action map. (b) The agent also emits a "status report" scored by an ML anomaly detector with FNR 10%; reports gate nothing. A colleague proposes replacing the shield with the detector. Give the formal argument against. (c) The heater's spec sheet guarantees $u = 2$ delivers heat in $[1.6, 2.4]$ (analog reality); redo the safety analysis for the boundary state and say what changes.
    Solution
    (a) From state $T$, action $u$ leads to $T + u - L$ for adversarial $L \in \{0..3\}$: the reachable set is $[T + u - 3,\ T + u]$. Action $u$ is safe at $T$ iff the whole set stays in $[16, 29]$: need $T + u - 3 \ge 16$ and $T + u \le 29$, i.e. $u \ge 19 - T$ and $u \le 29 - T$. Then check $W$-membership: candidate $W = \{19, \dots, 27\}$? Compute: at $T = 19$: need $u \ge 0$ and $u \le 10$ → all $u$, but reach must land in $W$, not just outside Bad — recompute the greatest fixed point with target $W$ itself. Try $W = \{19..27\}$: safe action at $T$ requires $T + u - 3 \ge 19$ and $T + u \le 27$: $u \ge 22 - T$, $u \le 27 - T$. At $T = 19$: $u \ge 3$ — impossible ($u \le 2$): 19 ∉ W. Iterate: try $W = \{20..27\}$: need $u \ge 23 - T$, $u \le 27 - T$. $T = 20$: $u \ge 3$ impossible. Keep shrinking: $W = \{k..27\}$ needs at $T = k$: $u \ge k + 3 - ... $ general: staying ≥ the floor $f$ needs $u \ge f + 3 - T$; at $T = f$: $u \ge 3$ — never satisfiable. Conclusion: no nonempty safe region exists — with max heat 2 and max cooling 3, the adversary wins from everywhere by always playing $L = 3$: $T$ drifts down by ≥ 1 per step no matter what. The verification's real finding is a capability gap: the plant is uncontrollable against worst-case load (Ch 28: the disturbance exceeds control authority). Fix the physics or the assumption: if $L \in \{0, 1, 2\}$, safe actions need $u \ge L_{max} + (f - T)$... at floor $f$: $u = 2 \ge 2$ ✓ (play $u = 2$, worst case $T' = T$), and ceiling: at $T = 27$, $u \le 29 - 27 = 2$ ✓; but staying in $W = \{f..27\}$: at $T = 27$, need $T + u \le 27$ → $u = 0$, worst case $T' = 24 \ge f$ ✓ for $f \le 24$. Greatest fixed point with $L \le 2$: $W = \{19, \dots, 27\}$ checks out: at $T = 19$: $u = 2$ → $T' \in [19, 21] \subseteq W$ ✓; at $T = 27$: $u = 0$ → $T' \in [25, 27]$ ✓; interior states have wider choice. Allowed map: $\mathit{safe}(T) = \{u : 19 \le T + u - 2 \text{ and } T + u \le 27\} = \{u : u \ge 21 - T,\ u \le 27 - T\}$. (b) The detector is statistical (10% FNR) and non-blocking: formally it changes no transition, so the system's trace set — including the Bad-reaching traces — is unchanged; $\square\neg\mathit{Bad}$ remains violated with certainty under the adversary, merely observed 90% of the time. A shield changes the transition relation itself (removes unsafe arrows), giving a guarantee quantified over all behaviors. Detection ≠ enforcement; probabilistic observation ≠ worst-case exclusion. (c) With analog heat $u{=}2 \mapsto [1.6, 2.4]$ and integer analysis abandoned: at the floor state $T = 19$ (with $L \le 2$), worst case is minimum heat 1.6 and max cooling 2: $T' = 19 - 0.4 = 18.6 < 19$ — the old floor is no longer maintainable; the safe region's floor must rise to where the deficit can be absorbed, and the analysis moves to real-valued intervals: maintainability needs $\min u_{\text{eff}} \ge \max L$, i.e. $1.6 \ge 2$ — false, so pure "hold forever at the floor" fails; instead the region shrinks until the slack above the floor absorbs the worst-case per-step deficit only transiently — with unbounded adversarial duration, again no infinite-horizon safe floor exists unless duty-cycling assumptions bound $L$'s average. Spec-sheet tolerances are model changes, and model changes reopen the proof: exactly the discipline this chapter exists to instill.

    Task 1 — A tiny model checker. Implement BFS reachability checking for finite transition systems given as Python dicts, returning either "SAFE" or a counterexample path to a bad state. Use it to check the producer–consumer example (correct and buggy variants) from the capstone.

    Reference solution
    from collections import deque

def model_check(initial, transitions, is_bad):
    """transitions: state -> iterable of successor states."""
    parent = {s: None for s in initial}
    q = deque(initial)
    while q:
        s = q.popleft()
        if is_bad(s):
            path = []
            while s is not None:
                path.append(s); s = parent[s]
            return "UNSAFE", path[::-1]
        for t in transitions(s):
            if t not in parent:
                parent[t] = s
                q.append(t)
    return "SAFE", None

# producer-consumer: state = (flag, d) with d = items written minus read (cap at 2)
def trans_correct(s):
    flag, d = s
    out = []
    if flag == 0: out.append((1, min(d + 1, 2)))   # P writes
    if flag == 1: out.append((0, max(d - 1, 0)))   # C reads
    return out

def trans_buggy(s):
    flag, d = s
    out = trans_correct(s)
    if flag == 1: out.append((1, min(d + 1, 2)))   # P overwrites!
    return out

bad = lambda s: s[1] >= 2
print(model_check([(0, 0)], trans_correct, bad))  # ('SAFE', None)
print(model_check([(0, 0)], trans_buggy, bad))    # ('UNSAFE', [(0,0),(1,1),(1,2)])

    Task 2 — DPLL SAT solver with unit propagation. Write a small DPLL solver (unit propagation + splitting) over CNF as lists of integer literals. Verify it on: the 4-clause unsat example from the SAT section, and the 3-coloring encoding of the triangle-plus-pendant graph from the drills (should be sat).

    Reference solution
    def unit_propagate(clauses, assign):
    changed = True
    while changed:
        changed = False
        for cl in clauses:
            unassigned, satisfied = [], False
            for lit in cl:
                v = assign.get(abs(lit))
                if v is None: unassigned.append(lit)
                elif (lit > 0) == v: satisfied = True; break
            if satisfied: continue
            if not unassigned: return None          # conflict
            if len(unassigned) == 1:
                lit = unassigned[0]
                assign[abs(lit)] = lit > 0
                changed = True
    return assign

def dpll(clauses, assign=None):
    assign = dict(assign or {})
    if unit_propagate(clauses, assign) is None: return None
    vars_all = {abs(l) for cl in clauses for l in cl}
    free = vars_all - assign.keys()
    if not free: return assign
    v = min(free)
    for val in (True, False):
        r = dpll(clauses, {**assign, v: val})
        if r is not None: return r
    return None

# unsat example: (x|y)(~x|y)(x|~y)(~x|~y) with x=1, y=2
print(dpll([[1,2],[-1,2],[1,-2],[-1,-2]]))   # None (unsat)

# 3-coloring: var(v,c) for v in A,B,C,D (0..3), c in 1..3 -> id 3*v+c
V = lambda v, c: 3 * v + c
verts, colors = range(4), (1, 2, 3)
edges = [(0,1),(1,2),(2,0),(3,0),(3,1)]      # triangle ABC + D-A, D-B
cnf  = [[V(v,c) for c in colors] for v in verts]                       # >=1 color
cnf += [[-V(v,a), -V(v,b)] for v in verts for a in colors for b in colors if a < b]
cnf += [[-V(u,c), -V(w,c)] for (u,w) in edges for c in colors]
model = dpll(cnf)
sol = {v: c for v in verts for c in colors if model.get(V(v,c))}
print(sol)   # e.g. {0:1, 1:2, 2:3, 3:3} — check: no edge shares a color

    Task 3 — Interval bound propagation, certified vs true. Implement IBP for an MLP (NumPy), certify an output threshold over an input box, and compare against the empirical range from a million random samples for the 2-2-1 network of the neural-verification section. Observe that IBP's bound contains, and generally exceeds, the sampled range.

    Reference solution
    import numpy as np

def ibp_affine(l, u, W, b):
    Wp, Wn = np.maximum(W, 0), np.minimum(W, 0)
    return Wp @ l + Wn @ u + b, Wp @ u + Wn @ l + b

def ibp_forward(l, u, layers):
    for i, (W, b) in enumerate(layers):
        l, u = ibp_affine(l, u, W, b)
        if i < len(layers) - 1:            # ReLU on hidden layers
            l, u = np.maximum(l, 0), np.maximum(u, 0)
    return l, u

W1 = np.array([[1., -1.], [2., 1.]]); b1 = np.zeros(2)
W2 = np.array([[1., -1.]]);           b2 = np.zeros(1)
layers = [(W1, b1), (W2, b2)]

l0, u0 = np.array([0., 0.]), np.array([1., 1.])
lo, hi = ibp_forward(l0, u0, layers)
print("IBP bounds:", lo, hi)               # [-3.] [1.]

def f(x):
    h = np.maximum(x @ W1.T + b1, 0)
    return h @ W2.T + b2

xs = np.random.default_rng(0).uniform(l0, u0, size=(1_000_000, 2))
ys = f(xs)
print("empirical range:", ys.min(), ys.max())   # ~[-3, 0]: true max is 0
thr = 0.5
print("certified y < 0.5:", hi[0] < thr)        # False: IBP too loose here
print("empirically y < 0.5:", ys.max() < thr)   # True: property holds, uncertified
