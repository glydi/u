    Agent loop

    Strip any agent to its skeleton and you find one loop: observe, decide, act, repeat. An LLM agent is a language model run inside this loop — its "observation" is the context window, its "action" is a message or tool call, and the loop's job is to feed each action's consequences back in. Everything else in this chapter — memory, planners, critics — is machinery bolted onto this cycle.

    Definition An agent loop is the iteration $$o_t = \mathrm{env}(a_{t-1}), \quad x_t = \mathrm{assemble}(o_t, m_t), \quad a_t = \pi_\theta(x_t), \quad m_{t+1} = \mathrm{update}(m_t, o_t, a_t),$$ where $\pi_\theta$ is the policy (the LLM), $x_t$ the assembled context, and $m_t$ the persistent state outside the model. Termination: a stop action, a success check, or a budget (Chapter 32). The loop converts a stateless next-token predictor into a stateful process: all statefulness lives in $m_t$ and the transcript, none in the weights.
    Worked example A file-fixing agent, one full cycle. $o_3$ = "pytest: 2 failed — test_parse line 41: expected 7, got 8". Assemble: system prompt + task + last few steps + this output = $x_3$. Policy emits $a_3$ = tool call read_file("parser.py", lines=30..50). Environment returns the code; the loop appends both to the transcript and iterates. After $a_5$ = an edit and $a_6$ = re-running pytest returns "2 passed", the success check fires and the loop halts. Six iterations, each identical in shape: the intelligence is in $\pi_\theta$, the agency is in the loop.
    Pitfall Per-step reliability compounds exactly as in Chapter 30: a loop whose steps each succeed with $p = 0.98$ completes a 50-step task with probability $0.98^{50} \approx 0.364$ if no step is recoverable. Loops need recovery (retries, replanning, verification) far more than they need smarter single steps.
    Where this goes Tool safety for the act edge is Chapter 32; multiple loops talking to each other is Chapter 33.
    Drill
    1. EASY With per-step success 0.95 and no recovery, what is the completion probability of a 20-step task? With one free retry per step (independent, same 0.95)?
      Solution
      No recovery: $0.95^{20} = e^{20\ln0.95} \approx 0.358$. With retry, per-step success $= 1 - 0.05^2 = 0.9975$; $0.9975^{20} \approx 0.951$. One retry nearly triples end-to-end reliability.
    2. MED Why must all persistent state live outside the model, and name two consequences for architecture design.
      Solution
      The LLM's weights are frozen and its activations are discarded after each call — it is a pure function of its context. Consequences: (1) anything the agent must remember has to be re-presented in context or stored in external memory $m_t$, so memory systems (this chapter) are not optional extras but the only mechanism of persistence; (2) the agent's behavior is reproducible and auditable from the transcript plus $m_t$ alone — and equally, corrupting the context (prompt injection, Chapter 32) corrupts the agent's entire "mind" for that step.
    3. HARD Compare the agent loop to the MDP formalism of Chapter 25: map each element, and identify what makes the LLM-agent case not a clean MDP.
      Solution
      Mapping: environment state ↔ MDP state $s_t$ (files, world); observation $o_t$ ↔ partial observation (POMDP, Chapter 26 — the agent never sees the full state); action $a_t$ ↔ action; success check ↔ reward. Deviations: (1) the effective "state" for the policy is the assembled context $x_t$, a designed function of history — so the agent is a POMDP policy with a hand-built (not learned) belief state, and context-assembly choices change the achievable optimum; (2) the action space is unbounded structured text, not a fixed set; (3) rewards are typically absent or terminal-only during operation — the loop usually runs a fixed policy rather than learning, so RL formalism describes it but training happens offline; (4) the horizon is not fixed and termination is itself an action, making it an optimal-stopping problem (Chapter 30's metareasoning) layered on the MDP.

    Agent state

    The agent's state is everything that persists between loop iterations: the transcript so far, scratch notes, memory stores, open task lists, budget counters. Designing an agent is largely deciding what goes into this state, where it lives, and how it is summarized back into the model's limited context.

    Definition Agent state $m_t$ is the tuple of persistent stores outside the model, typically: transcript (the append-only event log of observations and actions), working set (current goal, plan, open subtasks), memory stores (episodic/semantic/procedural, below), and control state (budgets spent, retries, permissions). The context $x_t$ shown to the model is a projection of $m_t$: $x_t = \mathrm{assemble}(m_t)$ under a token budget $B$, choosing what the model gets to "perceive" this step.
    Worked example A budget-checked projection. State: transcript 41,000 tokens; task spec 800; plan 300; last 3 tool outputs 2,600; retrieved memory 1,200; control counters 100. Budget $B = 8{,}000$ tokens for input. Assembly policy: always include spec + plan + control (1,200), last 3 outputs (2,600), retrieved memory (1,200) = 5,000; fill the remaining 3,000 with the transcript's most recent turns; older turns appear only as a 400-token running summary. The model never sees 85% of the raw state — the projection is the perceptual system.
    Think first Two agents have identical models and tools; one keeps its plan in the context every step, the other only in an external file it may read. Predict a behavioral difference.
    Reveal
    The plan-in-context agent conditions every action on the plan — coherent over long stretches, but it pays the tokens each step and stale plans keep steering it. The plan-in-file agent acts on local context, drifting off-plan whenever it doesn't think to re-read the plan (out of sight, out of mind: an LLM cannot be influenced by state not in its context). Standard resolution: pin a compact plan summary in context, keep the full plan external — perception decides behavior.
    Drill
    1. EASY Which belongs in the projection every step: (a) full transcript, (b) current subtask and constraints, (c) all of episodic memory?
      Solution
      (b). The full transcript and full memory exceed any budget and mostly aren't relevant; they are stores to retrieve from. Goal and constraints must be perceived every step or the agent forgets what it is doing and what it must not do.
    2. MED Why is an append-only event log the preferred substrate for agent state, rather than a mutable "current state" object?
      Solution
      (1) Auditability/provenance: every belief and action can be traced to the events that produced it (crucial for debugging and for Chapter 32's security). (2) Recoverability: crashes and retries replay from the log; a mutable object corrupted mid-step loses history. (3) Derived views stay cheap: summaries, memories and projections are all functions of the log and can be recomputed or improved later. Mutation destroys information; agents fail in ways you can only diagnose with the information mutation destroys.
    3. HARD Formally, context assembly is lossy compression of $m_t$ under budget $B$. Using Chapter 16's language, what should the projection maximize, and why is "most recent tokens" a poor approximation of it?
      Solution
      Choose $x_t$ to maximize the information relevant to the next decision: $\max_{x: |x|\le B} I(x; a_t^\ast)$ — mutual information with the optimal action (an information-bottleneck objective: compress $m_t$, preserve decision-relevant bits). Recency is a proxy that assumes relevance decays with time, which fails whenever (a) an early constraint ("never touch prod") matters forever — its relevance is constant; (b) an old observation becomes relevant again (the error seen 200 steps ago recurs); (c) recent tokens are bulky-but-redundant (a 3,000-token stack trace whose relevant content is one line). Better proxies combine recency with retrieval-by-similarity to the current subtask, pinned constraints, and summaries — i.e. the memory systems of the next sections, which exist precisely because recency ≠ relevance.

    Working memory

    Working memory is the small, fast store for what the agent is doing right now: the current subgoal, the variables in flight, the last few observations. In LLM agents it is the context window itself — expensive, tiny relative to the task, and wiped between sessions — which makes managing it the agent's scarcest-resource problem.

    Definition Working memory is the actively maintained, capacity-limited state used for the current computation: in the agent loop, the assembled context $x_t$ (capacity = the usable context window; per-step cost scales with attention over it). Cognitive-science anchor: human working memory holds roughly $7\pm2$ chunks (Miller) — with chunking (recoding many items into one familiar unit) as the capacity multiplier. The LLM analogue of chunking is summarization and naming: "steps 1–14: migrated schema, all tests green" is one chunk standing for thousands of tokens.
    Worked example Cost of a bloated working memory. Context 40k tokens vs a curated 8k, at (say) \$3 per million input tokens, 60-step task: bloated $\approx 60\times 40{,}000 = 2.4$M tokens → \$7.20; curated $\approx 0.48$M → \$1.44 — a 5× cost gap. Worse than cost: attention dilution — the needle-in-a-haystack literature shows retrieval accuracy from mid-context degrades as contexts grow ("lost in the middle"), so the bloated agent is also less reliable at using the one line that matters. Bigger working memory is not monotonically better.
    Pitfall Tool outputs are the great context-flooders: one verbose API response or full-file dump can be 20k tokens of which 50 matter. Truncate, extract, or summarize at the boundary (before appending to context), not after the window is already full.
    Drill
    1. EASY An agent's context holds: task (500), plan (300), last 4 tool outputs (4×2,000), history summary (700). Total? If the window budget is 8,000, what gives?
      Solution
      $500+300+8{,}000+700 = 9{,}500 > 8{,}000$. Compress tool outputs — e.g. keep the latest in full (2,000) and the previous three as 200-token extracts: $500+300+2{,}000+600+700 = 4{,}100$ ✓ with room to grow.
    2. MED Explain "chunking" as compression, and why a plan with named phases raises effective working-memory capacity.
      Solution
      Chunking replaces a set of items with one symbol whose meaning is stored elsewhere (in the model's weights or an external note) — it is source coding (Chapter 16): capacity limits count symbols, so recoding to higher-information symbols stores more content in the same slots. Named phases ("Phase 2: dedupe pipeline — done") let the context carry the whole task's shape in a dozen lines; the agent reasons over phase-level structure and re-expands a phase's details (from the log) only when needed. Same trick as a good proof citing lemmas instead of re-deriving them.
    3. HARD Attention cost is $O(n^2)$ per step in context length $n$ (Chapter 21). Compare total compute of (a) an agent that lets context grow linearly to $n = cT$ over $T$ steps, vs (b) one that holds $n = n_0$ constant by summarizing. Derive the scaling in $T$ for both.
      Solution
      (a) Step $t$ costs $\propto (ct)^2$; total $\propto c^2\sum_{t=1}^T t^2 = c^2\,\frac{T(T+1)(2T+1)}{6} = O(T^3)$ — cubic in task length. (b) Each step costs $\propto n_0^2$; total $O(n_0^2 T)$ — linear, plus summarization overhead $O(T/k)$ summary calls. The ratio grows like $T^2$: a 10× longer task is 1000× more expensive under (a) vs 10× under (b). This is why every long-horizon agent framework has compaction; the open question is only what information the summaries lose (next: memory consolidation and compression).

    Episodic memory

    Episodic memory stores what happened: particular events, with their when and where — "on Tuesday's run, the deploy failed because the token expired". It is memory of instances, not general facts, and it is what lets an agent learn from its own past without retraining: the next time a deploy fails, the relevant episode is retrieved and its lesson applied.

    Definition An episodic store is a set of records $e_i = (\text{content}, \text{time}, \text{task context}, \text{outcome})$ written during operation (per event, per step, or per completed task), and read by relevance retrieval at later times. Canonical retrieval score (generative-agents style): $\mathrm{score}(e) = \alpha\,\mathrm{sim}(q, e) + \beta\,\mathrm{recency}(e) + \gamma\,\mathrm{importance}(e)$, with recency exponentially decayed, e.g. $\mathrm{recency} = \delta^{\Delta t}$, and importance rated at write time.
    Worked example Score three episodes for the query "deploy failed with 401" ($\alpha = \beta = \gamma = 1$; $\delta = 0.99$ per hour; sim and importance in $[0,1]$). E1: "deploy failed: expired CI token, fixed by rotating secret" — sim 0.85, 200 h old ($0.99^{200} = 0.134$), importance 0.8 → $0.85 + 0.134 + 0.8 = 1.784$. E2: "deploy succeeded after retry" — sim 0.55, 3 h old ($0.970$), importance 0.3 → $1.820$. E3: "lunch order arrived late" — sim 0.05, 1 h old ($0.990$), importance 0.1 → $1.140$. E2 edges out E1 on recency despite E1 being the true precedent — with $\gamma$ raised to 2 (importance 1.6 vs 0.6), E1 wins ($2.58$ vs $2.12$). The weights are a policy choice, and the failure mode of each mis-weighting is predictable: too much $\beta$ = goldfish, too much $\alpha$ = nostalgic literalism, too much $\gamma$ = drama queen.
    Where this goes Reflection (later this chapter) turns episodes into lessons; consolidation turns them into semantic memory.
    Drill
    1. EASY With $\delta = 0.99$/hour, what is the recency weight of a 1-week-old episode?
      Solution
      $0.99^{168} = e^{168\ln 0.99} \approx e^{-1.688} \approx 0.185$.
    2. MED What should the unit of an episode be — a raw tool call, a step, or a completed task with outcome? Argue with retrieval in mind.
      Solution
      Retrieval serves future decisions, so the unit should carry a decision-relevant lesson: "task + what was tried + outcome + why" is the sweet spot. Raw tool calls are too granular (retrieving one is context-free noise; the store fills with millions of them); whole sessions are too coarse (the relevant nugget is buried, and similarity to a 10k-token blob is meaningless). Practical design: log everything raw (the event log is the ground truth), but write episodic summaries at task or milestone boundaries — one record per "thing that happened worth remembering", with outcome labels. Consolidation can always re-mine the raw log.
    3. HARD An agent retrieves its top-3 episodes into context each step. Describe the self-reinforcement pathology this creates and two mitigations.
      Solution
      Retrieved episodes influence current behavior → current behavior resembles them → the new episodes written are similar to the retrieved ones → their embeddings cluster tighter → they are retrieved even more (rich-get-richer, like a Pólya urn). The store converges to a self-confirming rut: early habits, good or bad, become permanent; a bad early lesson ("retries don't help") suppresses the exploration that would refute it. Mitigations: (1) outcome-weighted retrieval and forgetting — decay or down-weight episodes whose advice was followed and led to failure (close the loop on memory quality); (2) diversity in retrieval (MMR-style selection: penalize episodes similar to ones already retrieved) plus an exploration floor — occasionally act without memory conditioning, generating fresh episodes that can contradict the rut. Also: mark retrieved memories as suggestions, not instructions, in the prompt.

    Semantic memory

    Semantic memory stores what is true: facts, concepts, relationships, stripped of the episode that taught them — "the staging DB is read-only", not "on May 3rd I discovered...". It is the agent's knowledge base, and unlike episodic memory it should be deduplicated, updated in place, and checked for contradictions, because facts change.

    Definition A semantic store holds atomic assertions $f_j = (\text{subject}, \text{claim}, \text{confidence}, \text{provenance}, \text{timestamp})$ — as text snippets, key-value profiles, or knowledge-graph triples $(s, r, o)$. Write path: extract candidate facts from episodes/documents, canonicalize, then upsert: new fact → insert; matching fact → merge/boost confidence; conflicting fact → resolve (recency/provenance wins) or flag (contradiction detection, below). Read path: retrieval by the current query, same machinery as any retrieval system.
    Worked example Upsert in action. Store contains: ("api.example.com", "rate limit", "100 req/min", conf 0.9, from docs, Jan). New episode yields: "got 429 at 60 req/min — limit seems to be 60 now". Extraction: ("api.example.com", "rate limit", "60 req/min", conf 0.7, observed, Sep). Same subject+relation, different value → conflict path: observed-and-newer beats documented-and-older for operational facts, so the store updates to 60 with a note "docs say 100; observed 60 on Sep 12", keeping both provenances. An agent that instead appended a second fact would retrieve both and randomly act on either — semantic memory must be a merge, not a log.
    Think first Why keep episodic and semantic stores separate rather than one big pile of text memories?
    Reveal
    They have opposite maintenance semantics. Episodes are immutable history: never edit, only decay — their value is being a true record. Facts are mutable current-belief: dedupe, update in place, resolve conflicts — their value is being correct now. One pile forces one policy: either you "update" history (destroying the record) or you append facts (accumulating stale contradictions). Separation also aids retrieval: "what happened last time" and "what is true of X" are different queries with different ideal indexes.
    Drill
    1. EASY Classify as episodic or semantic: (a) "User prefers replies in Spanish"; (b) "On task #412 the user corrected my English reply to Spanish"; (c) "psql timeout is 30 s".
      Solution
      (a) semantic (a durable fact about the user, distilled); (b) episodic (a dated event — the evidence for (a)); (c) semantic.
    2. MED Design the confidence update for a fact re-observed $k$ times independently, starting at 0.7 per observation. When should confidence not increase with repetition?
      Solution
      Independent confirmations: treat each as evidence with likelihood ratio $\Lambda$; in log-odds, confidence grows additively (Chapter 30) — e.g. odds $\times\Lambda$ per observation, saturating sensibly ($1 - (1-0.7)^k$ is a simple version: 0.7, 0.91, 0.973...). Do NOT increase when observations are correlated: re-reading the same document, or re-extracting from episodes that all descend from one original claim (provenance tracking exists precisely to detect this). $k$ copies of one source is one observation; boosting per copy manufactures certainty out of duplication — the memory-store version of citogenesis.
    3. HARD Knowledge-graph triples vs free-text snippets for semantic memory: give two queries where the graph wins structurally, and the standard argument for text winning anyway in LLM agents.
      Solution
      Graph wins: (1) multi-hop queries — "which services depend on a library owned by team X?" is a 2-edge traversal, exact and complete; text retrieval must hope some snippet co-mentions the chain, and similarity search doesn't compose hops. (2) Aggregations/negations — "list ALL services without an owner" needs exhaustive enumeration, which similarity retrieval fundamentally can't guarantee (it returns the closest $k$, not the complete set). Text wins in practice because: extraction to a fixed schema is lossy and error-prone (the schema never anticipates all knowledge; wrong triples are confidently wrong), while LLMs natively consume nuanced free text — "read the 5 most relevant notes" degrades gracefully where "query the graph" fails brittly. The converging answer: text as ground truth with graph-shaped indexes (entities, links) layered on for the hop/aggregate queries — hybrid, like everything in retrieval.

    Procedural memory

    Procedural memory stores how to do things: skills, routines, checklists — knowledge that shows up as competent action rather than recallable fact. In humans it's riding a bicycle; in LLM agents it's the prompt playbooks, code snippets, and tool-use recipes the agent consults or has baked in. Its defining property: it is executed, not merely retrieved.

    Definition Procedural memory holds executable know-how: (i) in-weights — behaviors instilled by training/fine-tuning (the model "just knows" how to write a git commit); (ii) in-store — retrievable procedures: skill files, prompt templates, scripts, checklists, each with triggering conditions ("when deploying a Python service: ..."). A skill record is $(\text{trigger}, \text{procedure}, \text{preconditions}, \text{success criteria})$; acquisition is writing a new skill after solving a novel task (e.g. Voyager's growing skill library), and refinement is editing it after failures.
    Worked example Skill acquisition loop. Task: "set up nightly DB backups" — the agent solves it in 14 messy steps with two dead ends. A reflection pass distills: trigger "schedule recurring job on host X"; procedure: 6 clean steps (the working path only); preconditions: "cron access, creds in vault"; success check: "run job manually once, verify artifact". Next occurrence of a matching task: retrieved skill turns 14 exploratory steps into 6 scripted ones — measured as both speed (≈2× fewer calls) and reliability (the two dead ends are not re-explored). The store converts one agent-hour of search into a reusable amortized asset — the same amortization argument as metareasoning's compiled reflexes (Chapter 30).
    Pitfall Procedures rot. Environments change under them (APIs, paths, versions), and a confidently retrieved stale procedure fails worse than fresh reasoning — the agent trusts it and skips the checks it would otherwise run. Every stored skill needs its preconditions verified at use time, and a failure of a skill should down-weight or flag the skill, not just the episode.
    Drill
    1. EASY Classify: (a) "how to rotate the API key (7 steps)"; (b) "the API key was rotated on May 2"; (c) "keys expire every 90 days".
      Solution
      (a) procedural; (b) episodic; (c) semantic. The trio shows the three stores cooperating around one topic.
    2. MED A skill library grows to 500 skills. Retrieval brings the top-3 by similarity to the current task. What new failure appears, and what metadata fixes it?
      Solution
      Near-miss retrieval: the top-3 by text similarity may match the task's surface ("deploy...") but not its situation (wrong stack, wrong environment, deprecated) — and a plausible-but-wrong procedure is actively harmful (see the pitfall). Fixes: structured preconditions matched against the current state (filter before similarity, not after); per-skill success statistics (retrieve by expected utility, not just similarity — a skill with 2/9 recent successes is a warning, not a recipe); version/env tags; and a "no skill applies" threshold below which the agent reasons from scratch rather than force-fitting the nearest skill.
    3. HARD In-weights vs in-store procedures: compare on latency/cost, adaptability, auditability, and transfer across agents — and say which direction the industry's "skills" abstractions move procedures, and why.
      Solution
      In-weights: zero retrieval latency, always "in scope", cheap per use; but adaptation needs retraining, behavior is unauditable (you can't diff a weight-encoded habit), and transfer means shipping model checkpoints. In-store: costs tokens and a retrieval step; but editable in seconds (fix a step, all future uses fixed), fully auditable/diffable, versioned, and portable across any agent that can read text — plus per-skill permissioning. Industry skill/playbook abstractions move procedures out of weights into stores for exactly the governance reasons: enterprises need to inspect, edit, approve and share "how the agent does X" without touching a model. The equilibrium mirrors human organizations: weights hold general competence (how to code), stores hold local procedure (how WE deploy) — and consolidation (next) is the compiler between them.

    Memory consolidation

    Raw experience is bulky, redundant and mostly noise; consolidation is the background process that refines it — merging duplicate episodes, distilling recurring patterns into semantic facts, compiling successful action sequences into procedures, and letting the unimportant fade. It is the agent's sleep: not a luxury, but how a memory system stays useful as it grows.

    Definition Consolidation is a periodic (or event-triggered) transformation over the stores: $\mathrm{episodic} \to \mathrm{semantic}$ (patterns across episodes become facts: 5 episodes of 429 errors → "API limit is 60/min"); $\mathrm{episodic}\to\mathrm{procedural}$ (a working solution path becomes a skill); intra-store: dedup/merge, summarize clusters, decay-and-forget below an importance threshold. Formally it is compression with a utility constraint: minimize store size subject to preserving expected retrieval value for future tasks — lossy by design, and the loss policy is the design.
    Worked example One consolidation pass. Input: 40 episodes from a week (9,000 tokens). Clustering finds: 12 episodes about flaky test X (→ one semantic fact "test X is flaky under parallel runs, serialize it", conf 0.9; 12 episodes marked consolidated, kept as one exemplar + count); 6 episodes tracing one solved deployment (→ one procedure, 8 steps); 15 routine successes (→ decayed: importance 0.1, below threshold after a week → dropped); 7 unrelated singletons (kept as-is). Output stores: 1 fact + 1 skill + 8 episodes ≈ 1,100 tokens — a 8× compression that raises retrieval quality: the fact now outranks 12 near-duplicate episodes that used to crowd the top-k slots.
    Where this goes The compression side is formalized under memory compression below; what must never be lost silently is the provenance (two topics down).
    Drill
    1. EASY Name the target store for each consolidation: (a) "these 8 episodes show the user always wants tables, not prose"; (b) "this exact sequence fixed the build 3 times"; (c) "these 20 duplicate success logs".
      Solution
      (a) semantic (a user-preference fact); (b) procedural (a skill); (c) intra-episodic merge/decay (keep count + one exemplar, or drop).
    2. MED Why should consolidation run as a separate offline process rather than inline during tasks — give a cost reason and a quality reason.
      Solution
      Cost: consolidation reads many records and does clustering/LLM summarization — amortized cheaply in batch off the critical path, ruinous per-step (every loop iteration would pay it in latency and tokens). Quality: patterns are only visible across many episodes and after outcomes are known — inline, you'd distill from single unconfirmed events (was that fix actually right? wait until the task's end says so); offline, you consolidate with hindsight, using outcome labels to keep what worked. The biological echo (hippocampal replay during sleep) is the same argument: separate fast capture from slow integration.
    3. HARD Consolidation is where memory errors are born: list three distinct error types the process can inject, with a mitigation each.
      Solution
      (1) Overgeneralization: 3 episodes where retries failed → "retries never work" — a universal from a biased sample (all three were the same outage). Mitigation: require support diversity (distinct contexts/times) before promoting to a fact, and record the support count/conditions in the fact. (2) Summary drift/hallucination: the LLM summarizer adds or distorts details not in the sources (classic generation failure). Mitigation: extractive-first summaries (quote spans), provenance links back to raw episodes, and spot-verification of promoted facts against their sources. (3) Silent loss: decay deletes the one episode that would have mattered (rare-but-critical events score low on frequency-based importance). Mitigation: importance functions that weight outcome severity, not just frequency ("caused an outage" never decays); archive rather than delete (drop from the index, keep the log). Every consolidation should be reversible from the raw event log — compression you can undo is compression you can trust.

    Memory retrieval

    A memory is only as good as the moment it resurfaces. Retrieval is the read side of every store: given the current need — a query, the task state — return the few records most likely to help, under a token budget. The next seven topics are the standard pipeline: sparse and dense scoring, ANN indexes, hybrid fusion, reranking, routing.

    Definition Retrieval: given query $q$ and corpus $\mathcal D = \{d_i\}$, return top-$k$ by a relevance score $s(q, d)$. The pipeline stages: candidate generation (fast, high-recall scoring over the whole corpus — sparse or dense), fusion (combine multiple scorers), reranking (slow, precise scoring of the shortlist), assembly (fit winners into the context budget). Evaluation: recall@k $= \frac{|\text{relevant} \cap \text{top-}k|}{|\text{relevant}|}$, precision@k, and MRR $= \frac{1}{|Q|}\sum_q \frac{1}{\mathrm{rank}_q(\text{first relevant})}$.
    Worked example Metrics on one query. Relevant docs: $\{d_3, d_7, d_9\}$. System returns top-5: $(d_7, d_1, d_3, d_4, d_8)$. Recall@5 $= 2/3 \approx 0.667$ ($d_9$ missed). Precision@5 $= 2/5 = 0.4$. Reciprocal rank $= 1/1 = 1.0$ (first hit at rank 1). If a second query's first relevant hit lands at rank 4, its RR is 0.25 and MRR over the two queries $= (1.0 + 0.25)/2 = 0.625$. Note the division of labor: recall@k judges candidate generation (did the answer make the shortlist?), MRR/precision judge ranking (is it near the top, where the context budget lives?).
    Pitfall The stage that kills most systems is the one nobody evaluates: recall of candidate generation. Rerankers and prompts get tuned endlessly while 30% of answers never enter the top-100 shortlist at all — no downstream stage can recover a document that was never retrieved. Measure recall@100 before touching anything else.
    Drill
    1. EASY Relevant set $\{d_2, d_5\}$; returned top-4: $(d_9, d_5, d_2, d_1)$. Compute recall@4, precision@4, and RR.
      Solution
      Recall@4 $= 2/2 = 1.0$. Precision@4 $= 2/4 = 0.5$. RR $= 1/2 = 0.5$ (first relevant at rank 2).
    2. MED Your pipeline: candidates top-100 (recall@100 = 0.85), reranker lifts a present relevant doc into top-5 with probability 0.9. What's the end-to-end recall@5, and which stage do you improve if the reranker could instead be made perfect?
      Solution
      End-to-end $\approx 0.85\times0.9 = 0.765$. Perfect reranker: $0.85\times1.0 = 0.85$ — a ceiling set by candidate recall. Improving candidate recall to 0.95 with the current reranker: $0.95\times0.9 = 0.855$ — better than perfecting the reranker. Fix the leakiest stage; it's usually the first.
    3. HARD Agent memory retrieval differs from web search in that the "query" is often implicit (the task state, not a question). Give three concrete query-formulation strategies and their trade-offs.
      Solution
      (1) Last-turn-as-query: embed the latest observation/message. Cheap, zero extra calls; but myopic — misses needs implied by the broader task ("we're refactoring auth" context lost when the last turn is a stack trace). (2) LLM query generation: ask the model "what should we look up?" — can synthesize multi-faceted queries (error + component + past-incident phrasing), the standard for agentic search; costs a call and can hallucinate needs. (3) HyDE-style: generate a hypothetical answer and embed that — aligns query and document distributions (answers look like documents, questions don't), improving dense recall; risk: the hypothesis biases retrieval toward confirming itself. Practical stacks combine (1) as the cheap default with (2) escalated when stakes/uncertainty are high — a metareasoning (VOC) decision from Chapter 30.

    Sparse retrieval

    Sparse retrieval scores documents by the exact words they share with the query, weighted by how informative each word is. It is called sparse because each document is a vector with one dimension per vocabulary word, almost all zeros. Forty years old and still the backbone: exact term match is unbeatable for names, codes, error strings — the tokens whose meaning IS their spelling.

    Definition Represent documents in the term-frequency space; score by TF-IDF-style weighting: term frequency $\mathrm{tf}(t,d)$ times inverse document frequency $\mathrm{idf}(t) = \log\frac{N}{n_t}$ (with $N$ documents, $n_t$ containing $t$): common words count little, rare words a lot. Score $s(q,d) = \sum_{t\in q} \mathrm{tf}(t,d)\cdot\mathrm{idf}(t)$. Implementation: an inverted index mapping each term to its postings list of documents, so only documents sharing a query term are ever touched — sub-linear in corpus size.
    Worked example Corpus of $N = 1000$ docs. Query "kernel panic". "kernel" appears in $n = 50$ docs: idf $= \log(1000/50) = \log 20 \approx 3.00$ (natural log). "panic" in 20: idf $= \log 50 \approx 3.91$. Doc A contains kernel ×3, panic ×1: $s = 3(3.00) + 1(3.91) = 12.91$. Doc B contains kernel ×1, panic ×2: $s = 3.00 + 2(3.91) = 10.82$. Doc C contains "the" ×40 (idf $= \log(1000/990) \approx 0.01$) and kernel ×1: $s \approx 3.00 + 0.4 = 3.4$. A wins. Note the mechanism: rarity = information (Chapter 16's $-\log p$ is literally the idf formula — a term's weight is its surprisal).
    Where this goes BM25 (next) fixes TF-IDF's two blind spots: unbounded term-frequency reward and no length normalization.
    Drill
    1. EASY $N = 10^6$ docs; "the" appears in $9\times10^5$, "segfault" in 100. Compute both idfs (natural log) and their ratio.
      Solution
      idf(the) $= \ln(10^6/9{\times}10^5) = \ln 1.111 = 0.105$. idf(segfault) $= \ln(10^4) = 9.21$. Ratio $\approx 87$: one "segfault" outweighs dozens of "the"s.
    2. MED Why does an inverted index make sparse retrieval fast, and what query type defeats it?
      Solution
      The index maps term → postings list; scoring touches only $\bigcup_{t\in q}\mathrm{postings}(t)$ — for rare terms, a few hundred docs out of millions, with skip-list/WAND tricks pruning further. Defeated by queries whose every term is common (all postings lists huge — approaching a full scan), and structurally by vocabulary-mismatch queries: if the query says "car" and the doc says "automobile", the intersection is empty and the doc is unreachable at any speed — the gap dense retrieval exists to fill.
    3. HARD Sparse vectors have dimension $|V| \approx 10^5$ yet dot products are cheap; dense vectors have $d = 10^3$ yet need special indexes. Explain the asymmetry.
      Solution
      Cost tracks nonzeros, not dimensions. A sparse query has ~5 nonzero terms; its dot product with the corpus touches only those 5 postings lists — the inverted index is exactly a transposed sparse matrix, and sparsity makes exhaustive scoring sub-linear. Dense vectors have ALL $10^3$ coordinates nonzero for every document: no postings structure exists (every doc "contains" every dimension), so exact search is a full $O(Nd)$ scan, and sub-linear search requires approximate geometric indexes (ANN, below) that exploit the vectors' clustering rather than their zeros. Sparsity is a computational resource; density buys semantics by spending it.

    BM25

    BM25 is TF-IDF with two dials of realism: seeing a term twice matters less than twice as much (saturation), and long documents shouldn't win just by containing more words (length normalization). It is the default lexical ranker in nearly every search engine, and the baseline that dense retrieval papers still have to beat.

    Definition $$\mathrm{BM25}(q,d) = \sum_{t\in q} \mathrm{idf}(t)\cdot\frac{\mathrm{tf}(t,d)\,(k_1 + 1)}{\mathrm{tf}(t,d) + k_1\Big(1 - b + b\,\frac{|d|}{\mathrm{avgdl}}\Big)}, \qquad \mathrm{idf}(t) = \ln\!\Big(\frac{N - n_t + 0.5}{n_t + 0.5} + 1\Big),$$ with $k_1 \in [1.2, 2]$ controlling term-frequency saturation (as $\mathrm{tf}\to\infty$ the fraction $\to k_1 + 1$: bounded) and $b\in[0,1]$ the length-normalization strength ($b = 0$: none; $b = 1$: full).
    Worked example $k_1 = 1.5$, $b = 0.75$, avgdl $= 100$. Query term with idf $= 3.0$; document length 200 (twice average), tf $= 4$. Denominator's length factor: $1 - 0.75 + 0.75\cdot 2 = 1.75$. Score contribution $= 3.0\cdot\frac{4\cdot 2.5}{4 + 1.5\cdot 1.75} = 3.0\cdot\frac{10}{6.625} = 4.53$. Same tf in a length-100 doc: factor 1, contribution $= 3.0\cdot\frac{10}{5.5} = 5.45$ — the long doc is discounted 17%. Saturation: raising tf from 4 to 8 in the average doc gives $3.0\cdot\frac{20}{9.5} = 6.32$, only +16% for doubling the count; tf $\to\infty$ caps at $3.0\times2.5 = 7.5$. Keyword stuffing has strictly diminishing returns.
    Explore

    One query term, idf fixed at 3. Slide tf, document length, and the two dials — watch saturation bend the curve and length normalization slide it.

    1. EASY With $k_1 = 1.2$, $b = 0$, idf $= 2$, compute the score for tf $= 1$ and tf $= 3$.
      Solution
      tf=1: $2\cdot\frac{1\cdot2.2}{1 + 1.2} = 2\cdot 1.0 = 2.0$. tf=3: $2\cdot\frac{3\cdot2.2}{3+1.2} = 2\cdot\frac{6.6}{4.2} = 3.14$. Tripling tf adds only 57%.
    2. MED Why does BM25's idf use the odd-looking $\ln\frac{N - n_t + 0.5}{n_t + 0.5}$ form, and what happens to a term appearing in more than half the corpus under the un-shifted variant?
      Solution
      It derives from the Robertson–Sparck Jones relevance weight — the log-odds that a document containing $t$ is relevant vs not, under the probabilistic retrieval model; the $+0.5$s are add-half smoothing (avoiding division by zero and taming small counts). Without the outer $+1$ (the classic form), a term with $n_t > N/2$ gets $\ln$ of a value $< 1$: a negative weight — matching a very common term would reduce the score, which is why Lucene's variant adds 1 to keep idf $\ge 0$.
    3. HARD Your agent's memory corpus contains many short factoids (~20 tokens) and a few long transcripts (~2,000). With avgdl pulled to 120 by the mix, what does $b = 0.75$ do to each class, and how would you fix retrieval quality without abandoning BM25?
      Solution
      Length factor $1 - b + b|d|/\mathrm{avgdl}$: factoids get $0.25 + 0.75(20/120) = 0.375$ — their term matches are amplified ~2.7× (denominator shrinks); transcripts get $0.25 + 0.75(16.7) = 12.75$ — matches crushed ~13×. So a transcript containing the exact answer once loses to a factoid sharing one incidental term: bimodal length distributions break the single-avgdl assumption. Fixes: (1) chunk the transcripts to comparable lengths before indexing (the standard answer — normalize the corpus, not the formula); (2) index the classes separately with per-class avgdl and fuse results (RRF, below); (3) lower $b$ toward 0.3 as a compromise, accepting weaker length correction. Chunking is best: it also improves the granularity of what gets stuffed into context.

    Dense retrieval

    Dense retrieval scores by meaning instead of spelling: an encoder maps queries and documents into one vector space where "car" and "automobile" land close together, and relevance is geometric closeness. It finds what sparse retrieval structurally cannot — paraphrases, translations, descriptions — and misses what sparse nails: exact identifiers it has never learned to embed.

    Definition A bi-encoder embeds query and document independently: $u = E_q(q)$, $v = E_d(d) \in \mathbb R^{d}$, with relevance $s(q,d) = \cos(u, v) = \frac{u^\top v}{\lVert u\rVert\lVert v\rVert}$ (or plain dot product). Documents are embedded offline and indexed; a query costs one encoder pass plus a nearest-neighbor search. Trained contrastively (Chapter 21's InfoNCE) on (query, positive doc, negatives): pull true pairs together, push negatives apart — the quality of hard negatives (lexically similar but irrelevant) largely determines the model.
    Worked example Cosine in the small. $u = (0.6, 0.8)$, $v_1 = (0.8, 0.6)$, $v_2 = (-0.6, 0.8)$. $\cos(u, v_1) = \frac{0.48 + 0.48}{1\cdot1} = 0.96$ — near-duplicate meaning. $\cos(u, v_2) = \frac{-0.36 + 0.64}{1} = 0.28$ — weakly related. Where it beats sparse: query "how do I make my code run faster" matches a doc titled "optimizing Python performance" with zero shared content words — sparse score 0, dense cosine high, because the encoder was trained to map both descriptions of the intent to the same region.
    Pitfall Dense retrieval fails exactly where semantics is not the signal: exact codes (error 0x80070057), version strings, names the encoder tokenizes into meaningless pieces, and negation ("flights NOT via Frankfurt" embeds close to its opposite). It also degrades out-of-domain: an encoder trained on web QA mis-ranks legal or genomic text. These are precisely sparse retrieval's strengths — hence hybrid (two topics down).
    Drill
    1. EASY Compute the cosine similarity of $u = (1, 2, 2)$ and $v = (2, 1, 2)$.
      Solution
      $u\cdot v = 2 + 2 + 4 = 8$; $\lVert u\rVert = \lVert v\rVert = 3$. Cosine $= 8/9 \approx 0.889$.
    2. MED Why are hard negatives essential in training, and what does a model trained only with random negatives learn?
      Solution
      Random negatives are trivially far (a cooking doc for a kernel query): the contrastive loss is quickly satisfied by coarse topical features, and gradients vanish — the model learns topic detection, not relevance. At retrieval time its errors are exactly the cases that matter: among 50 same-topic candidates it cannot rank the truly relevant one. Hard negatives (same topic, shared words, wrong answer — e.g. BM25-retrieved non-answers) force the encoder to learn the fine distinctions that separate relevant from related. The curriculum mirrors the deployment distribution: you will always be ranking among plausible candidates.
    3. HARD Bi-encoder vs cross-encoder: the cross-encoder reads query and document together through full attention. Explain why the bi-encoder's factorization $s = u^\top v$ is both its scaling superpower and a hard expressiveness ceiling, with a concrete relevance pattern it cannot represent.
      Solution
      Superpower: independence of the two encoders lets all $N$ document vectors be precomputed; query time is one encoding + a MIPS/ANN lookup — $O(1)$ encoder passes versus the cross-encoder's $N$ joint passes. Ceiling: relevance must be a fixed bilinear function of two independently-computed points; all query-document interaction is squeezed through one $d$-dimensional bottleneck before the pair ever "meet". Patterns beyond it: any relevance requiring token-level alignment between the specific pair — e.g. "does this doc answer THIS question's particular constraint" ("...returns error 42 when the input is empty AND the flag is set"): the doc vector must pre-commit to one summary of everything it could be relevant to; a conjunction of details that only matters for this query can't be checked without joint attention. Formally, cross-encoders compute functions of the pair outside the bilinear class (and empirically rerank far better). Hence the pipeline: bi-encoder recall over millions, cross-encoder precision over the top-100 (reranking, below).

    Vector databases

    Once documents are vectors, you need a place that stores millions of them, finds near neighbors in milliseconds, keeps metadata attached, and handles inserts and deletes without rebuilding the world. That is a vector database: an ANN index wrapped in database ergonomics — filtering, persistence, replication, hybrid queries.

    Definition A vector database stores records $(\mathrm{id}, v\in\mathbb R^d, \text{metadata}, \text{payload})$ and serves $k$-NN queries $\mathrm{top}_k \{s(q, v_i)\}$ — usually approximate (next topic) — with metadata filtering (pre- or post-filter: "only records where user=X and date>Y"), CRUD, and often built-in hybrid (sparse+dense) search. Memory arithmetic: $N$ vectors of dimension $d$ in float32 cost $4Nd$ bytes plus index overhead (HNSW graphs add roughly 1.5–2×); quantization (int8, product quantization) divides storage by 4–64× at some recall cost.
    Worked example Sizing an agent's memory store. 5M chunks, $d = 768$, float32: $4\times 5{\times}10^6\times 768 = 15.36$ GB of raw vectors; with HNSW overhead ≈ 25–30 GB RAM. Options: (a) int8 quantization → 3.84 GB raw (≈ 8 GB served), recall drop typically <1–2%; (b) reduce to $d = 256$ via Matryoshka/truncation → 5.12 GB float32, small quality loss; (c) both → ≈1.3 GB raw. The lesson: vector memory cost is a design variable spanning 20× for a few points of recall — and at 5M records, exact scan (15 GB per query pass) is why ANN indexes are non-negotiable.
    Think first Metadata filtering: should the DB filter before the ANN search or after? What goes wrong in each direction?
    Reveal
    Post-filter: ANN returns top-100 overall, then filter — if the filter is selective (user=X owns 0.1% of records), likely zero survivors: recall collapses. Pre-filter: restrict to matching records, then search — correct results, but the ANN index (built over everything) navigates poorly over a sparse allowed-subset (graph connectivity breaks); naive fallback is brute-force over the filtered set, fine when small, slow when the filter matches millions. Real engines choose per-query by estimated selectivity, or maintain filtered sub-indexes — know which yours does, because "works in the demo, empty in prod" is usually this.

    1. EASY How many GB do 20M vectors at $d = 1536$, float32, raw?
      Solution
      $4\times2{\times}10^7\times1536 = 1.2288\times10^{11}$ bytes ≈ 122.9 GB.
    2. MED Product quantization splits $d = 768$ into 96 sub-vectors of 8 dims, each coded by its nearest of 256 centroids. Compute bytes per vector and the compression vs float32, and name the cost.
      Solution
      96 sub-codes × 1 byte (256 = $2^8$ centroids) = 96 B per vector, vs $4\times768 = 3072$ B: 32× compression. Cost: distances are computed to reconstructed (centroid-approximated) vectors — a lossy metric; recall at a given $k$ drops, typically mitigated by re-scoring the shortlist against full-precision vectors kept on disk.
    3. HARD An agent writes memories continuously (inserts) and consolidation deletes/updates them. Why are deletes hard for graph-based ANN indexes, and what do production systems actually do?
      Solution
      HNSW-style graphs are built by linking each new point into a navigable small-world structure; a node also serves as a routing waypoint for searches passing through its neighborhood. Hard-deleting it orphans its neighbors' links and can disconnect regions — recall degrades unpredictably; repairing connectivity properly is close to local rebuilding. Production practice: tombstoning (mark deleted, filter from results, keep routing through the corpse), then periodic background compaction/rebuild when tombstones exceed a threshold (10–20%); some engines use segment architectures (LSM-like): immutable index segments + a small fresh segment, merged periodically — deletes are segment rewrites. The agent-design consequence: prefer append + tombstone semantics for memory updates, and schedule consolidation to coincide with index compaction.

    Approximate nearest neighbor search

    Exact nearest-neighbor search over millions of dense vectors means scanning them all — the curse of dimensionality kills every exact shortcut. ANN search trades a sliver of recall for orders of magnitude of speed: navigate a graph of neighborhoods, or probe a few clusters, and find almost always the same neighbors a full scan would.

    Definition ANN structures answer top-$k$ queries approximately, measured by recall vs exact search. Two dominant families: IVF (inverted file): k-means the corpus into $C$ cells; at query time search only the $n_{\text{probe}}$ nearest cells — cost $\approx \frac{n_{\text{probe}}}{C}N$ distance computations; recall grows with $n_{\text{probe}}$. HNSW (hierarchical navigable small world): a multi-layer proximity graph; search greedily descends from a sparse top layer to the dense bottom layer, keeping a beam of $\mathrm{ef}$ candidates — $O(\log N)$-ish hops, recall grows with $\mathrm{ef}$. Both expose one knob trading recall against latency.
    Worked example IVF arithmetic. $N = 10$M, $C = 4096$ cells (avg 2,441 vectors each). $n_{\text{probe}} = 8$: distances computed $\approx 8\times2441 = 19{,}528$ plus 4,096 centroid distances ≈ 23.6k total — a 424× speedup over the 10M full scan. Suppose measured recall@10 is 0.87. Doubling $n_{\text{probe}}$ to 16: ≈43.2k distances (232× speedup), recall 0.94; at 64: ≈160k (63×), recall 0.99. The recall-latency curve is concave — the first probes buy the most — and where you sit on it should be chosen by the application's tolerance, not the default.
    Explore

    2-D IVF: points are clustered into cells; the query (crosshair) searches only the nearest n_probe cells. See which true neighbors are found vs missed as you turn the knob.

    Pitfall ANN recall failures are silent and query-dependent: queries near cell boundaries lose neighbors that sit just across the border (IVF), and out-of-distribution queries navigate the graph poorly (HNSW). An agent whose memory lookup quietly misses the crucial record 8% of the time exhibits maddening "sometimes it remembers, sometimes it doesn't" behavior — benchmark recall on YOUR query distribution, not the index's advertised numbers.

    1. EASY IVF with $C = 1024$ cells over 2M vectors, $n_{\text{probe}} = 4$: roughly how many distance computations per query (ignoring centroids)?
      Solution
      Avg cell ≈ 1953 vectors; $4\times1953 \approx 7{,}800$ — vs 2M for exact: ~256×.
    2. MED Why does exact sub-linear NN search break in high dimensions (the curse), making "approximate" the only option?
      Solution
      Space-partitioning structures (k-d trees etc.) prune regions provably farther than the current best. In high $d$, distances concentrate: the gap between the nearest and the median neighbor shrinks relative to the mean distance, so almost no region can be provably excluded — the tree degenerates to scanning nearly everything ($2^d$-flavored branching for exactness). Real embeddings have lower intrinsic dimension (they cluster on manifolds, Chapter 9), which is exactly the structure IVF (cluster it) and HNSW (build a navigable graph on it) exploit — but only probabilistically, hence approximate.
    3. HARD In HNSW, explain the role of the layer hierarchy and of ef, and why recall problems concentrate on (a) low-degree "outlier" points and (b) filtered searches.
      Solution
      Layers implement zoom: upper layers hold exponentially fewer points with long-range links — greedy search there gets near the target region in few hops (like an expressway network); the bottom layer's short links finish locally. ef is beam width at the bottom: the search keeps the ef best-so-far candidates and expands them; larger ef explores more of the neighborhood graph before committing — recall rises, latency rises (Chapter 26's beam search, verbatim). (a) Outliers have few, long edges; greedy routes rarely pass near them and small beams never detour to them — they become unreachable islands (bad for rare-but-critical memories!). (b) Filtering removes nodes from consideration but the search still routes through the full graph; if survivors are sparse, beams fill with filtered-out nodes and valid candidates are never reached — recall craters unless ef is raised sharply or the engine has filter-aware traversal.

    Hybrid retrieval

    Sparse retrieval nails exact tokens and rare identifiers; dense retrieval nails paraphrase and meaning. Their failure sets barely overlap — which is precisely the condition under which combining classifiers pays (Chapter 19's ensembles). Hybrid retrieval runs both and merges the lists, and it is the boring, correct default for agent memory and RAG.

    Definition Hybrid retrieval issues the query to two (or more) engines — BM25 over an inverted index, cosine over a vector index — obtaining ranked lists $L_1, L_2$, then fuses them into one ranking, either by score fusion (normalize scores to comparable ranges, take a weighted sum $s = \lambda\,\tilde s_{\text{sparse}} + (1{-}\lambda)\,\tilde s_{\text{dense}}$) or by rank fusion (combine positions only — RRF, next topic). Variants add more channels: recency, metadata boosts, a second embedding model, or learned sparse models (SPLADE) that bridge the two families.
    Worked example Complementary failure, one query: "TypeError in payments-v2 retry handler". Dense list: docs about retry logic and error handling in payment services — semantic neighbors, but the top hit discusses payments-v1 (the encoder barely distinguishes version strings). Sparse list: every doc containing the literal "payments-v2" — including the changelog that names the bug, which dense ranked #40. Fused: the changelog (high sparse rank, mediocre dense) and the retry-pattern doc (high dense, absent sparse) both surface in the top 5. Coverage $=$ union of strengths; each channel's blind spot is covered by the other's postings.
    Pitfall Score fusion across engines is treacherous: BM25 scores are unbounded and corpus-dependent; cosines live in $[-1, 1]$ with model-specific typical ranges. A fixed $\lambda$ tuned on one corpus silently rebalances on another (add long documents → BM25's scale shifts → dense drowns). Min-max or z-score normalization per query helps but is noisy for short lists — which is exactly the case for rank-based fusion.
    Drill
    1. EASY Min-max normalize then fuse with $\lambda = 0.5$: sparse scores for docs (A, B, C) = (12, 8, 4); dense cosines = (0.6, 0.9, 0.3). Which doc wins?
      Solution
      Sparse normalized: A 1.0, B 0.5, C 0. Dense: A 0.5, B 1.0, C 0. Fused: A 0.75, B 0.75, C 0 — a tie between A and B (break by either raw signal or a reranker); C is out.
    2. MED Under what corpus/query conditions should you weight sparse higher, and dense higher? Give two each.
      Solution
      Sparse-heavy: (1) queries dominated by identifiers, codes, exact names — logs, legal citations, part numbers (semantics of these IS their literal form); (2) out-of-domain corpora where the embedding model is untrained (biomedical, code in a niche language) — dense similarity is unreliable there. Dense-heavy: (1) natural-language questions over prose where vocabulary mismatch is the norm (support KBs, docs: users never use the doc's words); (2) cross-lingual or paraphrase-heavy settings, where lexical overlap approaches zero by construction. Best practice: route per query (query routing, below) or let a reranker adjudicate.
    3. HARD Model hybrid gain: sparse alone has recall@20 = 0.7, dense alone 0.75. Compute the hybrid's top-40 (union) recall under (a) independent failures, (b) correlated failures where 60% of sparse's misses are also dense misses. What does the comparison teach?
      Solution
      (a) Miss probabilities 0.3 and 0.25; independent joint miss $= 0.075$; union recall $= 1 - 0.075 = 0.925$. (b) Joint miss $= P(\text{sparse miss})\times P(\text{dense miss}\mid\text{sparse miss}) = 0.3\times0.6 = 0.18$; union recall $= 0.82$. Teaching: the ensemble's value is entirely in the decorrelation of failures — hybrid gains 17.5 points under independence but only 7 under correlation. So invest in channels that fail differently (lexical vs semantic vs recency), not in a third embedding model correlated with the first; and measure joint-miss rate directly, since it — not either marginal recall — determines the hybrid ceiling. (Same theorem as Chapter 30's self-consistency ceiling and Chapter 19's ensemble diversity.)

    Reciprocal Rank Fusion

    RRF is the duct tape of retrieval: to merge ranked lists from engines whose scores are incomparable, ignore the scores entirely and add up reciprocal ranks. No normalization, no tuning worth the name, provably hard to break — and in practice within a whisker of carefully tuned score fusion.

    Definition Given ranked lists $L_1, \dots, L_m$, each document's fused score is $$\mathrm{RRF}(d) = \sum_{j=1}^{m} \frac{1}{k + r_j(d)},$$ where $r_j(d)$ is $d$'s rank in list $j$ (documents absent from a list contribute 0) and $k$ is a smoothing constant, canonically $k = 60$. Large $k$ flattens the curve (rank 1 barely beats rank 10 — gentle, consensus-driven); small $k$ sharpens it (top ranks dominate — winner-take-all).
    Worked example Two lists, $k = 60$. Sparse: (A, B, C, D); dense: (C, E, A, F). A: $\frac{1}{61} + \frac{1}{63} = 0.01639 + 0.01587 = 0.03226$. C: $\frac{1}{63} + \frac{1}{61} = 0.03226$ (tie with A — symmetric ranks). B: $\frac{1}{62} = 0.01613$. E: $\frac{1}{62} = 0.01613$. D: $\frac{1}{64} = 0.01563$. F: $\frac{1}{64} = 0.01563$. Fused order: {A, C} then {B, E} then {D, F}. The two documents that both engines liked (A ranked 1&3, C ranked 3&1) decisively beat every single-engine favorite — RRF is a consensus machine: appearing in multiple lists at moderate rank beats topping one list.
    Think first Why is throwing away the scores (keeping only ranks) so robust — and what information does it genuinely lose?
    Reveal
    Robust because ranks are invariant to any monotone transformation of each engine's scores: scale drift, corpus-dependent ranges, one engine's inflation — all vanish; no cross-engine calibration is needed, ever. Lost: score gaps. If dense scores are (0.95, 0.94, 0.41), ranks say 1, 2, 3 — the cliff between 2 and 3 (a strong "the answer is one of the first two" signal) is erased; likewise a query where one engine is confidently useless (all scores near zero) still contributes its noise ranks with full weight. Score fusion can in principle exploit both; in practice the calibration burden usually outweighs the gain, which is the empirical case for RRF.
    Drill
    1. EASY $k = 60$: doc ranked 2 in one list and 5 in another vs doc ranked 1 in a single list. Who wins?
      Solution
      Two-list doc: $\frac{1}{62} + \frac{1}{65} = 0.01613 + 0.01538 = 0.03151$. Single-list #1: $\frac{1}{61} = 0.01639$. The consensus doc wins by ~2×.
    2. MED Recompute the worked example with $k = 1$ and describe how the ordering philosophy changes.
      Solution
      A: $\frac12 + \frac14 = 0.75$. C: $\frac14 + \frac12 = 0.75$. B: $\frac13 = 0.333$. E: $\frac13 = 0.333$. D: $\frac15 = 0.2$. F: $0.2$. Same order here, but the ratios explode: rank 1 is worth 2.5× rank 4 (vs 1.05× at $k = 60$). With small $k$, a single top rank can beat presence in two lists (rank 1 alone $= 0.5$ > ranks 3+4 $= 0.45$): winner-take-all, trusting each engine's top picks; large $k$ trusts breadth of agreement. $k = 60$'s flatness is a deliberate bet that engines' fine-grained top-rank ordering is noise.
    3. HARD RRF over $m$ lists where one engine is adversarially bad (random ranks). How much can it corrupt the fusion, compared to score fusion with an unbounded bad engine? What does this say about adding channels?
      Solution
      RRF bounds each engine's influence: any document gets at most $\frac{1}{k+1}$ from one list ($\approx 0.0164$ at $k = 60$) — a random engine adds bounded, roughly uniform noise; documents favored by the honest engines (each contributing up to $\frac{1}{k+1}$ apiece) still dominate, degrading the fusion gracefully by ~$1/m$ of the signal. Score fusion with raw scores has no such bound: an engine emitting a huge score for one junk document places it at rank 1 outright — a single bad channel can own the output. Consequence: under RRF, adding a channel of uncertain quality is a low-risk experiment (bounded downside, possible decorrelation upside), which is why RRF-based hybrids accumulate channels (sparse + dense + recency + metadata boosts) so freely. With score fusion every added channel is a calibration liability.

    Reranking

    Candidate generation is built for recall over millions; it cannot afford to read anything closely. Reranking is the second, careful pass: a cross-encoder (or LLM judge) reads the query together with each of the top 50–100 candidates and re-scores them with full attention. It is the single highest-leverage quality upgrade in most retrieval stacks.

    Definition A reranker is a scoring model $s_\theta(q, d)$ that jointly encodes the pair (cross-attention over concatenated text, Chapter 21) and outputs a relevance score; applied to the fused shortlist of $n$ candidates, it costs $n$ forward passes and reorders them. Training: pairwise or listwise ranking losses on labeled/click data. LLM-as-reranker: prompt a model to score or order candidates — highest quality, highest cost. The architecture theorem from the dense-retrieval drill applies: joint encoding strictly generalizes bilinear scoring, so a good reranker dominates any bi-encoder ordering — at $n$× the compute.
    Worked example Budgeted pipeline. Corpus 5M chunks. Stage 1 (hybrid + RRF) returns top-100 in 30 ms, recall@100 = 0.93. Stage 2: cross-encoder at 3 ms/pair reranks 100 in 300 ms; among lists containing the answer, it places it top-5 with probability 0.92. End-to-end recall@5 $= 0.93\times0.92 = 0.856$ — versus 0.61 for the un-reranked hybrid's top-5. Cost: one query-time cross-encoder batch. The same reranker applied to top-1000 would add recall (candidate recall@1000 = 0.97) but 10× the latency: the shortlist size is the reranking budget dial, set by your latency SLO.
    Pitfall Rerankers are trained on relevance, not usefulness-to-the-agent. A chunk restating the question ranks high (maximal lexical-semantic match) while the chunk containing the answer's prerequisite ranks low. For agent memory, the score you want is "will including this change the next action for the better" — approximate it with task-conditioned reranking prompts ("rank by usefulness for deciding X"), not bare query-doc similarity.
    Drill
    1. EASY Reranking top-50 at 4 ms per pair, sequentially vs batched 8-wide: latencies?
      Solution
      Sequential: $200$ ms. Batched (assuming near-linear batching): $\lceil 50/8\rceil\times 4 \approx 28$ ms. Rerankers are batch-friendly; always batch.
    2. MED When does reranking HURT end-to-end quality? Give two mechanisms.
      Solution
      (1) Domain mismatch: a reranker trained on web QA applied to code or logs can be worse than the BM25 order it overwrites — it confidently reorders by the wrong notion of relevance (the fix: evaluate the reranker's win-rate over the stage-1 order before shipping; keep stage-1 order as fallback). (2) Objective mismatch amplification: with duplicate-heavy corpora, a relevance reranker fills the whole top-5 with five near-copies of the same top passage (each individually maximally relevant), squeezing out complementary information that the diversity-blind score can't see — fixed by MMR-style diversified selection after scoring, or dedup before.
    3. HARD Design the evaluation for a reranker in an agent-memory system where no relevance labels exist. Give three complementary methods and their biases.
      Solution
      (1) Downstream A/B: run the agent with/without the reranker on a task suite; measure task success, steps, cost. Unbiased for what you care about, but expensive, high-variance (task noise swamps retrieval deltas), and slow to iterate. (2) LLM-judged relevance: have a strong model label (query, memory) pairs sampled from live traffic; compute recall/MRR deltas offline. Fast and repeatable; biased by the judge's own relevance notion (correlated with the reranker if same model family — inflates agreement) and blind to usefulness-vs-relevance gaps. (3) Counterfactual replay: from logged episodes where the agent later found the right answer, mark the memory it eventually used as the "gold" record; test whether the reranker would have surfaced it earlier. Cheap, grounded in real outcomes; biased toward memories the OLD system could eventually find (survivorship — misses what was never found at all). Use (2) for iteration speed, (3) for grounding, (1) as the gate before shipping.

    Query routing

    Not every question should go to every index — "what did we decide yesterday?" wants episodic memory, "what's the API limit?" wants semantic facts, "how do I deploy?" wants the skill store, and "what's 2+2" wants nothing at all. Query routing is the dispatcher: classify the need, send it to the right store(s) with the right parameters, and skip retrieval when it would only add noise.

    Definition A router is a function $\rho(q, \text{state}) \to \{(\text{store}_i, \text{params}_i)\}$ choosing which indexes to query (possibly none, possibly several), with what reformulated query, filters, and $k$. Implementations: rule-based (patterns, metadata), a small classifier, or an LLM call ("which sources could answer this?"). Routing quality decomposes into recall (did it include a store containing the answer?) and precision (did it avoid flooding context from irrelevant stores?); the fallback design — what happens when the routed stores come up empty — matters as much as the primary choice.
    Worked example Cost-benefit of a router. Without routing, every step queries all 4 stores, k=5 each: 20 chunks ≈ 3,000 tokens injected per step; over 40 steps ≈ 120k tokens, mostly noise (measured: 70% of injected chunks unused). With an LLM router (1 cheap call, ~200 tokens): average 1.4 stores queried, 7 chunks ≈ 1,050 tokens per step, and — because context is cleaner — task success rises from 78% to 84% on the eval suite. The router pays for itself twice: fewer tokens, better attention. The catch: router recall was 0.96 — the remaining 4% of misroutes cluster on ambiguous queries, which is where the fallback ("if results look weak, broaden to all stores") earns its keep.
    Think first Should the router ever return "retrieve nothing"? What is the cost of getting that wrong in each direction?
    Reveal
    Yes — for self-contained requests (arithmetic, formatting, transformations of text already in context), retrieval injects distractors that measurably hurt (irrelevant context degrades LLM accuracy). Wrongly retrieving: token cost + attention pollution + risk the model parrots an irrelevant memory. Wrongly skipping: the agent answers from parametric knowledge — stale or hallucinated — when a correct record existed; usually the worse error for factual queries. Asymmetric stakes argue for a confidence-thresholded skip: retrieve unless clearly unnecessary, and let the reranker/context-assembler drop weak results.
    Drill
    1. EASY Route these: (a) "what port does staging redis use?" (b) "summarize what we tried this session" (c) "rotate the TLS cert like last quarter".
      Solution
      (a) semantic store (a fact). (b) working memory/transcript — no store lookup needed (it's all in the log). (c) procedural store for the skill, plus episodic for last quarter's execution record — a two-store route.
    2. MED A rule-based router hits 90% accuracy at ~0 cost; an LLM router hits 97% at 200 tokens + 300 ms per step. Frame the choice as expected value for (i) an interactive chat agent, (ii) a batch overnight agent.
      Solution
      Value of +7 points routing accuracy ≈ its effect on task success × task value; cost = latency (dear in chat) + tokens (dear at scale). (i) Interactive: 300 ms per step on every step is directly felt; if misroutes are recoverable by fallback, the cheap router + strong fallback often nets higher user value. (ii) Batch: latency is nearly free, token cost is marginal versus rerun costs of failed tasks — the LLM router's error reduction usually wins. General pattern: escalate — rules first, LLM router only when rules abstain or confidence is low, capturing most of the 7 points at a fraction of the cost (the VOC logic of Chapter 30 again).
    3. HARD Routing interacts with store design: as stores multiply (per-project, per-user, per-type), router error grows, but merged stores lose filtering precision. Model the trade-off and give the design that dominates both extremes.
      Solution
      Many stores: router must pick from $S$ options; misroute probability grows with $S$ (and with inter-store ambiguity), and each miss is catastrophic for recall (the answer's store wasn't searched). One mega-store: routing is trivial but every query competes against all content — precision falls, and cross-domain false neighbors (similar text, wrong project) pollute results; per-domain ranking calibration is lost. Dominating design: one physical store, logical routing by metadata filters — a single index with rich metadata (project, type, user, time), where the "router" emits a filter predicate rather than a store choice. Soft-routing becomes possible (search broadly, boost the predicted filter match), so router errors degrade gracefully (right answer still reachable at lower rank) instead of catastrophically. Recall failures become continuous, not binary — the same graceful-degradation principle as RRF.

    Context management

    The context window is the agent's whole perceptual field, and every step is a packing problem: system rules, task, plan, recent turns, tool outputs, retrieved memories — all compete for a fixed budget, and whatever loses is invisible to the model this step. Context management is the discipline of deciding, continuously, what the model gets to see.

    Definition Context management allocates the window budget $B$ across content classes each step: $\sum_c b_c \le B$, with per-class policies — pinned (system prompt, task, constraints: always present, top-of-context), rolling (recent turns: keep last $r$, summarize older — "compaction"), on-demand (retrieved memories, tool outputs: admitted by relevance, evicted when stale), and structural conventions (stable ordering, delimiters — also serving prompt-cache reuse, Chapter 23's KV cache: identical prefixes are billed/computed once). Compaction: when the transcript nears a threshold, replace older spans with an LLM-written summary that preserves decisions, open questions, and constraints.
    Worked example A compaction event. Budget 32k; transcript reaches 26k at step 33 (threshold 80%). Compactor summarizes steps 1–25 (19k tokens) into 1.2k: decisions made, files touched, failed approaches (kept verbatim: the two error messages that keep recurring), current plan state. New context: pinned 1.5k + summary 1.2k + steps 26–33 raw 7k = 9.7k — 22k tokens reclaimed. Cache accounting: the pinned prefix is byte-identical across steps, so with prompt caching only the delta is reprocessed; but the compaction itself rewrote the prefix → one full-cost step, then cheap steps resume. Scheduling compaction rarely-but-decisively (not every step) is both a quality and a cost policy.
    Explore

    Watch a context window fill over an agent's steps. Tool outputs arrive (spiky), the rolling window grows, and compaction fires at the threshold — trading transcript for summary. Tune the sizes.

    Pitfall Compaction is lossy exactly where agents are fragile: a summary that says "fixed the config issue" without the actual working config forces re-discovery when it breaks again; a dropped constraint ("user said never push to main") is a safety incident waiting. Compaction prompts must explicitly preserve: constraints, unresolved questions, exact artifacts (paths, commands, values) — and the raw log must remain retrievable outside the window.
    Drill
    1. EASY Budget 16k; pinned 2k; retrieved 1.5k; last tool output 3k. How many tokens remain for the rolling transcript?
      Solution
      $16 - 2 - 1.5 - 3 = 9.5$k tokens.
    2. MED Why does putting stable content first and volatile content last matter for both cost and quality?
      Solution
      Cost: prompt/KV caching works on longest common prefixes — a stable prefix (system, task, tool schemas) is computed once and reused every step; putting anything volatile early invalidates the cache for everything after it (Chapter 23). Quality: models attend most reliably to the beginning and end of context ("lost in the middle"); pinned rules at the very start and the current decision point at the very end places the two highest-stakes classes at the two highest-attention positions, with bulky reference material in the attention valley where degradation costs least.
    3. HARD Design the compaction summary spec for a coding agent as an explicit schema, and justify each field by the failure it prevents.
      Solution
      Schema: (1) goal + acceptance criteria (verbatim) — prevents goal drift as the original request scrolls away; (2) constraints/prohibitions (verbatim, never summarized) — prevents safety/scope violations whose cost is unbounded; (3) state of the world: files changed with one-line whats, commands that now work (exact strings) — prevents re-derivation and un-reproducible past successes; (4) failed approaches + why — prevents loops (the classic compaction failure: agent retries what a summarized-away step already disproved); (5) open questions/TODO stack — preserves the plan's frontier; (6) key identifiers (paths, ports, IDs, error signatures) verbatim — summaries paraphrase, but identifiers only work exactly. Meta-rule: anything that will be needed as an exact string is quoted, not described; anything decision-shaped is kept, and narrative is what gets dropped — a summary optimized for resuming action, not for reading.

    Memory compression

    Stores grow without bound; budgets don't. Memory compression shrinks what is kept — by summarizing, deduplicating, quantizing, and forgetting — while trying to preserve what future retrieval will need. It is rate-distortion theory (Chapter 16) wearing work clothes: minimize bits subject to keeping the memories' usefulness.

    Definition Memory compression operates at three layers: content (summarize records: 2,000-token episode → 150-token distilled lesson; merge near-duplicates into one record with a count), representation (embedding quantization: float32→int8→PQ codes, dimension truncation), and selection (forgetting: drop/archive records scoring below a retention utility $u(e) = f(\text{recency}, \text{frequency of use}, \text{outcome importance})$). The rate-distortion frame: choose what to keep to minimize expected future regret — the loss from a needed memory being absent or degraded — subject to a storage/token budget.
    Worked example Compression accounting. Store: 100k episodic records, avg 400 tokens (40M tokens; embeddings 100k × 768 × 4B = 307 MB). Pass 1 — dedup: 22% are near-duplicates (cosine > 0.95, same outcome) → merged, 78k records. Pass 2 — content: records older than 30 days and used ≥1 time get 80-token summaries (originals archived to cold storage): token store → 78k×(recent 400 / old 80 mix) ≈ 11M tokens. Pass 3 — representation: int8 embeddings → 60 MB. Retrieval quality check on a held-out query set: recall@10 drops 0.91 → 0.89 — two points paid for a 3.6× token and 5× embedding reduction. The check is the point: compression without a quality gate is just deletion with extra steps.
    Where this goes What compression must never destroy silently is provenance (next topic) — a summary that forgets where it came from can't be audited or corrected.
    Drill
    1. EASY 50k records at 300 tokens each are summarized 5:1 for the 60% that are old. New total tokens?
      Solution
      Recent: $20\text{k}\times300 = 6$M. Old: $30\text{k}\times60 = 1.8$M. Total 7.8M vs 15M — 48% reduction.
    2. MED Forgetting by "least recently used" is standard in caches. Why is pure LRU wrong for agent memory, and what utility function fixes it?
      Solution
      Cache LRU assumes recency of access predicts future access and that misses are cheap (refetch). Agent memories violate both: rare-but-critical records (the incident postmortem, the "never do X" lesson) are accessed rarely precisely because they matter only in rare states — LRU evicts exactly the high-regret items; and a miss is not a refetch, it's a repeated catastrophe. Fix: retention utility $u = \alpha\,\mathrm{recency} + \beta\,\mathrm{use\ frequency} + \gamma\,\mathrm{outcome\ severity} + \delta\,\mathrm{uniqueness}$ (no near-duplicates elsewhere in the store) — with severity and uniqueness dominating, and archival (drop from hot index, keep retrievable cold) instead of deletion so the worst case is latency, not loss.
    3. HARD Summarization-based compression changes the retrieval geometry: a summary's embedding differs from its source's. Describe the failure this causes and two architectures that avoid it.
      Solution
      Failure: queries matched the source's specific phrasing/details ("ECONNRESET during bulk upload"); the summary ("resolved a networking issue") embeds elsewhere — after compression the same query no longer retrieves the record: silent recall regression, invisible until the exact situation recurs. Architectures: (1) multi-vector records: keep the original's embedding(s) as retrieval keys pointing to the compressed content — retrieval geometry preserved, tokens compressed (decouple the key from the payload); (2) summary-plus-index terms: at compression time, extract and store the specific identifiers/error strings as searchable metadata alongside the summary (the sparse channel survives even if the dense one shifts). Both follow one principle: compress the payload, never the address.

    Memory provenance

    Every memory should carry its receipts: where it came from, when, through what transformations, and on whose authority. Provenance is what lets an agent distinguish "the user told me" from "I inferred it" from "a web page claimed it" — three very different reasons to believe — and it is the audit trail that makes memory correctable and safe.

    Definition Provenance metadata per record: $(\text{source type}, \text{source id}, \text{timestamp}, \text{derivation chain}, \text{authority/trust level})$. Source types with descending default trust: direct user statement > verified tool observation > agent inference > retrieved third-party content. Derivation chains record transformations: fact F ← consolidated-from episodes {E12, E17, E31} ← raw log spans. Uses: trust-weighted retrieval and conflict resolution, targeted invalidation (source retracted → cascade to descendants), dedup of common-origin "corroboration" (Chapter's consolidation quiz), and security triage (Chapter 32: content from untrusted sources must not silently become trusted instructions).
    Worked example Cascade invalidation. Store contains: F1 "deploy window is Friday 2pm" ← from E44 (user message, May); F2 "schedule releases before Friday 2pm" ← inferred from F1; skill S3 "release checklist" step 7 references F2. September: user says "we moved deploys to Tuesdays". Upsert touches F1 — and the derivation chain turns one edit into three: F1 updated (new value, new provenance), F2 flagged for re-derivation (its premise changed), S3 step 7 flagged for review. Without chains, F2 and S3 keep steering the agent to Fridays for months — stale derived beliefs are the hardest bugs to find because nothing about them looks wrong locally.
    Pitfall The most dangerous provenance failure is laundering: content from an untrusted source (a scraped page, a tool output containing adversarial text) gets consolidated into a bland semantic fact, losing its origin — and future retrievals present it with the store's implicit authority. Injection attacks on memory work exactly this way (Chapter 32). Rule: trust level is inherited through every transformation and never upgraded by rewriting.
    Drill
    1. EASY Rank default trust for: (a) output of ls the agent ran; (b) a sentence from a retrieved blog post; (c) the user's explicit correction.
      Solution
      (c) > (a) > (b). User statements are authoritative for their domain; own tool observations are reliable but interpretable; third-party retrieved text is unverified claims.
    2. MED Two conflicting facts: F_a from a user message 6 months ago; F_b inferred by the agent last week from indirect evidence. Which wins, and what should the agent actually do?
      Solution
      Neither auto-wins: the conflict pits authority (user > inference) against freshness (recent > stale), and the answer depends on whether the fact is user-owned (preferences: user statement stands until the user changes it — inference shouldn't override) or world-state (things drift: recent evidence matters). Correct behavior for consequential facts: surface the conflict — "You told me X in March; recent evidence suggests Y — which is current?" — converting a silent guess into a cheap clarification. Provenance is what makes this question askable: without it there are just two contradictory strings.
    3. HARD Design provenance for consolidation: fact F is distilled from 9 episodes. What must be stored to support (a) confidence calculation, (b) later invalidation, (c) audit, without keeping all 9 episodes in the hot store?
      Solution
      Store with F: (a) evidence summary: count of supporting episodes, number of independent root sources (after tracing chains — 9 episodes from 2 sources = 2), time span of observations, and any contradicting episodes seen (support 9 / oppose 1 is a different belief than 9/0) — enough to recompute confidence without the originals; (b) source pointers: the episode IDs and their root-source IDs (episodes archived cold, not deleted) so a retraction of any root can find F, and so F can list what would need re-checking; (c) derivation record: which consolidation run (version, prompt, date) produced F — so a discovered systematic consolidation bug can identify every fact it may have corrupted (recall-by-derivation), and so an auditor can pull the archived episodes and re-run the distillation. The pattern is exactly data lineage in data engineering: pointers and process metadata in the hot path, payloads in cold storage.

    Contradiction detection

    A memory store accumulates claims from different times and sources, and the world changes under it — so contradictions are not an anomaly but a steady state. Detecting them matters twice: unresolved conflicts make the agent incoherent (it acts on whichever version retrieval happens to surface), and detected conflicts are valuable signals — something changed, or some source is wrong.

    Definition Contradiction detection identifies pairs (or sets) of records that cannot all be true: at write time (check each new fact against retrieved near-neighbors before upserting) or by periodic sweep. Detection = candidate pairing (same subject/relation via embedding + metadata match) followed by a judgment: rule-based for structured slots (same key, different value), NLI-style entailment/contradiction classification for free text (Chapter 21's sentence-pair models: entail / neutral / contradict). Resolution policies: recency wins (for drifting world-state), authority wins (per provenance), keep-both-flagged (surface to the user), or scope-split (both true in different contexts — "port 8080 in dev" vs "port 80 in prod" is not a contradiction but a missing qualifier).
    Worked example Write-time check. Incoming fact: "the nightly job runs at 03:00 UTC" (source: today's cron output — high trust, fresh). Neighbor search on subject "nightly job" returns: N1 "nightly job runs at 01:00 UTC" (user message, 8 months); N2 "nightly job takes ~20 min" (observation). NLI: (new, N1) → contradict (same slot, different value); (new, N2) → neutral. Resolution: world-state slot + fresher + tool-observed → new value wins; N1 superseded (kept in history with pointer), and — because N1's provenance is a user statement — a low-priority note surfaces: "schedule changed from what you told me". N2 untouched. Cost: one embedding lookup + one small NLI/LLM call per write, the price of a coherent store.
    Think first Scope-splitting: "the API returns XML" and "the API returns JSON" — before resolving, what should a good detector ask?
    Reveal
    Whether a hidden qualifier makes both true: different endpoints? versions (v1 XML, v2 JSON)? Accept headers? times (it migrated)? The right move is often not to pick a winner but to refine both records with the qualifier ("v1: XML; v2: JSON") — apparent contradictions are how a store discovers its facts were underspecified. Only if the records are genuinely co-scoped does resolution by recency/authority apply.
    Drill
    1. EASY Classify each pair: (a) "Alice owns billing" / "Bob owns billing"; (b) "deploy takes 10 min" / "deploy takes 12 min"; (c) "use Python 3.11" / "Python 3.8 is EOL here".
      Solution
      (a) Contradiction (single-owner slot), unless scope-split (different services/time). (b) Compatible — noisy measurements of the same quantity; merge as a range or keep fresher. (c) Consistent — both can hold; no conflict.
    2. MED Why is write-time checking against near-neighbors incomplete, and what does the periodic sweep add?
      Solution
      Write-time only compares the newcomer to its top-k neighbors: contradictions with records phrased differently (embedding miss), or entailed indirectly through a chain (A→B, B conflicts with C, but A vs C look unrelated), escape. Also, both members of a conflicting pair may have been written before detection existed. The sweep does global work: cluster by subject/entity, cross-check within clusters, and follow derivation chains — catching phrasing-distant and transitive conflicts, at batch cost. Same split as consolidation: cheap local checks inline, expensive global coherence offline.
    3. HARD An agent's store says both "always run migrations before deploy" (procedural, from a postmortem) and "deploys are blocked while migrations run" (fact, from the platform docs). Not a logical contradiction — but a practical trap. What class of inconsistency is this, and how would a detector catch it?
      Solution
      It is a plan-level incoherence: individually true records whose joint application yields a deadlocked or contradictory procedure (run migrations first + deploys blocked during migrations ⇒ the naive combined plan stalls; resolution needs ordering detail: migrations complete, then deploy). Pairwise NLI won't flag it — neither statement contradicts the other; the conflict only appears when both are instantiated into one plan. Detection routes: (1) simulation/dry-run checking of procedures that cite both records (execute the combined checklist abstractly; a step whose precondition is negated by another step's effect = flag — STRIPS-style precondition analysis, Chapter 26); (2) at consolidation, when a procedure references facts, run a targeted LLM coherence check over the procedure + all cited facts jointly ("can these all be followed simultaneously? what ordering makes them consistent?"). The general lesson: consistency of a memory store is relative to use — stores feeding planners need plan-level checks, not just pairwise ones.

    8 ms from Oregon is physically incompatible with Frankfurt (~140+ ms) — the measurement entails a location contradicting the docs. World-state drifts and fresh direct observation beats stale documentation; but the store should record the supersession and flag it, since doc-vs-reality gaps often indicate wider staleness.

    Planner

    The planner is the component that turns a goal into a structure of steps before (and while) acting. It doesn't touch the world; it produces the artifact — a step list, a DAG, a strategy — that the rest of the agent executes, checks, and revises. Separating planning from doing is the oldest trick in both AI (Chapter 26) and management, and it works for the same reason in both.

    Definition A planner maps (goal, state, capabilities) → plan, where a plan is an ordered or partially-ordered set of steps with, ideally: per-step intent, required inputs, expected outputs, and success criteria. LLM planners generate plans as structured text; classical planners (Chapter 26: STRIPS, HTN) search over formal operators. Plan quality dimensions: soundness (steps achievable with available tools), completeness (steps suffice for the goal), granularity (steps sized to the executor's reliable stride), and testability (each step's success is checkable — the property that makes the critic/verifier loop possible).
    Worked example Two plans for "add rate limiting to the API". Plan A: 1. understand code 2. add rate limiting 3. test. Plan B: 1. locate middleware stack (out: file list) 2. pick limiter algorithm given the reqs — token bucket, 100/min (out: decision note) 3. implement middleware (out: diff; check: unit tests pass) 4. add config + env override (check: staging boots) 5. integration test burst behavior (check: 429 after 100 in 60 s) 6. update docs. Plan A is not a plan; it's the goal restated in three pieces — unfalsifiable steps, no artifacts. Plan B is executable and checkable: each step can fail visibly, which is what makes replanning (later) possible. The measurable difference: executors given B-style plans complete multi-file tasks at far higher rates because each step is within the model's reliable horizon.
    Where this goes The planner's output feeds the executor (next), gets audited by the critic/verifier, and — when reality disagrees — is revised by replanning. Formal planning is Chapter 26; multi-agent planners are Chapter 33.
    Drill
    1. EASY Rewrite the step "handle the database" (from a migration plan) into a testable step.
      Solution
      E.g.: "Write and run migration adding column retries INT DEFAULT 0 to jobs; success: migration applies cleanly on a staging copy and \d jobs shows the column; rollback script tested." Intent, artifact, and a binary check.
    2. MED Should the planner plan the whole task upfront or just the next few steps? Give the argument each way and the standard synthesis.
      Solution
      Full upfront: global coherence (later steps shape earlier choices — schema design should anticipate step 9), better cost estimation, reviewable before any action. But early steps' outcomes are unknown, so deep plans are built on guesses and rot fast (Chapter 29's compounding error, planning edition). Next-few-steps: always grounded in current reality, cheap to revise — but greedy/myopic, walking into corners a lookahead would avoid. Synthesis (hierarchical/receding-horizon, as in MPC Chapter 28): a stable high-level skeleton (phases, milestones — coarse enough to survive surprises) plus detailed planning only for the current phase, re-detailed as phases complete.
    3. HARD LLM planners exhibit a characteristic failure: fluent, confident plans containing steps the available tools cannot perform (calling APIs that don't exist, assuming permissions not held). Diagnose why, and give two structural fixes beyond "prompt it better".
      Solution
      Diagnosis: the model plans from its prior over how such tasks are typically done in training data, not from the actual capability set in context — plan plausibility is optimized, not plan soundness; nothing in free-text generation grounds each step against the real action space (the same ungrounded-generation failure as hallucination, manifested at the plan level). Fixes: (1) capability-grounded planning: require each step to name the specific tool + arguments from the provided schema list, and validate the plan mechanically against the schemas before execution (unparseable/unknown-tool steps bounce back) — moving soundness from the model's judgment to a checker (Chapter 32's validation, applied at plan time); (2) plan linting by dry-run: simulate the plan against a cheap model of the environment (or just precondition-check each step: does the file exist? is the permission held?) and return failures for revision before any real action — CEGIS for plans (Chapter 30). Both convert "trust the plan" into "verify the plan", which is the chapter's recurring move.

    Executor

    The executor takes one step of the plan and makes it real: choose the tool, fill the arguments, run it, read what came back, and produce the step's artifact. It is where the agent meets friction — timeouts, weird outputs, half-successes — and its virtue is not brilliance but reliability: do the step, notice whether it worked, report honestly.

    Definition An executor consumes a step spec (intent, inputs, success criteria) and produces (actions taken, artifacts, outcome ∈ {success, failure(reason), partial}, evidence). It owns the micro-loop within a step: try → observe → adjust → retry (bounded), and the boundary discipline: results are checked against the step's success criteria before being reported up — an executor that reports "done" without evidence poisons every layer above it. Separation of concerns: the executor does not re-decide the plan (that's replanning); it may only flag that the step as specified is impossible.
    Worked example Executing step 5 from the rate-limit plan ("integration test burst behavior; success: 429 after 100 requests in 60 s"). Attempt 1: burst script hits connection refused — executor micro-diagnoses (service not running), starts it (within its remit: making the step's precondition true), retries. Attempt 2: 100 requests → all 200 OK: the check FAILS. Executor's report: outcome = failure; evidence = "150 requests in 60 s all returned 200; limiter middleware present in code but config shows enabled: false in staging"; suggested cause attached. It does not silently flip the config (that changes system behavior beyond the step's scope) — it reports, and the planner/critic decides. The value is in the crisp failure with evidence: the fix becomes a one-step replan instead of an investigation.
    Pitfall The lethal executor bug is optimistic reporting: marking a step done because the tool call returned without error. Exit code 0 is not success — success is the step's criterion holding (the test asserting the behavior, the file containing the change). Every "it said it did it but it didn't" agent story traces to a missing evidence check at the executor boundary.
    Drill
    1. EASY A step says "delete stale branches; success: only main and develop remain". The executor runs the delete command, which exits 0. What must it do before reporting success?
      Solution
      Verify the postcondition independently: list branches and check the survivor set equals {main, develop}. Exit code 0 means the command ran, not that the state is right (protected branches, permission-skips and pattern mismatches all exit 0).
    2. MED Where is the line between executor-level retry/adjustment and escalation to replanning? Propose a rule.
      Solution
      Rule: the executor may vary how within the step's stated intent and scope (retry transient failures, fix its own syntax errors, satisfy local preconditions like starting a service), but must escalate anything that changes what — the step's outputs, other steps' assumptions, or system behavior outside the step (config semantics, data, permissions). Plus a budget line: after $n$ failed attempts or when failures aren't changing character, stop — repeated identical retries signal a wrong plan, not bad luck. The test: "would the planner have written a different plan had it known this?" — if yes, it must find out.
    3. HARD Executors can be humans, scripts, LLM calls, or sub-agents. For the step "update 40 call sites to the new API signature", compare a scripted executor (codemod) vs an LLM executor per-file, on reliability, cost, and failure legibility — and design the hybrid.
      Solution
      Codemod: deterministic, near-zero marginal cost, uniform — but brittle to variation (the 3 call sites with unusual patterns are silently mangled or missed), and its failures are illegible (a wrong transform looks like a right one). LLM per-file: handles variation and context (renames a local variable that would now shadow), ~40 calls of cost, but nondeterministic — may "improve" unrelated code, and reliability per file < 1 compounds over 40. Hybrid: codemod for the mechanically-matchable majority (grep/AST match determines applicability), LLM only for the residue the matcher rejects, and a uniform verifier over all 40 (typecheck + tests + diff review that flags any change outside the signature migration). Route by matchability, verify uniformly — determinism where possible, judgment where necessary, evidence everywhere.

    Critic

    The critic reads work and finds what's wrong with it — before the world does. It sits between "done" and "shipped": reviewing plans for holes, diffs for bugs, answers for errors, and its economics are the generator-verifier asymmetry of Chapter 30: judging is easier than producing, so a modest critic can catch a strong generator's mistakes.

    Definition A critic maps an artifact (+ its intent/spec) → structured findings: {issue, location, severity, suggested fix}, without executing anything (contrast the verifier, next, which runs checks). Implementations: the same LLM in a review role (works because generation and review sample different failure modes — review conditions on the completed artifact, catching what stepwise generation's local decisions missed), a different model, or specialized critics per aspect (correctness, security, style). Effectiveness demands independence: a critic shown the generator's reasoning inherits its framing; a critic that reads only the artifact + spec judges fresh.
    Worked example Critique economics. Generator produces diffs with a 12% serious-bug rate. Critic pass (one LLM review call, ~1/5 the generation cost): catches 70% of serious bugs with a 10% false-alarm rate; each finding triggers a regeneration (full cost) that fixes it with probability 0.9. Bug rate after one critique round: survivors $= 12\%\times0.3 = 3.6\%$; plus caught-but-unfixed $12\%\times0.7\times0.1 = 0.84\%$ → ≈ 4.4%, at expected cost $1 + 0.2 + (0.12\times0.7 + 0.88\times0.1)\times1.2 \approx 1.4\times$ baseline. A 63% bug reduction for 40% more cost — and a second round takes 4.4% → ~1.8%. Diminishing returns set in exactly where the critic's blind spots overlap the generator's (the shared-bias residue no amount of self-review removes — Chapter 30's correlated-errors ceiling).
    Think first Same model as generator and critic: why does this help at all, and where does it stop helping?
    Reveal
    Helps because the two roles condition differently: generation makes thousands of local, greedy decisions under its own momentum; review sees the finished whole against the spec, a different computation that surfaces inconsistencies, omissions, and spec violations the stream missed (also: sampling noise — a slip is not stable under re-examination). Stops at shared systematics: wrong beliefs (the model thinks the API works that way), shared blind spots (it never considers timezone bugs), and self-preference (rating its own style as fine). Those need a different model, a tool (verifier), or a human — independence is the resource, and self-critique has a hard ceiling of it.
    Drill
    1. EASY Distinguish critic from verifier on the artifact "a SQL migration script".
      Solution
      Critic: reads it — "no index on the new FK column; DROP without a backup step; will lock the table during peak". Verifier: runs it — applies to a staging copy, measures lock time, runs the test suite. Judgment vs execution; the critic finds issues execution wouldn't surface (missing backup step) and vice versa (actual lock duration).
    2. MED Critic findings have a false-positive cost too. With 10% false-alarm rate per artifact and a policy of always regenerating on findings, what pathologies appear, and what triage policy fixes them?
      Solution
      Pathologies: (1) churn — correct artifacts get regenerated, each regeneration a fresh chance to introduce a real bug (you can end WORSE than no critic if FP-triggered rewrites inject bugs at a higher rate than the critique removes them); (2) drift — repeated rewrite cycles chase style nits, burning budget; (3) alarm fatigue in human-review pipelines. Triage: severity-gate actions (regenerate only on high-severity findings; log low ones), require the critic to cite concrete evidence (location + why it fails, suppressing vibes-based findings), verify-before-rewrite where cheap (let the verifier confirm the alleged bug — a failing test reproduces it), and cap critique rounds (two, usually).
    3. HARD You can spend one extra inference on either (a) a second independent generation + pick-best, or (b) one generation + one critique-and-fix round. Using generator accuracy p = 0.7, critic catch rate 0.7 / false-alarm 0.1, fix success 0.9, and a selector that picks a correct artifact from a pair containing one with probability 0.85 — which wins?
      Solution
      (a) Two generations: both correct $0.49$ (pick correct: 1); exactly one correct $2\times0.7\times0.3 = 0.42$ (pick correct: 0.85); none $0.09$. Success $= 0.49 + 0.42\times0.85 = 0.847$. (b) Generate (0.7 correct). If correct: critic false-alarms 0.1 → rewrite, assume rewrite is fresh draw at 0.7... compute: correct path: $0.7\times[0.9 + 0.1\times0.7] = 0.7\times0.97 = 0.679$. Incorrect path (0.3): caught 0.7 → fix succeeds 0.9: $0.3\times0.7\times0.9 = 0.189$. Total $= 0.679 + 0.189 = 0.868$. (b) edges out (a): 0.868 vs 0.847 — targeted repair beats blind resampling at these parameters because the critic converts information about where the failure is into a high-probability fix, while pick-best pays the selector's error on every discordant pair. Flip the parameters (weak critic, strong selector — e.g. an executable test as selector: 1.0) and (a) wins: with a perfect selector, success $= 1 - 0.3^2 = 0.91$. The general rule: verifiable selection favors sampling; unverifiable domains favor critique.

    Verifier

    The verifier doesn't read the work and form an opinion — it runs a check whose outcome the work cannot argue with: the tests pass or they don't, the schema validates or it doesn't, the proof checks or it doesn't. Wherever a verifiable surface exists, the verifier converts "probably fine" into a fact, and agent architectures are largely exercises in maximizing verified surface.

    Definition A verifier is a procedure $V(\text{artifact}, \text{spec}) \to \{\text{pass}, \text{fail}(\text{evidence})\}$ whose verdict is determined by execution or formal checking, not judgment: test suites, type checkers, schema/contract validation, property-based tests, proof checkers (Chapter 34), simulation/dry runs, cross-computation consistency (recompute by a different route, compare). Two axes classify quality: soundness of failure (a fail is really a fail — flaky tests break this) and coverage (what fraction of wrongness the check can see: passing tests bounds error only over tested behavior — Chapter 30's random-testing bound). The agent-design consequence: a verified step's reliability is the verifier's, not the model's — so route work through verifiable forms (code over prose, schemas over free text) whenever possible.
    Worked example Verified vs unverified pipeline. Task: produce a data transformation. Route A (prose spec → LLM writes the output file directly): correctness ≈ the model's per-task accuracy, say 0.8, and errors are silent. Route B (LLM writes a transformation script + 6 property checks — row counts conserved, no nulls in key columns, totals match input within ε, spot-check 5 known rows): the script runs or fails loudly; checks catch, say, 85% of wrong-output cases. Residual silent-error rate: A = 20%; B $= 0.2\times0.15 = 3\%$ — a 6.7× reduction not from a better model but from re-routing the same competence through a checkable form. Bonus: B's failures carry evidence (which check failed), feeding targeted repair.
    Where this goes Verifiers are the trust anchors of Chapter 32 (output validation) and the whole subject of Chapter 34; process vs outcome verification trade-offs are Chapter 30's.
    Drill
    1. EASY Which are verifiers vs critics: (a) mypy on the diff; (b) "review this diff for concurrency issues"; (c) replaying a recorded request against the new build and diffing responses.
      Solution
      (a) verifier (mechanical check); (b) critic (judgment); (c) verifier (executed comparison).
    2. MED A test suite passes. Enumerate three distinct reasons the artifact can still be wrong, mapping each to a verifier-improvement.
      Solution
      (1) Coverage gap: the bug lives in untested behavior → add property-based/fuzz tests, coverage-guided test generation. (2) Spec gap: tests encode the wrong expectation (the agent wrote tests asserting its own misunderstanding — the self-referential trap) → tests reviewed independently of the implementation, or derived from the original spec/examples the user provided. (3) Environment gap: passes in the test env, fails in prod (config, data scale, timing) → staging runs on realistic data, contract tests against real dependencies. "Verified" is always relative to a check-set; the check-set is the real spec.
    3. HARD An agent generates both the code and its tests. Analyze the failure mode, and design a protocol that restores most of the verification value without human-written tests.
      Solution
      Failure: shared misunderstanding — if the agent misreads the requirement ("sort descending"), it writes code AND tests embodying the same error; the green suite verifies internal consistency, not correctness (the verifier's independence assumption is violated at the spec level). Protocol: (1) derive tests from a different information source than the implementation: the user's literal examples/acceptance criteria become executable fixtures verbatim (not paraphrased by the model); (2) sequence commitment: write tests FIRST from the spec, get them confirmed (by the user, or by checking them against provided examples), freeze them, then implement — the implementation can no longer bend the tests toward itself; (3) adversarial split: separate "tester" pass prompted to break the implementation (property-based generation, edge-case hunting), scored by bugs found — decorrelating errors by role (Chapter 33's debate, in miniature); (4) metamorphic testing where no oracle exists: check invariants that need no ground truth (sort twice = sort once; f(reverse(x)) relates to f(x) predictably). Each recovers independence from a different direction: source, time, incentive, and structure.
    An agent's code change passes the full test suite it also wrote in the same session. The strongest remaining doubt is:
    When one mind (one context) writes both artifact and check, spec-level errors are correlated: the same misunderstanding shapes both, and green means "self-consistent". Independence of the check's origin — user-provided examples, frozen pre-implementation tests, a second agent — is what restores verification value.

    Supervisor

    Above the planner, executor, critic and verifier sits the supervisor: the control loop's control loop. It doesn't do the work or check the artifact — it watches the process: is the agent looping? over budget? stuck? off-goal? drifting into territory that needs a human? The supervisor's tools are budgets, circuit breakers, escalation, and the authority to stop.

    Definition A supervisor monitors execution streams against policy: progress (is state advancing, or cycling? — e.g. repeated similar actions with similar failures), budgets (tokens, time, steps, spend — Chapter 32 formalizes these), scope (are actions within the task's declared surface: files, systems, permissions?), and risk triggers (destructive operations, external side effects → require approval, Chapter 32's human-in-the-loop). Interventions, escalating: annotate (inject guidance into the loop's context), redirect (force replanning), pause-and-ask (escalate to human), kill. Implementation ranges from pure rules (cheap, predictable) to an LLM monitor reading the transcript (catches semantic drift rules can't see) — usually layered.
    Worked example Loop detection catch. Transcript: step 21 — edit config, run tests, 3 fail; step 24 — edit same config differently, same 3 fail; step 27 — revert, re-edit, same 3 fail. Rule layer sees: same test-failure signature 3× within 8 steps → trigger. Supervisor injects an annotation: "You have attempted config changes 3 times against the same failing tests. The failure may not be config-related. Re-read the test output and form a different hypothesis before the next edit." Step 28: agent re-reads, notices the tests reference a fixture file it never looked at, finds the real bug. Cost of supervision: one regex-ish monitor + one injected paragraph. Without it: agents demonstrably grind identical failure loops for dozens of steps — the local context each step makes the same next action look reasonable; only a process-level view sees the circle.
    Pitfall A supervisor with the same blind spots as the worker supervises nothing: an LLM monitor instantiated from the same context tends to share the worker's framing ("yes, another config edit seems reasonable"). Keep the supervisor's view different — summaries of action/outcome patterns rather than the full narrative, different prompt, ideally different incentives ("your job is to find reasons to stop") — independence again, one level up.
    Drill
    1. EASY Which intervention fits each: (a) agent at 92% of token budget, mid-task; (b) agent about to run DROP TABLE on prod; (c) agent's last 6 steps show no file changes and repeating searches.
      Solution
      (a) annotate ("budget nearly exhausted: wrap up — commit progress, summarize remaining work") and prepare graceful stop; (b) pause-and-ask — hard approval gate on destructive scope; (c) annotate/redirect — name the stall, force a replan or a different information-gathering action.
    2. MED Why should the supervisor's stop authority be mechanical (outside the LLM loop) rather than another prompt the worker sees?
      Solution
      Anything that acts only through the worker's context is advisory: the worker can misread, deprioritize, or (under adversarial injection, Chapter 32) be steered to ignore it — and a runaway loop is precisely the state in which context-following is already broken. Budgets, kill switches and permission gates must bind at the harness level (the code running the loop), where no token sequence can override them: enforcement in the substrate, guidance in the context. Same principle as Chapter 34's runtime monitors and safety shields.
    3. HARD Design progress metrics for a supervisor overseeing a long coding task, robust to the fact that legitimate work sometimes looks stalled (reading, thinking) and illegitimate churn sometimes looks busy (many edits).
      Solution
      Use outcome-anchored, not activity-anchored, metrics: (1) verifier trajectory — failing-test count / error count over time: genuine progress usually moves it (down, or up-then-down when refactoring); flat across many edits = churn signal. (2) State novelty — hash/embed the (files-changed, error-signature) pairs: revisiting previously-seen states repeatedly = looping even if each visit "looks busy"; long reads that then produce a novel state = legitimate. (3) Frontier movement — plan-step completion with evidence (executor reports), weighted by verification: steps closing with verified artifacts vs steps reopening. (4) Budget-normalized: all of the above per token/time spent, with task-size-relative thresholds. Combine as: alarm when novelty AND verifier trajectory are both flat over a window, regardless of activity volume; never alarm on low activity alone. And log supervisor alarms as training data — thresholds are learnable from which alarms preceded genuine stalls.

    Planner-executor loops

    Wire the planner and executor into a cycle and you get the workhorse architecture of practical agents: plan, execute a step, observe, update the plan, repeat. The loop's rhythm — how often planning re-engages — spans a spectrum from plan-once (rigid, cheap) to plan-every-step (adaptive, expensive), and choosing the rhythm is choosing what kinds of surprise the agent can absorb.

    Definition A planner-executor loop alternates: $P$: (goal, state, plan$_{t}$, feedback) → plan$_{t+1}$; $E$: (next step of plan$_{t+1}$) → (outcome, evidence); with feedback flowing back to $P$. Regimes: open-loop (plan once, execute all — valid only when the environment is predictable and steps can't fail informatively); interleaved (re-plan on triggers: step failure, surprising observation, milestone — the practical default); receding-horizon (re-plan every step over a short lookahead — MPC from Chapter 28, maximally adaptive, maximally costly). The division of labor is cognitive: planning is slow/global/expensive, execution is fast/local/cheap — the loop is how a system affords both.
    Worked example Rhythm arithmetic. Task: 12 steps. Planning call: 2k tokens; execution step: 1k. Open-loop: $2 + 12 = 14$k tokens — but a failure at step 4 invalidates steps 5–12 silently; measured completion 55%. Re-plan-every-step: $12\times2 + 12 = 36$k, completion 88%. Trigger-based (re-plan only on failure/surprise, ~3 events): $2 + 3\times2 + 12 = 20$k, completion 85%. Trigger-based buys ~94% of the adaptive gain at ~55% of the cost — the general shape: surprises are sparse, so condition planning on them rather than on the clock.
    Where this goes ReAct (next) collapses this loop into a single prompt pattern; replanning (two on) is the P-side discipline; Chapter 33 distributes P and E across different agents.
    Drill
    1. EASY Match regime to task: (a) migrate 500 identical records; (b) debug an unknown flaky test; (c) book a trip with fixed constraints.
      Solution
      (a) open-loop (predictable, uniform steps; add a verifier per batch); (b) receding-horizon/every-step (each observation reshapes the hypothesis); (c) interleaved (plan the itinerary once, re-plan on sold-out/price surprises).
    2. MED What information must the executor's feedback contain for re-planning to be better than re-planning from scratch?
      Solution
      Delta-relevant state: which step failed and how (error class, evidence), what side effects already happened (irreversible actions constrain the new plan — you can't re-choose a sent email), what was learned about the environment (the API is v2, the file moved), and which completed artifacts remain valid. Without these the planner either redoes work (ignoring sunk progress) or builds on falsified assumptions. The feedback is the plan's diff against reality — replanning is patching, not rewriting, when the feedback supports it.
    3. HARD Interleaved loops can thrash: replan triggers fire, the new plan hits a different surprise, triggers again — oscillating between plans without progress. Diagnose the underlying cause and give two stabilizers, one from control theory, one from the memory sections.
      Solution
      Cause: the planner responds to each surprise locally without accumulating a model of WHY plans keep failing — each replan optimizes against the latest observation only, like a controller with high gain and no integral term chasing noise (and like value-less greedy search re-expanding the same nodes). Stabilizer 1 (control): hysteresis and damping — require surprises to exceed a threshold before replanning (deadband), keep plan changes minimal (penalize plan distance from the current plan, the trust-region idea from Chapter 15/25: small steps in plan space), and rate-limit replans. Stabilizer 2 (memory): feed the failure history into planning — an episodic record "plans A, B failed for reasons r_A, r_B" forces the planner to address the accumulated constraint set rather than resample plausible plans that ignore it (the same mechanism as reflection, next topic, and the supervisor's loop-detection one level down).

    ReAct

    ReAct (Reason + Act) is the pattern that made LLM agents practical: interleave free-text reasoning ("Thought: ...") with tool calls ("Action: ...") and their results ("Observation: ...") in one running transcript. The thought stream plans, interprets and adapts; the actions ground it in reality — each fixes the other's weakness.

    Definition ReAct structures the loop's transcript as repeating triples: Thought$_t$ (reasoning about state and what to do next) → Action$_t$ (a tool call with arguments) → Observation$_t$ (the tool's result, appended verbatim), until a final answer action. Against its ablations: act-only (no thoughts) loses adaptive interpretation — the model chains tool calls without diagnosing surprising results; reason-only (no actions, i.e. plain CoT) loses grounding — facts come from the model's parametric memory, hallucination included. The original result (Yao et al.): ReAct beats both ablations on knowledge tasks (HotpotQA) and interactive tasks (ALFWorld, WebShop), and the thought trace doubles as an interpretable log.
    Worked example One ReAct cycle from a real shape of task. Thought: "The user asks when the Golden Gate Bridge opened relative to the Bay Bridge. I know roughly, but should verify both dates." Action: search("Golden Gate Bridge opening date"). Observation: "...opened May 27, 1937." Thought: "Now the Bay Bridge." Action: search("San Francisco–Oakland Bay Bridge opening date"). Observation: "...opened November 12, 1936." Thought: "Bay Bridge opened ~6 months earlier. Compute: Nov 12 1936 → May 27 1937 is 196 days." Action: finish("The Bay Bridge opened first — November 12, 1936, about six and a half months (196 days) before the Golden Gate Bridge's May 27, 1937 opening."). The act-only ablation gets the dates but botches the comparison reasoning; reason-only confidently misremembers a date. The interleaving is the point: every claim that can be grounded was grounded, every observation got interpreted before the next move.
    Pitfall ReAct's thought stream is not privileged truth — it is generated text, subject to confabulation like any other: agents produce thoughts that misdescribe the observation just received, or rationalize an action the pattern-completion already committed to. Downstream components (critics, supervisors) should trust Observations (ground truth from tools) over Thoughts (the model's running commentary), and the gap between them is a diagnostic goldmine.
    Drill
    1. EASY Label each transcript line as Thought, Action, or Observation: (a) "404: page not found"; (b) "The endpoint moved — try the v2 path"; (c) http_get("/api/v2/users").
      Solution
      (a) Observation (tool result); (b) Thought (interpretation + intention); (c) Action (tool call).
    2. MED Why does forcing a Thought before every Action measurably change WHICH action gets taken, given the model could "think silently" in its activations?
      Solution
      Autoregressive computation is serial and shallow per token: emitting reasoning tokens gives the model extra sequential computation steps whose intermediate results are written into context and attended to — effectively extending its computational depth (the CoT mechanism, Chapter 30). The action tokens are then conditioned on the explicit analysis rather than on a single forward pass's implicit guess; empirically this shifts action distributions toward the reasoned choice, especially after surprising observations where the "reflex" continuation and the analyzed continuation diverge. The thought is scaffolding for computation, not just narration — though (see pitfall) not always faithful narration.
    3. HARD ReAct puts everything — thoughts, actions, raw observations — into one linear context. Identify three scaling failures of this design at long horizons and name the architecture from this chapter that addresses each.
      Solution
      (1) Context exhaustion: observations (tool dumps) flood the window; old triples scroll away or blow the budget → context management/compaction (summarize old triples, truncate observations at the boundary). (2) No structure over subtasks: the flat stream can't represent parallel branches or a task hierarchy — step 40 can't cleanly reference "subtask B's result" → task decomposition + DAG execution (below), with per-subtask contexts and a structured results ledger instead of one scroll. (3) Everything is equally trusted and equally forgettable: injected text in an observation sits in the same stream as system guidance (security), and the crucial early constraint has no privileged persistence → provenance-aware context assembly (pinned constraints, trust-tagged spans — Chapter 32 hardening). ReAct is the right inner loop; at scale it becomes one component inside these outer structures.

    Reflection

    Reflection is the agent stepping out of the doing loop to ask: how did that go, and what should I do differently? After a failure (or a success), a reflection pass reads the trajectory, names what went wrong or right, and writes the lesson where the next attempt will see it. It is learning without gradient updates — the "weights" that change are the agent's memory and prompts.

    Definition Reflection (Reflexion-style): after an episode with outcome signal, generate a verbal analysis $\ell = R(\text{trajectory}, \text{outcome})$ — cause of failure, what to try instead — and store it (episodic/semantic memory, or the next attempt's context). The next trial conditions on $\{\ell_i\}$: $\pi(a\mid x, \ell_{1:k})$. It is policy improvement in language space: the outcome signal (often just success/fail) is converted by the model's own credit assignment into a targeted behavioral delta — far more sample-efficient than RL's gradient from the same one bit, when the model's causal analysis is right. Empirical anchor: Reflexion lifted GPT-4 HumanEval pass@1 from ~80% to ~91% by iterating code attempts against test feedback with verbal self-corrections.
    Worked example Three-trial arc. Trial 1: agent's web task fails — it searched, clicked the first result, extracted a stale price. Outcome: wrong answer. Reflection: "Failure cause: trusted the first search result; the page was a 2019 archive. Lesson: check page dates; prefer official sources; cross-check prices across two sources." Trial 2 (lesson in context): agent checks dates, cross-checks — fails differently (both sources paywalled, agent gave up). Reflection 2: "Paywalls blocked both; lesson: the manufacturer's site lists MSRP openly." Trial 3: succeeds. The one-bit outcome signal became two specific, reusable behavioral rules — and rule 1 ("check dates, cross-check") transfers to every future retrieval task, not just this one: reflection's lessons generalize exactly as far as the verbal abstraction does.
    Think first Reflection's credit assignment is the model blaming its own trajectory. When is this analysis systematically wrong, and what anchors it?
    Reveal
    Wrong when the true cause is outside the model's view (environment flakiness — the API was down; the test itself is broken) or outside its self-model (it doesn't know its own systematic biases): it then invents plausible-but-false causes and writes confident bad lessons, which persist and misdirect future attempts — memory makes both good and bad lessons durable. Anchors: ground reflections in evidence (require citing the specific observation that indicates the cause), verify lessons when cheap (if the lesson says "the endpoint needs auth", test that directly), track lesson outcomes (a lesson followed by repeated failure gets down-weighted — close the loop), and distinguish "hypothesis" from "verified cause" in what gets stored (provenance for lessons).
    Drill
    1. EASY Turn this bad reflection into a good one: "I failed because the task was hard. Lesson: try harder."
      Solution
      Specific cause + falsifiable behavioral rule, e.g.: "Failed because I edited config.yaml without checking which config file the service actually loads (it loads config.prod.yaml). Lesson: before editing config, run the service's config-dump command to identify the live file." Names evidence, names the change, and is testable next time.
    2. MED Compare reflection to RL fine-tuning on the same episodes, on: sample efficiency, transfer, persistence, and failure risk.
      Solution
      Sample efficiency: reflection extracts a rich verbal delta from one episode (RL gets one noisy gradient nudge) — orders of magnitude better when the self-analysis is correct. Transfer: verbal lessons transfer across tasks sharing the abstraction, and across agents (text is portable); RL updates transfer only through the weights' generalization. Persistence: lessons persist only while retrieved/in-context (and consume budget); RL persists in weights for free. Failure risk: a wrong lesson is inspectable and deletable; a wrong gradient is invisible inside weights — but reflection can also be confidently wrong at scale (bad lessons compound via memory), and it can't improve what language can't express (subtle perceptual-motor calibration). They compose: reflections as the fast loop, periodic distillation of validated lessons into fine-tuning as the slow loop — memory consolidation into weights.
    3. HARD Design reflection for SUCCESSES, not just failures: what should be extracted, and why is naive success-reflection ("do that again") actively risky?
      Solution
      Extract: (1) which decisions were load-bearing vs incidental — via counterfactual probing ("would it have worked without step 5?"), else the lesson enshrines superstition (the agent ritualizes incidental steps — cargo cult); (2) preconditions of the success — what about the environment made this work (version, permissions, data shape), so the skill (procedural memory) carries applicability conditions and doesn't misfire elsewhere; (3) efficiency deltas — which detours were wasted, so the distilled procedure is the clean path, not the historical one; (4) near-misses — what almost failed (flaky step that passed on retry) as future risk flags. Naive risk: success is weaker evidence than failure (many paths succeed by luck; one success doesn't validate each step — survivorship bias), and "repeat exactly" freezes exploration precisely where the agent is already competent, while its preconditions silently rot (stale procedures, from the procedural-memory pitfall). Success-lessons need MORE verification than failure-lessons, because failures self-correct on the next attempt and bad habits don't.

    Replanning

    Plans are hypotheses, and reality reviews them. Replanning is the discipline of revising a plan mid-flight when evidence arrives — a step failed, a discovery changed the problem, a constraint appeared — while preserving what remains valid: completed work, standing constraints, and lessons from the failure that triggered the revision.

    Definition Replanning maps (plan, execution state, trigger evidence) → plan′, under conservation rules: completed steps' artifacts are facts; irreversible actions constrain (can't unsend); untouched valid steps carry over; invalidated steps (their preconditions or purpose falsified) are rebuilt. Triggers: step failure after executor retries, precondition discovered false, new information changing the goal's shape, budget pressure (re-scope to fit), or supervisor redirect. The minimal-change principle: prefer the smallest plan edit consistent with the evidence — full replans discard context, invite thrash, and re-litigate settled decisions.
    Worked example Surgical vs full replan. Plan: 8 steps to add a feature; steps 1–4 done (schema migrated, API added). Step 5 fails: the frontend framework version doesn't support the intended component. Full replan from scratch risks: re-deciding the schema (steps 1–2's settled choices reopened — maybe differently, orphaning the migration), losing the step-5 failure evidence.     Task decomposition

    Big tasks fail as wholes and succeed as parts. Decomposition splits a goal into subtasks each small enough to execute reliably, specified tightly enough to check, and independent enough to survive a sibling's failure. It is the multiplier on everything else in this chapter: memory, planning, verification and parallelism all work at the granularity decomposition chooses.

    Definition A decomposition of task $T$ is a set of subtasks $\{t_i\}$ with a dependency relation, such that completing all $t_i$ (respecting dependencies) achieves $T$. Quality criteria: coverage (the union really is $T$ — no orphan requirements), minimal coupling (few, explicit interfaces between subtasks: what $t_j$ needs from $t_i$ is a named artifact, not shared mutable context), right-sizing (each $t_i$ within the executor's reliable horizon — the step-count at which its success rate stays high), and checkability (per-subtask acceptance criteria). The reliability argument: a monolithic 40-step execution at per-step 0.98 completes with $0.98^{40}\approx0.45$; decomposed into 8 subtasks of 5 steps, each independently verified and retried once on failure, each subtask succeeds with $s = 0.98^5 \approx 0.904$, retried: $1-(1-s)^2 \approx 0.991$, total $0.991^8 \approx 0.93$. Decomposition + verification + retry converts compounding failure into containable failure.
    Worked example Decomposing "build a CLI that syncs a local folder to S3". Subtasks: (1) config/arg parsing — out: parsed options struct; check: unit tests on 6 arg combos. (2) local scanner — out: file manifest with hashes; check: golden test on fixture dir. (3) remote lister — out: S3 manifest; check: mocked-API test. (4) diff engine — in: two manifests; out: upload/delete sets; check: property test (diff of identical manifests is empty; diff is inverse-symmetric). (5) transfer executor — in: diff; check: integration test against localstack. (6) wiring + end-to-end — check: full sync on fixture, idempotency (second run = no-ops). Interfaces are data (manifests, diff sets) — subtask 4 can be built and verified before 3 exists (feed it fixtures). Coupling audit: no subtask reads another's internals; the one global (S3 client config) flows through 1's artifact. This shape is what makes the DAG execution of the next topic possible.
    Pitfall The seductive wrong decomposition is by phase ("1. research 2. design 3. implement 4. test") — phases aren't independently checkable ("research" has no acceptance test), can't be parallelized, and defer all verification to the end, where errors are most expensive. Decompose by deliverable component with per-component checks; let each component internally have its mini-phases.

The shape is general: overhead pushes toward bigger subtasks, superlinear per-step decay pushes toward smaller; the optimum sits where marginal overhead equals marginal failure cost, and reliability-critical tasks should size below the step-optimal point.

    DAG task execution

    Once a task is decomposed with dependencies, it is a directed acyclic graph — and executing it well is a scheduling problem Chapter 17 already gave us the tools for: topological order for correctness, critical path for the speed limit, and parallel workers for everything off it.

    Definition A task DAG has nodes = subtasks (with duration/cost estimates) and edges $t_i \to t_j$ = "$j$ needs $i$'s artifact". Execution: repeatedly run any node whose dependencies are all complete (a topological traversal, Chapter 17); with unlimited parallel workers, the makespan equals the critical path — the longest duration-weighted path through the DAG: $\mathrm{CP} = \max_{\text{paths } P}\sum_{t\in P} d_t$; total work is $\sum_t d_t$, and the maximum useful parallelism is work/CP. Failure semantics: a failed node blocks only its descendants; independent branches continue — plus retry/replan localized to the failed subtree. Scheduling with $w$ workers: makespan $\ge \max(\mathrm{CP}, \text{work}/w)$; list scheduling (greedy: run any ready task) achieves within 2× of optimal (Graham's bound).
    Worked example The S3-sync DAG from the last topic, durations in agent-minutes: config(4); scanner(8) needs config; lister(8) needs config; diff(6) needs scanner+lister; transfer(10) needs diff; wiring(5) needs transfer. Also docs(6) needs config only. Critical path: config→scanner/lister(8)→diff→transfer→wiring $= 4+8+6+10+5 = 33$. Total work $= 4+8+8+6+10+5+6 = 47$. One worker: 47 min. Two workers: scanner ∥ lister overlap (save 8), docs ∥ anything (save 6) → 33 min = CP, achieved. Max useful parallelism $= 47/33 \approx 1.42$ — a third worker buys nothing. If transfer fails, docs and everything upstream stand; the replan touches only {transfer, wiring}.

    2. MED Why should an agent framework require subtask artifacts to be explicitly declared (typed outputs) rather than letting subtasks communicate through a shared workspace?
      Solution
      Declared artifacts make the edges REAL: the scheduler knows exactly when a dependent may start (its inputs exist and validate), failures are attributable (which artifact is missing/malformed), caching works (unchanged inputs → skip recompute, like build systems), and hidden dependencies can't form. A shared workspace creates undeclared edges — task B quietly reads a file A wrote — so parallel execution races, reordering breaks things "randomly", and the DAG the scheduler sees is a fiction.     3. HARD Subtask durations are LLM-estimated and noisy. The critical path computed from estimates can differ from the realized one. Why does this matter for worker allocation, and what's the robust scheduling policy?
      Solution
      Allocation tuned to the estimated CP starves branches that turn out critical: if a "short" off-path task balloons (heavy-tailed durations are the norm for agent subtasks — a retry loop triples a task), the realized CP shifts and workers idle on the formerly-critical branch. Expected makespan under noise exceeds the makespan of expected durations (Jensen: max of sums is convex), so deterministic planning is systematically optimistic. Robust policy: (1) don't pre-assign — use greedy list scheduling on READY tasks (allocation self-corrects as reality unfolds; Graham's 2× bound holds regardless of estimate quality); (2) prioritize ready tasks by estimated remaining critical path THROUGH them (longest-processing-time flavored heuristics), updating estimates from realized durations; (3) hedge the high-variance nodes: start likely-critical, high-uncertainty tasks earliest, and consider speculative duplication (run two approaches to a risky subtask in parallel, keep the first verified result) when workers would otherwise idle — spending cheap parallelism to buy makespan variance reduction.

    Workflow orchestration

    Orchestration is the engineering layer that makes agent workflows survive contact with production: durable state that outlives crashes, retries with backoff, timeouts, checkpointing, resumption, observability. It answers the unglamorous question every real deployment hits: the process died at step 23 of 40 — now what?

    Definition A workflow orchestrator executes a defined graph of steps with durability guarantees: persistent state (every step's inputs/outputs journaled — the event-sourcing pattern from the agent-state topic, hardened); resumability (on crash, replay the journal to the last completed step and continue — requiring steps to be idempotent or transactional, Chapter 32); failure policy per step (retries with exponential backoff, timeouts, fallbacks, compensation); observability (traces, step-level metrics, human-inspectable runs). The agent twist on classical orchestration (Airflow/Temporal-style): steps may be LLM calls — nondeterministic, so replay must journal their outputs rather than re-execute them (re-running an LLM step during recovery may produce a different answer than the one later steps already consumed).
    Worked example Crash and resume. A 12-step document-processing workflow dies (OOM) during step 8. Journal holds: steps 1–7 complete with outputs; step 8 started, no completion record. Recovery: reload state from journal (no re-execution — step 3's LLM summary is read back verbatim, not regenerated); step 8's policy says idempotent → safe to re-run; steps resume 8→12. Total loss: one step's partial work. Without journaling, recovery re-runs 1–7: step 3's regenerated summary differs slightly, step 5's extraction (keyed to the old summary's phrasing) now mismatches — the workflow "resumes" into a subtly inconsistent state that fails mysteriously at step 11. Determinism-by-journaling is what makes agentic workflows debuggable at all.
    Where this goes Idempotency, retries and transactional semantics get their formal treatment in Chapter 32; orchestrating multiple agents with private states is Chapter 33; and monitoring the orchestrated whole is Chapter 34's runtime verification.

    2. MED Why must LLM steps be journaled-and-replayed rather than re-executed during recovery, while a pure function step could be either?
      Solution
      Recovery correctness requires the resumed run to be consistent with what already happened: later steps consumed specific earlier outputs. def tok(s): return re.findall(r"[a-z0-9]+", s.lower())

# --- BM25 ---
class BM25:
    def __init__(self, docs, k1=1.5, b=0.75):
        self.k1, self.b = k1, b
        self.toks = [tok(d) for d in docs]
        self.N = len(docs)
        self.avgdl = sum(map(len, self.toks)) / self.N
        self.df = Counter(t for d in self.toks for t in set(d))
        self.inv = defaultdict(list)          # term -> [(doc, tf)]
        for i, d in enumerate(self.toks):
            for t, f in Counter(d).items():
                self.inv[t].append((i, f))
    def idf(self, t):
        n = self.df.get(t, 0)
        return math.log((self.N - n + 0.5) / (n + 0.5) + 1)
    def search(self, q):
        scores = defaultdict(float)
        for t in tok(q):
            for i, f in self.inv.get(t, []):
                dl = len(self.toks[i])
                denom = f + self.k1 * (1 - self.b + self.b * dl / self.avgdl)
                scores[i] += self.idf(t) * f * (self.k1 + 1) / denom
        return sorted(scores.items(), key=lambda x: -x[1])

    n = np.linalg.norm(v)

D = np.stack([vec(d) for d in docs])

    return sorted(sc.items(), key=lambda x: -x[1])

        if t not in memo:

            memo[t] = d + max((cp(x) for x in deps), default=0)
        return memo[t]
    end = max(tasks, key=cp)
    return cp(end)

def run(tasks, workers):
    done, failed, attempts = set(), set(), {t: 0 for t in tasks}
    ready = [t for t, (deps, _, _) in tasks.items() if not deps]
    busy = []                      # heap of (finish_time, task)
    t_now, idle_workers = 0.0, workers
    log = []
    while ready or busy:
        while ready and idle_workers > 0:
            task = ready.pop(0); idle_workers -= 1
            deps, dur, _ = tasks[task]
            heapq.heappush(busy, (t_now + dur, task))
        if not busy: break
        t_now, task = heapq.heappop(busy); idle_workers += 1
        deps, dur, pf = tasks[task]
        attempts[task] += 1
        ok = random.random() >= pf or attempts[task] > 1   # first try may fail
        if not ok and attempts[task] <= MAX_RETRY:
            log.append(f"t={t_now:5.1f} {task} FAILED (verifier) -> retry")
            ready.append(task); continue
        if not ok:
            failed.add(task); log.append(f"t={t_now:5.1f} {task} FAILED permanently"); continue
        done.add(task); log.append(f"t={t_now:5.1f} {task} done (attempt {attempts[task]})")
        for t2, (d2, _, _) in tasks.items():
            if t2 not in done and t2 not in [x for _, x in busy] and t2 not in ready:
                if all(d in done for d in d2): ready.append(t2)
    blocked = [t for t in tasks if t not in done and t not in failed]
    return t_now, log, failed, blocked

    Lab 3 — Memory with scoring, consolidation, and contradiction check Build a mini memory store: records with (text, time, importance, source-trust); retrieval scored by similarity+recency+importance; a consolidation pass that merges near-duplicates; a write-time contradiction check on structured slots.

    import time, math, re
import numpy as np
from collections import defaultdict

def emb(text):                     # toy embedding: hashed char-3grams, normalized
    v = np.zeros(256)
    s = re.sub(r"\s+", " ", text.lower())
    for i in range(len(s) - 2): v[hash(s[i:i+3]) % 256] += 1
    n = np.linalg.norm(v); return v / n if n else v

class Memory:
    def __init__(self): self.recs = []     # dicts
    def write(self, text, importance=0.5, trust=0.5, slot=None, value=None, t=None):
        t = time.time() if t is None else t
        # contradiction check on structured slots
        if slot is not None:
            for r in self.recs:
                if r.get("slot") == slot and r.get("value") != value and not r.get("superseded"):
                    newer = t > r["t"]; stronger = trust >= r["trust"]
                    if newer and stronger:
                        r["superseded"] = True
                        print(f"  [conflict] {slot}: '{r['value']}' -> '{value}' (newer+trusted wins)")
                    else:
                        print(f"  [conflict] {slot}: keeping '{r['value']}', flagging new claim")
                        importance = max(importance, 0.9)   # surface the dispute
        self.recs.append(dict(text=text, e=emb(text), t=t, imp=importance,
                              trust=trust, slot=slot, value=value, superseded=False))
    def retrieve(self, q, k=3, now=None, decay=0.9995):
        now = time.time() if now is None else now
        qe = emb(q); out = []
        for r in self.recs:
            if r["superseded"]: continue
            rec = decay ** ((now - r["t"]) / 60)           # per-minute decay
            out.append((float(qe @ r["e"]) + rec + r["imp"], r))
        return sorted(out, key=lambda x: -x[0])[:k]
    def consolidate(self, thresh=0.9):
        merged = 0
        for i, a in enumerate(self.recs):
            if a["superseded"]: continue
            for b in self.recs[i+1:]:
                if b["superseded"]: continue
                if float(a["e"] @ b["e"]) > thresh:
                    keep, drop = (a, b) if a["imp"] >= b["imp"] else (b, a)
                    keep["imp"] = min(1.0, keep["imp"] + 0.1)   # merged support
                    drop["superseded"] = True; merged += 1
        return merged
